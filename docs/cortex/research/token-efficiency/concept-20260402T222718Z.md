# Research Dossier: token-efficiency — concept

**Slug:** token-efficiency
**Phase:** concept
**Timestamp:** 20260402T222718Z
**Depth:** standard

---

## Summary

The Cortex system already has most of the infrastructure needed for token tracking — context percentage flows through hooks, power-search tracks external API costs in SQLite, and Claude Code's session JSONL transcripts contain per-turn token breakdowns. The main work is (1) refactoring cortex-research to use power-search as its backend (6 of 9 API calls map directly, 2 need orchestration wrappers, 1 requires a design decision), and (2) wiring a lightweight token ledger that reads from existing data sources (session JSONL transcripts, hook context metrics, power-search usage DB) and persists to a unified store for offline analysis.

---

## Findings

### A. cortex-research → power-search Migration

- **6 direct fits (no adaptation):** Quick/Perplexity → `Intent.DEEP_RESEARCH`, Tavily search → `Intent.WEB_SEARCH`, Jina extraction → `Intent.READ_URL`, Firecrawl → `Intent.SCRAPE_URL`, Crawl4AI → `Intent.CRAWL_SITE`, YouTube → `Intent.YOUTUBE_VIDEO`
- **2 partial fits (need orchestration wrapper):** Gemini synthesis/fact-check → `Intent.GENERATE` with custom prompt; Standard Path's multi-step search-extract-gap-fill loop requires calling `search()` multiple times in sequence — power-search handles individual steps, cortex-research must chain them
- **1 no-fit:** gpt-researcher (`--depth deep`) is a standalone research orchestrator with its own Tavily integration and iteration loops. Power-search has no equivalent. Options: replace with Perplexity deep research, keep gpt-researcher as a separate path, or drop `--depth deep`
- **New capabilities gained for free:** Google grounded search, YouTube search (not just single video), provider fallback chains, cost tracking in SQLite
- **Cost tracking comes automatically:** Every `search()` call records provider, intent, query, cost, tokens_in, tokens_out, elapsed_ms to `~/.power-search/usage.db`

### B. Power-search SQLite Schema (Already Built)

- **Database:** `~/.power-search/usage.db` (28 KB, 33 queries recorded, $0.52 spent so far)
- **Schema:** `usage(id, ts, provider, intent, query, cost, tokens_in, tokens_out, elapsed_ms)` — tracks everything needed for external API cost analysis
- **9 providers** with per-provider cost formulas: Perplexity ($3/$15 per 1M in/out + $0.008/req), Gemini ($0.30/$2.50), Jina (free/$0.0001), Tavily ($0.008-0.016/req), OpenAI ($2.50/$10), Firecrawl ($0.005/page), Crawl4AI (free), Gemini Grounded (+$0.036 surcharge), Gemini YouTube (token-based)
- **Routing modes:** smart (default), cheapest, quality — each reorders provider chains per intent
- **Budget enforcement:** Optional `daily_budget` config with `BudgetExceededError`
- **Extensible:** `Tracker.record()` accepts arbitrary provider/intent strings — can add "claude" as a provider

### C. Claude Code Token Observability

- **Session JSONL transcripts** (`~/.claude/projects/<slug>/<session-id>.jsonl`) are the richest source: per-turn `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` with cache tier breakdowns
- **Hooks do NOT receive token counts** — only `context_window.remaining_percentage` (a percentage, not absolute tokens)
- **Workaround:** Hooks receive `transcript_path` in their stdin JSON — a hook can read the JSONL transcript and parse the last entry to extract per-turn usage. This is the viable path for real-time token tracking inside a running session
- **`/cost` command** shows session cost but is interactive-only, not programmatic
- **`--print --output-format json`** gives complete token breakdown but only works in non-interactive mode
- **Telemetry events** (`~/.claude/telemetry/1p_failed_events`) contain session-level totals (`last_session_cost`, `last_session_total_input_tokens`, etc.) — fragile but rich
- **Third-party tools:** `ccusage` (parses JSONL transcripts), Claude-Code-Usage-Monitor (real-time charts)

### D. Cortex Hook Interception Points

- **13 hook scripts** across **9 Claude Code lifecycle events** (SessionStart, PreToolUse, PostToolUse, PreCompact, PostCompact, Stop, TaskCreated, TaskCompleted, TeammateIdle)
- **Context metrics bridge already exists:** `gsd-statusline.js` writes `{remaining_percentage, used_pct, timestamp}` to `/tmp/claude-ctx-{session_id}.json` — PostToolUse hooks already read this
- **Context warnings already fire** at 35% and 25% remaining (gsd-context-monitor.js)
- **Hot-context checkpoints** written at 40% context used (context-checkpoint.js)
- **Compaction hooks** (PreCompact/PostCompact) can measure compression efficiency
- **TaskCreated/TaskCompleted hooks** can capture context snapshots at task boundaries
- **Key limitation:** Only percentages, not absolute token counts, flow through hooks. For absolute counts, must parse the session JSONL transcript

## Trade-offs

### Option: Replace gpt-researcher with Perplexity deep research
**Pros:** Unified interface, cost tracking, no separate OpenAI dependency
**Cons:** Perplexity is single-call — loses gpt-researcher's multi-step iteration, source validation, and custom research methodology
**Verdict:** selected — gpt-researcher usage is rare and Perplexity's sonar-pro is comparable for most research tasks. Keep `--depth deep` flag but route to `Intent.DEEP_RESEARCH` with quality routing mode

### Option: Token tracking via session JSONL parsing (in PostToolUse hook)
**Pros:** Per-turn absolute token counts, cache hit data, no external dependencies, data already exists
**Cons:** Adds ~10-50ms file read per hook invocation, JSONL format may change between Claude Code versions, parsing last line of growing file has edge cases
**Verdict:** selected — the latency is acceptable (hooks are async for PostToolUse), and this is the only path to absolute token counts within a running session

### Option: Token tracking via context_window.remaining_percentage only
**Pros:** Zero additional I/O, already flowing through hooks, no JSONL parsing
**Cons:** Percentage only — can't derive absolute counts without knowing total context window size (which varies by model), can't track cache hits or input/output split
**Verdict:** rejected as primary source — useful as a supplementary signal but insufficient for the "understand what's going on" goal

### Option: Extend power-search SQLite to also store Claude token usage
**Pros:** Single database for all cost data, unified queries, power-search already has Tracker API
**Cons:** Conceptual mismatch — power-search tracks external API costs per search query, Claude tokens are per-turn orchestration costs. Different granularity and lifecycle
**Verdict:** deferred — keep separate stores initially (power-search for external API costs, token-ledger for Claude usage), consider unification later if the schema naturally converges

### Option: Store token data in JSONL vs SQLite
**Pros (JSONL):** Append-only, no schema migration, human-readable, simple to implement
**Pros (SQLite):** Queryable, aggregatable, power-search already uses it, supports indexes
**Cons (JSONL):** Querying requires full scan or external tools
**Cons (SQLite):** Schema changes need migration, slightly more complex writes
**Verdict:** selected SQLite — matches power-search's approach, enables `SELECT SUM(tokens) WHERE phase='research'` style queries, and the "analyze later" use case benefits from structured queries

## Recommendations

- **Phase the work into two deliverables:** (1) Refactor cortex-research SKILL.md to use power-search `search()` calls instead of raw API calls, keeping the multi-step orchestration logic but swapping the transport layer. (2) Add a token-ledger system that collects Claude token usage from session JSONL transcripts via a PostToolUse hook and persists to SQLite
- **For cortex-research refactor:** Replace 6 direct-fit API calls with `search()`, wrap the Standard Path's multi-step loop to call `search()` sequentially, route `--depth deep` to `Intent.DEEP_RESEARCH` with quality mode. Keep phase routing (concept/implementation/evals) and dossier templating unchanged
- **For token ledger:** Create a new PostToolUse hook (`cortex-token-tracker.sh` or `.js`) that reads `transcript_path` from hook input, parses the last JSONL entry for usage data, and appends to `~/.cortex/token-ledger.db` (SQLite). Schema: `(id, ts, session_id, slug, phase, turn_number, input_tokens, output_tokens, cache_creation_tokens, cache_read_tokens, cost_usd, context_remaining_pct)`
- **Leverage existing infrastructure:** The context metrics bridge (`/tmp/claude-ctx-{session_id}.json`), compaction hooks, and task boundary hooks already provide the interception points — new code is minimal
- **Don't build dashboards or inline display** — per the clarify brief, this is storage for offline analysis. Provide a simple CLI query script (`cortex-token-report.sh`) that runs SQLite queries against the ledger

## Open Questions

- Is the session JSONL transcript format stable enough to rely on for token extraction, or should we treat it as fragile and build a fallback?
- Should the token ledger live in `~/.cortex/` (global, survives project switches) or in `{project}/.cortex/` (project-scoped)?
- How should compaction events be represented in the ledger? Compaction resets the effective context but doesn't consume tokens in the traditional sense
- What's the right granularity for efficiency strategies — per-command model routing, or broader phase-level strategies (e.g., "use haiku for all discuss phases")?
- Should the token-ledger hook fire on every PostToolUse, or only on Stop events (less granular but lower overhead)?
