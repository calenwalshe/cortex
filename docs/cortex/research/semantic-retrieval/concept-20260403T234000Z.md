## Summary

Benchmarking revealed a critical constraint: sentence-transformers model load is ~13 seconds regardless of cache state — completely unsuitable for hooks with <5s budgets. The viable architecture splits embedding and retrieval into two distinct paths: **embed at compaction time** (background, latency-tolerant) using either sentence-transformers or ollama, and **retrieve at query time** using pre-computed numpy arrays (18ms for cosine similarity over 1K facts, no model load required). This split makes retrieval hook-safe while keeping embedding quality high.

---

## Benchmark Results

### Model Load Time

| Approach | Cold Start | Warm Start | Notes |
|----------|-----------|------------|-------|
| sentence-transformers all-MiniLM-L6-v2 | ~13s | ~13s | Model reload every invocation — no warm cache benefit for subprocess |
| ollama nomic-embed-text | ~0.7s (model already loaded) | ~0.1s | Server process keeps model warm |

**Verdict:** sentence-transformers is too slow for any hook-time use. ollama is fast for single queries (97ms) but requires the ollama daemon to be running.

### Embedding Speed

| Approach | 100 facts | 1000 facts | Facts/sec |
|----------|-----------|------------|-----------|
| sentence-transformers (384-dim) | 0.35s | 2.41s | ~414/s |
| ollama nomic-embed-text (768-dim) | ~4.5s (est.) | ~45s (est.) | ~22/s |

**Verdict:** sentence-transformers is 19x faster for batch embedding. For compaction-time embedding (background, latency-tolerant), sentence-transformers is the clear winner.

### Retrieval Speed (pre-computed embeddings)

| Operation | Latency | Notes |
|-----------|---------|-------|
| numpy .npy load (100 facts x 384) | <1ms | 150KB file |
| Cosine similarity over 1K facts | 18ms | No model needed — pure numpy |
| Cosine similarity over 10K facts | ~180ms (projected) | Still fast — linear scale |

**Verdict:** Retrieval with pre-computed embeddings is trivially fast. No model load required at query time.

### Storage Size

| Facts | .npy size (384-dim) | .npy size (768-dim) |
|-------|---------------------|---------------------|
| 100 | 150KB | 300KB |
| 1,000 | 1.5MB | 3MB |
| 10,000 | 15MB | 30MB |

**Verdict:** 384-dim is sufficient. Storage is negligible even at 10K facts.

## Architecture Decision: Two-Phase Split

### Phase A: Embed (at compaction time)

- **When:** PostCompact hook, after fact extraction
- **How:** Python subprocess calling sentence-transformers
- **Model:** all-MiniLM-L6-v2 (384-dim — fast, small, good quality)
- **Output:** `.cortex/fact-embeddings.npy` (numpy array) + `.cortex/fact-index.json` (fact ID → row mapping)
- **Latency budget:** Relaxed — PostCompact can be async. 13s model load + ~2s for 1K facts = 15s total, acceptable for background hook
- **Incremental:** Only embed new facts (track last embedded fact count or ID)

### Phase B: Retrieve (at query time)

- **When:** Session-start hook, skill invocations, or on-demand via a CLI script
- **How:** Python script or Node.js script with numpy — load .npy, compute cosine similarity, return top-K
- **Model required:** NO — pre-computed embeddings only need numpy for dot product
- **Latency:** <50ms for load + cosine over 1K facts
- **Query embedding:** This is the one place we need the model at query time. Two options:
  - **Option A (ollama):** curl to localhost:11434/api/embed — 97ms, requires daemon running
  - **Option B (pre-compute query patterns):** For known query patterns (session-start, per-skill), pre-compute query embeddings. For ad-hoc queries, fall back to ollama.
  - **Option C (sentence-transformers subprocess):** 13s cold start — unacceptable for hooks. Only viable for CLI-driven ad-hoc queries where user expects latency.

### Recommended Query-Time Approach

**Use ollama for query embedding (Option A)** with graceful degradation:
1. If ollama is running: embed query via API (97ms), cosine over facts (18ms) → total ~120ms
2. If ollama is not running: fall back to loading all facts (no semantic filtering) with a warning
3. This keeps the dependency optional — Cortex works without ollama, just without semantic filtering

## Open Questions Resolved

| Question | Answer | Evidence |
|----------|--------|----------|
| Storage format | numpy .npy for embeddings + JSON index for ID mapping | .npy is simplest, 150KB/100 facts, <1ms load |
| Model choice | all-MiniLM-L6-v2 for embedding, ollama nomic-embed-text for query-time | MiniLM is 19x faster batch; ollama is only option for fast single-query |
| Cold start | Split architecture eliminates cold start — model only loads at compaction time (async) | 13s load is fine for background PostCompact |
| Query interface | Python CLI: `cortex-retrieve.py <query> [--top-k N]` → JSON on stdout | Hooks call via subprocess, parse JSON output |
| Embedding staleness | Track `.cortex/fact-embeddings.meta.json` with `{last_embedded_count: N, model: "..."}` | Re-embed only when facts.jsonl has more lines than last_embedded_count |
| Retrieval consumers | session-start (load relevant context), cortex-status (show relevant facts), any skill via helper | Start with session-start, expand later |

## Remaining Design Questions (for spec)

1. **Embedding dimension mismatch:** all-MiniLM-L6-v2 is 384-dim, ollama nomic-embed-text is 768-dim. If we embed with MiniLM and query with ollama, dimensions don't match. **Options:**
   - **A)** Use ollama for both embed and query (slower batch but consistent dimensions)
   - **B)** Use MiniLM for both (fast batch, but 13s query-time cold start — only OK for background/CLI)
   - **C)** Use MiniLM for embed, and also pre-compute + cache the MiniLM query embeddings for common query patterns; use ollama only for novel queries with a dimension adapter
   - **Recommendation:** Option A (ollama for both). The batch embedding speed (22 facts/sec) is acceptable for compaction — even 1K facts takes ~45s, which is fine for an async hook. Consistency > speed here.

2. **Async PostCompact:** Current PostCompact hook is synchronous. Embedding 100+ facts takes seconds. Should we make the embedding step async (fire-and-forget) or accept the latency?

3. **Graceful degradation surface:** What exactly happens when ollama isn't running? Load all facts? Load most recent N facts? Load nothing?

## Trade-offs

| Decision | Chosen | Alternative | Why |
|----------|--------|-------------|-----|
| Embed at compaction vs real-time | Compaction (batch) | Real-time per-fact | Hooks can't afford 13s model load; batch amortizes cost |
| numpy .npy vs SQLite BLOB | numpy .npy | SQLite | Simpler, faster, no dependency; SQLite adds complexity for no gain at <10K facts |
| ollama for query embedding | ollama API | sentence-transformers subprocess | 97ms vs 13s; ollama daemon usually running |
| 384-dim vs 768-dim | 768-dim (ollama) pending decision | 384-dim (MiniLM) | Dimension consistency between embed and query is critical — can't mix |
| Single .npy file vs per-compaction files | Single .npy (overwritten) | Per-compaction archives | Simpler; old embeddings aren't useful — facts.jsonl is the source of truth |
