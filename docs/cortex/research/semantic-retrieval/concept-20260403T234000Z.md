## Summary

Benchmarking revealed a critical constraint: sentence-transformers model load is ~13 seconds regardless of cache state — completely unsuitable for hooks with <5s budgets. The viable architecture splits embedding and retrieval into two distinct paths: **embed at compaction time** (background, latency-tolerant) using either sentence-transformers or ollama, and **retrieve at query time** using pre-computed numpy arrays (18ms for cosine similarity over 1K facts, no model load required). This split makes retrieval hook-safe while keeping embedding quality high.

## Benchmark Results

### Model Load Time

| Approach | Cold Start | Warm Start | Notes |
|----------|-----------|------------|-------|
| sentence-transformers all-MiniLM-L6-v2 | ~13s | ~13s | Model reload every invocation — no warm cache benefit for subprocess |
| ollama nomic-embed-text | ~0.7s (model already loaded) | ~0.1s | Server process keeps model warm |

**Verdict:** sentence-transformers is too slow for any hook-time use. ollama is fast for single queries (97ms) but requires the ollama daemon to be running.

### Embedding Speed

| Approach | 100 facts | 1000 facts | Facts/sec |
|----------|-----------|------------|-----------|
| sentence-transformers (384-dim) | 0.35s | 2.41s | ~414/s |
| ollama nomic-embed-text (768-dim) | ~4.5s (est.) | ~45s (est.) | ~22/s |

**Verdict:** sentence-transformers is 19x faster for batch embedding. For compaction-time embedding (background, latency-tolerant), sentence-transformers is the clear winner.

### Retrieval Speed (pre-computed embeddings)

| Operation | Latency | Notes |
|-----------|---------|-------|
| numpy .npy load (100 facts x 384) | <1ms | 150KB file |
| Cosine similarity over 1K facts | 18ms | No model needed — pure numpy |
| Cosine similarity over 10K facts | ~180ms (projected) | Still fast — linear scale |

**Verdict:** Retrieval with pre-computed embeddings is trivially fast. No model load required at query time.

### Storage Size

| Facts | .npy size (384-dim) | .npy size (768-dim) |
|-------|---------------------|---------------------|
| 100 | 150KB | 300KB |
| 1,000 | 1.5MB | 3MB |
| 10,000 | 15MB | 30MB |

**Verdict:** 384-dim is sufficient. Storage is negligible even at 10K facts.

## Architecture Decision: Two-Phase Split

### Phase A: Embed (at compaction time — async PostCompact hook)

- **When:** PostCompact hook, after fact extraction (separate async hook entry)
- **How:** Python script calling ollama `/api/embed` with batch input
- **Model:** `nomic-embed-text` (768-dim) via ollama HTTP API
- **Output:** `.cortex/fact-embeddings.npy` (numpy array) + `.cortex/fact-index.json` (fact ID → row mapping)
- **Latency:** 2.4s for 53 facts (current count) — async, non-blocking
- **Incremental:** Only embed new facts (track last embedded fact count or ID in `.cortex/fact-embeddings.meta.json`)

### Phase B: Retrieve (at query time — <100ms)

- **When:** Session-start hook, skill invocations, or on-demand via a CLI script
- **How:** Python script — load .npy, embed query via ollama, cosine similarity, return top-K
- **Model at query time:** ollama `nomic-embed-text` (77ms per query, model stays warm via systemd)
- **Latency:** 79ms end-to-end (2ms npy load + 77ms query embed + 0.07ms cosine)
- **Degradation:** If ollama unreachable or .npy missing → load all facts, log warning to stderr

## Open Questions Resolved

| Question | Answer | Evidence |
|----------|--------|----------|
| Storage format | numpy .npy for embeddings + JSON index for ID mapping | .npy is simplest, 150KB/100 facts, <1ms load |
| Model choice | all-MiniLM-L6-v2 for embedding, ollama nomic-embed-text for query-time | MiniLM is 19x faster batch; ollama is only option for fast single-query |
| Cold start | Split architecture eliminates cold start — model only loads at compaction time (async) | 13s load is fine for background PostCompact |
| Query interface | Python CLI: `cortex-retrieve.py <query> [--top-k N]` → JSON on stdout | Hooks call via subprocess, parse JSON output |

| Retrieval consumers | session-start (load relevant context), cortex-status (show relevant facts), any skill via helper | Start with session-start, expand later |

## Design Questions — Resolved (2026-04-04)

All three open questions resolved via live benchmarks on target machine.

### 1. Embedding dimension mismatch → ollama for both (768-dim)

**Decision:** Use ollama `nomic-embed-text` (768-dim) for both batch embedding and query embedding.

**Evidence:**
- `all-MiniLM-L6-v2` = 384-dim, `nomic-embed-text` = 768-dim — cannot mix (cosine on mismatched dims is meaningless)
- ollama batch: 22.1 facts/sec via single-call batching (53 facts in 2.40s)
- sentence-transformers is 19x faster batch but creates the mismatch; not worth it
- 768-dim storage is 2x larger but still negligible (163KB for 53 facts)

**Rejected alternatives:**
- sentence-transformers for both: 13s cold start per subprocess invocation kills query-time use
- Mixed dims with adapter: unnecessary complexity for zero gain

### 2. Async PostCompact → Yes, separate async hook entry

**Decision:** Embedding runs as a second PostCompact hook with `"async": true`.

**Evidence:**
- Current PostCompact hook is synchronous (no `"async"` flag in settings.json)
- Fact extraction (JS) is fast and must remain synchronous — it produces facts.jsonl
- Embedding step adds 2.4s for 53 facts — would block compaction if synchronous
- Precedent: the Stop hook already uses `"async": true` in this project's settings.json
- Pattern: sync hook writes facts.jsonl → async hook reads facts.jsonl and writes .npy

### 3. Graceful degradation → Full-load fallback with warning

**Decision:** When ollama is unreachable or `.npy` is missing, load all facts with a stderr warning.

**Evidence:**
- The current system has no semantic filtering — it loads all handoff files equally
- Falling back to "load all facts" is falling back to current behavior (no regression)
- ollama runs as systemd service (`active` state confirmed), but availability is not guaranteed
- Silent failure would mask embedding staleness; warning makes it observable

## Trade-offs

| Decision | Chosen | Alternative | Why |
|----------|--------|-------------|-----|
| Embed at compaction vs real-time | Compaction (async batch) | Real-time per-fact | Hooks can't afford model load; batch amortizes cost |
| numpy .npy vs SQLite BLOB | numpy .npy | SQLite | Simpler, faster, no dependency; SQLite adds complexity for no gain at <10K facts |
| ollama for both embed + query | ollama `nomic-embed-text` 768-dim | sentence-transformers 384-dim | Dimension consistency is mandatory; ollama batch (22/s) is acceptable for async hook |
| Sync vs async PostCompact | Async (separate hook entry) | Synchronous in existing hook | 2.4s embedding would block compaction; Stop hook already uses async pattern |
| Degradation when ollama down | Load all facts + stderr warning | Load nothing / load recent N | Current system loads all — fallback = no regression; warning makes it observable |
| Single .npy file vs per-compaction | Single .npy (overwritten) | Per-compaction archives | Simpler; old embeddings aren't useful — facts.jsonl is the source of truth |
