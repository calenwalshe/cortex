# Research Dossier: complexity-tiers -- concept

**Slug:** complexity-tiers
**Phase:** concept
**Timestamp:** 20260406T120000Z
**Depth:** standard

---

## Summary

This dossier designs three pipeline variants (trivial, standard, complex) that branch from the `complexity` field already present in the clarify-brief template. The goal is to eliminate wasted tokens on simple work and add mandatory safety depth on risky work, while keeping standard as the unchanged baseline. The design also specifies the upgrade/downgrade mechanism: how downstream commands detect that complexity was mis-labeled and correct course.

---

## 1. Current Baseline (Standard Pipeline)

The standard pipeline is today's only pipeline. Every slug, regardless of difficulty, traverses the full sequential spine:

| Step | Command | Artifacts Produced |
|------|---------|--------------------|
| 1. Clarify | `/cortex-clarify` | clarify-brief.md |
| 2. Research (concept) | `/cortex-research --phase concept` | concept dossier |
| 3. Research (implementation) | `/cortex-research --phase implementation` | implementation dossier |
| 4. Research (evals) | `/cortex-research --phase evals` | eval-proposal.md |
| 5. Spec | `/cortex-spec` | spec.md, gsd-handoff.md, contract-001.md |
| 6. Bridge | `/cortex-bridge` | .planning/ scaffold |
| 7. Execute | GSD | code + commits |
| 8. Validate | contract validators | eval-status.md |
| 9. Repair (if needed) | repair contracts | repair-contract-N.md |
| 10. Assure | all evals pass | final eval-status.md |
| 11. Close | `/cortex-close` | archive |

**Token cost profile:** ~15,000-40,000 tokens per slug depending on research depth and repair cycles. A trivial rename or config change pays the same cost as a multi-file architectural change.

## 2. Pipeline Variant Design

### 2.1 Trivial Pipeline

**When to use:** Single-file changes, config tweaks, dependency bumps, documentation fixes, typo corrections, straightforward bug fixes with known root cause. The problem is fully understood before starting.

#### What Gets Skipped

| Standard Step | Trivial Behavior | Rationale |
|---------------|------------------|-----------|
| Research (all phases) | **Skipped entirely** | Nothing to discover -- the solution is known |
| Spec sections 3, 4, 5, 6 | **Omitted** (Architecture Decision, Interfaces, Dependencies, Risks) | No architectural decisions to make |
| Eval proposal | **Skipped** | Validators in the thin contract are sufficient |
| `/cortex-bridge` | **Skipped** | No GSD scaffold needed -- execute inline or via `/gsd:fast` / `/gsd:quick` |
| `/cortex-review` | **Optional** (human decides) | Low-risk changes rarely need formal review |
| `/cortex-audit` | **Skipped** | No security surface change |
| Repair budget | **1 attempt max** | If a trivial fix needs 2 repairs, it was mis-classified |

#### Thin Spec

The thin spec collapses 9 sections into 4:

```markdown
# Spec: {SLUG} (trivial)

**Slug:** {SLUG}
**Timestamp:** {TIMESTAMP}
**Status:** {STATUS}
**Complexity:** trivial

## 1. Problem
{one sentence}

## 2. Scope
### In Scope
- {bulleted list}
### Out of Scope
- {bulleted list}

## 7. Sequencing
{numbered steps -- typically 1-3}

## 9. Acceptance Criteria
- [ ] {criterion}
```

Sections 3 (Architecture Decision), 4 (Interfaces), 5 (Dependencies), 6 (Risks), 8 (Tasks) are omitted. The spec template enforces this by checking `complexity: trivial` and skipping those sections without error.

#### Thin Contract

```markdown
# Contract: {SLUG} -- trivial

**ID:** cortex-{SLUG}-001
**Slug:** {SLUG}
**Phase:** implementation
**Status:** draft
**Complexity:** trivial
**Repair Budget:** max_repair_contracts: 1

## Objective
{one sentence}

## Deliverables
- {file paths}

## Write Roots
- {paths}

## Done Criteria
- [ ] {criteria -- typically 1-3 items}

## Validators
- [ ] [external] {test or lint command}

## Completion Promise
CORTEX_PROMISE: cortex-{SLUG}-001 COMPLETE
```

Omitted sections: Scope (covered by write roots), Eval Plan (validators are sufficient), Approvals (human approval at spec time covers it), Failed Approaches (N/A for first contract), Why Previous Failed (N/A), Rollback Hints (trivial changes are trivially revertible).

#### Bridge Behavior

`/cortex-bridge` is **skipped**. Trivial work executes via:
- `/gsd:fast` for inline single-commit tasks, or
- `/gsd:quick` for tasks needing atomic commit tracking but no subagent overhead

The thin contract's done criteria are checked directly after execution, without a full `.planning/` scaffold.

#### Estimated Token Savings

| Component | Standard Cost | Trivial Cost | Savings |
|-----------|--------------|--------------|---------|
| Research (concept + impl) | ~5,000-10,000 | 0 | 100% |
| Spec (9 sections) | ~3,000-5,000 | ~800-1,200 | 70-80% |
| Contract (full) | ~2,000-3,000 | ~500-800 | 65-75% |
| Bridge + scaffold | ~2,000-3,000 | 0 | 100% |
| Review/Audit | ~3,000-5,000 | 0 (optional) | 100% |
| **Total** | **~15,000-26,000** | **~1,300-2,000** | **~85-92%** |

### 2.3 Complex Pipeline

**When to use:** Multi-file architectural changes, new subsystems, security-sensitive work, public API changes, cross-system integrations, anything touching auth/data/secrets, work with unclear requirements or multiple viable approaches.

#### What Gets Added

| Standard Step | Complex Behavior | Rationale |
|---------------|------------------|-----------|
| Research | **Both concept AND implementation phases mandatory** | Must explore problem space and solution space separately |
| Research (evals) | **Mandatory** -- eval-proposal.md required before spec | Can't spec without knowing how to verify |
| Spec section 3 | **ADR format mandatory** -- alternatives table with rejection rationale | Architectural decisions need recorded reasoning |
| Spec section 6 | **Risk register format** -- probability/impact/mitigation matrix | Risks need structured tracking, not prose |
| `/cortex-fit` | **Mandatory** if introducing new dependencies or tools | Prevents ecosystem drift |
| `/cortex-audit` | **Mandatory** before assure phase | Security review is not optional for complex work |
| `/cortex-review` | **Mandatory** with contract compliance section | No shortcuts on review |
| Eval plan | **Must exist before spec approval** (not after) | Eval criteria inform the spec, not the reverse |
| Repair budget | **5 attempts** (up from default 3) | Complex work legitimately needs more repair cycles |
| Cross-artifact coherence | **Mandatory validator** | Spec must address all clarify-brief goals and integrate all research findings |

#### Extended Validators

Complex contracts add these validators beyond the standard set:

```markdown
## Validators
- [ ] [external] {standard validators from spec}
- [ ] [external] Cross-artifact coherence: spec addresses all clarify-brief goals
- [ ] [external] All research findings referenced or explicitly deferred in spec
- [ ] [judgment] Architecture decision has rejection rationale for all alternatives
- [ ] [judgment] Risk register has mitigation for every P0/P1 risk
- [ ] [external] Security audit completed with no unresolved CRITICAL findings
- [ ] [judgment] Eval plan approved before execution began
```

#### Mandatory Research Phases

| Research Phase | Standard | Complex |
|----------------|----------|---------|
| Concept | Required (1 dossier minimum) | Required |
| Implementation | Optional | **Required** |
| Evals | Optional | **Required** -- must produce eval-proposal.md |
| Eval plan | Written after spec (optional timing) | **Written before spec approval** |

The eval-plan-before-spec rule is the key difference. In standard, you can spec first and figure out evals later. In complex, you must know how to verify the work before committing to build it. This prevents specs that are un-evaluable.

#### `/cortex-fit` Gate

When a complex slug introduces a new dependency, framework, or tool, `/cortex-fit` must run before `/cortex-spec`. The fit report's Tech Radar ring signal feeds into the spec's Dependencies section. If the fit report returns `Hold`, the dependency cannot be used without explicit human override.

#### Token Cost

| Component | Standard Cost | Complex Cost | Delta |
|-----------|--------------|--------------|-------|
| Research (concept + impl + evals) | ~5,000-10,000 | ~10,000-20,000 | +100% |
| Spec (9 sections + ADR + risk matrix) | ~3,000-5,000 | ~5,000-8,000 | +60% |
| Contract (extended validators) | ~2,000-3,000 | ~3,000-4,500 | +50% |
| Bridge + scaffold | ~2,000-3,000 | ~2,000-3,000 | 0% |
| Mandatory review + audit | ~3,000-5,000 | ~6,000-10,000 | +100% |
| Fit report (if needed) | 0 | ~2,000-3,000 | N/A |
| **Total** | **~15,000-26,000** | **~28,000-48,500** | **+70-90%** |

The added cost is justified: complex work that ships broken costs far more in repair cycles than the upfront intelligence investment.

## 4. Complexity Upgrade/Downgrade Mechanism

### 4.1 Upgrade Triggers

A command detects that work is harder than labeled and upgrades complexity. Upgrades are **one-way during a slug's lifecycle** -- once upgraded, a slug stays at the higher tier.

#### Signal Sources

| Signal | Detected By | Upgrade Path |
|--------|-------------|-------------|
| Research sets `reclarify_required: true` | `/cortex-research` | trivial -> standard, standard -> complex |
| >3 open questions with `severity: critical` | `/cortex-research` | trivial -> standard |
| >5 open questions total after concept research | `/cortex-research` | trivial -> standard |
| Research dossier recommends multiple viable architectures | `/cortex-research` | standard -> complex |
| Clarify brief lists security/auth/data constraints | `/cortex-clarify` | any -> complex |
| Write roots span >5 files or >3 directories | `/cortex-spec` | trivial -> standard |
| Contract requires >5 validators | `/cortex-spec` | trivial -> standard |
| First repair contract is created | `/cortex-review` / repair | trivial -> standard |
| Second repair contract is created | `/cortex-review` / repair | standard -> complex |
| `/cortex-fit` returns `Hold` or `Assess` | `/cortex-fit` | standard -> complex |
| Spec touches public API or cross-system boundary | `/cortex-spec` | standard -> complex |

#### Implementation

Each command that can trigger an upgrade does so by:

1. Checking `state.json` field `complexity` against the trigger conditions above.
2. If upgrade is warranted, writing the new complexity to `state.json`.
3. Emitting a structured message: `COMPLEXITY_UPGRADE: {old} -> {new} (reason: {signal})`.
4. Updating `current-state.md` with the upgrade record.
5. **Blocking further execution** until the upgrade's newly-required steps are completed.

The blocking behavior is critical. If a trivial slug upgrades to standard mid-spec, `/cortex-spec` blocks and requires research to be run first. The human sees the upgrade reason and can either:
- Accept (run the missing steps)
- Override (set `complexity_override: true` in state.json to force the original tier)

Override is logged in `decisions.md` for audit trail.

#### Upgrade State Machine

```
trivial ──upgrade──> standard ──upgrade──> complex
   │                    │                     │
   └────override────────┴─────override────────┘
         (logged, human-only, never automatic)
```

### 4.2 Downgrade Rules

Downgrades are **not automatic**. A slug classified as complex does not downgrade to standard even if the work turns out simpler than expected. Rationale:

1. The cost of running a complex pipeline on simple work is tokens (recoverable).
2. The cost of running a simple pipeline on complex work is bugs (not recoverable).
3. Asymmetric risk means "over-prepare" is always safer than "under-prepare."

**Exception:** A human can manually downgrade by editing `state.json` and setting `complexity_override: true` with a downgrade reason. This is logged in `decisions.md`. No command auto-downgrades.

### 4.3 Upgrade Detection Points in the Spine

```
clarify ─────────────────── [security/auth constraint check]
    │
research (concept) ──────── [reclarify, critical questions, multiple architectures]
    │
research (implementation) ─ [write root count, cross-system boundaries]
    │
spec ────────────────────── [validator count, write root count, public API]
    │
execute ─────────────────── (no detection -- GSD owns this)
    │
validate/repair ─────────── [repair contract count triggers upgrade]
    │
assure ──────────────────── (no detection -- too late to upgrade)
```

## 5. Implementation Considerations

### 5.1 State Schema Changes

`state.json` needs these new fields:

```json
{
  "complexity": "trivial|standard|complex",
  "complexity_override": false,
  "complexity_upgrades": [
    {
      "from": "trivial",
      "to": "standard",
      "reason": "research produced 4 critical open questions",
      "timestamp": "2026-04-06T12:00:00Z",
      "command": "/cortex-research"
    }
  ]
}
```

### 5.2 Template Variants

Two approaches for thin spec/contract:

**Option A: Conditional sections in existing templates.** Add `<!-- complexity: trivial — SKIP THIS SECTION -->` comments. Commands check complexity and skip sections.

**Option B: Separate template files.** `spec-trivial.md`, `contract-trivial.md`. Commands select the template based on complexity.

Recommendation: **Option A.** Fewer files to maintain. The templates already have comment blocks. Adding conditional markers is low friction and keeps the template count at 1 per artifact type.

### 5.3 Command Modifications Required

| Command | Change |
|---------|--------|
| `/cortex-clarify` | Writes `complexity` to state.json. Checks for security/auth/data keywords in constraints to auto-suggest complex. |
| `/cortex-research` | Checks complexity before running. If trivial, blocks with "research skipped for trivial slugs." If complex, blocks `/cortex-spec` until both concept and implementation dossiers exist. Checks upgrade triggers after producing dossier. |
| `/cortex-spec` | Selects thin vs full template. If complex, requires eval-plan to exist before proceeding. Checks upgrade triggers (write root count, validator count). |
| `/cortex-bridge` | If trivial, skips bridge and suggests gsd:fast/quick. |
| `/cortex-review` | If complex, mandatory (blocks assure without review artifact). |
| `/cortex-audit` | If complex, mandatory (blocks assure without audit artifact). |
| `/cortex-drive` | Reads complexity and adjusts autonomous decisions: trivial skips research/bridge/review, complex adds mandatory stops. |

### 5.4 Risks

| Risk | Mitigation |
|------|------------|
| Humans always pick "trivial" to skip steps | Upgrade mechanism catches under-classified work. Override audit trail creates accountability. |
| Upgrade blocking is frustrating mid-flow | Clear message: "Upgrading to standard because X. Run `/cortex-research` to continue." Override available for informed humans. |
| Three template variants = maintenance burden | Option A (conditional sections) keeps it to 1 template per artifact type. |
| Complex pipeline is too expensive for budget-constrained work | Human override exists. Complexity is a recommendation, not a prison. |

## 6. Open Questions

- Should `/cortex-drive` auto-select complexity based on the idea text (LLM classification), or always require human input?
  - Position: Human input at clarify time. LLM classification is a suggestion, not a decision. Evidence that would change this: data showing humans consistently misclassify complexity.
- Should trivial slugs skip the clarify brief entirely (direct to spec)?
  - Position: No. The clarify brief is the identity anchor for every slug. Even trivial work needs a one-sentence problem statement and acceptance criteria. Skipping it saves ~500 tokens but loses traceability.
- Should the upgrade mechanism be opt-in (human must approve) or opt-out (auto-upgrades unless human overrides)?
  - Position: Opt-out. Auto-upgrade with human override. The default should be safe (more depth), not fast (less depth). The human who wants speed can override explicitly.
