## Owner Summary

**What we found:** BLUF (bottom line up front) is definitively the right communication model for a returning multitasker with zero working memory. The four pillars of extreme clarity — precision, simplicity, familiarity, necessity — all point the same direction: lead with the outcome in plain language, then put everything else below a visual separator the owner can ignore. The two specific surfaces causing pain (research dossiers and spec.md) have the same root problem: they're structured for the writer's process, not the reader's decision.

**What it changes:** The fix is a consistent two-layer structure across both surfaces. Layer 1: 2-3 sentences in plain English answering "what happened / what was found / what's needed." No file paths, no jargon, no artifact references. Layer 2: all the existing content, unchanged, below a divider. This is purely additive — nothing gets removed.

**What's still open:** How to enforce the necessity filter so the Owner Summary doesn't get bloated over time. That's a spec-level decision.

## Summary

BLUF (Bottom Line Up Front) is the correct communication model for this use case. Research confirms it outperforms inverted pyramid (designed for narrative storytelling, not status updates) and progressive disclosure (an interactive UI pattern that doesn't apply to static terminal output). For a reader returning cold with no working memory, the structure is: outcome in 2-3 sentences → everything else below a visual separator. The four pillars of extreme clarity — precision, simplicity, familiarity, necessity — operationalize this: every sentence earns its place or gets cut. The "necessity" pillar is the most important: omit anything that doesn't help the owner decide or act. Prune after drafting, don't pre-censor.

The codebase audit identified the same root failure in both pain surfaces: **the structure follows the producer's process, not the reader's decision path.** Dossiers open with frontmatter and dense jargon-loaded summaries. Specs present sections in assembly-line order (Problem → Architecture → … → Acceptance Criteria) when the reader most needs to see Acceptance Criteria second — right after the Problem — to understand what winning looks like before committing to reading further. The fix is identical in both cases: add a plain-language owner layer first, don't change what's below it.

## Findings

- **BLUF wins for zero-context async users.** Military-derived communication model: 2-3 sentences covering situation, outcome/decision, and what's needed from the reader. The reader decides whether to read further in the first 10 seconds. Source: Perplexity research, confirmed against communications literature.

- **Progressive disclosure complements BLUF in static documents.** In terminal output (no interactivity), "progressive disclosure" means: owner-layer first, visual separator, detail layer below. The reader opts into the detail by scrolling, not by clicking. This matches the terminal medium.

- **The four pillars of extreme clarity are: precision, simplicity, familiarity, necessity.** Necessity is the most important: omit anything not required for the reader to understand or decide. "Draft fully, then prune ruthlessly." Source: technical writing research.

- **Decision layer / detail layer separation.** Decision layer: key outcomes, recommendations, what's needed — scannable in under 30 seconds. Detail layer: evidence, process, artifact paths — for readers who want depth. Never mix layers.

- **"Status line + delta" is the dev tool convention for returning users.** The formats that work across Linear, Devin, and GitHub: a single-line status ("what state are we in") plus a short delta list ("what changed since you last looked"). Not a step-by-step log of what the agent did.

- **Codebase audit finding: dossier `## Summary` section exists but is jargon-heavy.** The existing template has the right section in the right place. The failure is in how it's populated — it reads for an insider, not the owner. Fix: add an explicit `## Owner Summary` block above it that enforces plain language.

- **Codebase audit finding: spec.md section order is wrong for owner approval.** Current order: Problem → Architecture → Interfaces → Dependencies → Risks → Sequencing → Tasks → Acceptance Criteria. An owner wanting to approve a spec must read all nine sections before seeing the "what does winning look like" criteria. Fix: move Acceptance Criteria to section 2, immediately after Problem.

- **Codebase audit finding: cortex-drive Phase 6 HITL report is instructional, not enforced.** The Level 1 HITL report template is well-designed (plain language, no jargon, 4 bullets). But Phase 6 just says "follow the template" — no formula, no auto-generation. The template exists but relies on implementation discipline, which breaks under autonomous operation.

## Trade-offs

### Option: Add Owner Summary block to dossier template (additive)
**Pros:** No existing content removed. Backward compatible — existing dossiers remain valid. Easy to enforce: 3-bullet formula, plain-language rule, no-jargon rule. Low risk of scope creep.
**Cons:** Two summary sections (`## Owner Summary` and `## Summary`) creates mild redundancy. If the Owner Summary is good enough, no one reads the Summary below.
**Verdict:** selected — the redundancy is acceptable; the existing Summary is for completeness, the Owner Summary is for the human.

### Option: Replace the existing `## Summary` with a reformatted version
**Pros:** No redundancy. Cleaner template.
**Cons:** Breaking change — existing dossiers look different. Higher implementation complexity (rewrite instructions for cortex-research Phase 3). Risk that the "reformatted" summary drifts back toward jargon without an explicit plain-language constraint.
**Verdict:** rejected — additive is safer and achieves the same effect for the owner.

### Option: Reorder spec.md sections
**Pros:** Owners see the approval-critical information (Problem + Acceptance Criteria) in the first two sections. Matches decision-narrative reading order.
**Cons:** Breaks the expectation of readers who know the current section order. Requires updating cortex-spec SKILL.md to enforce the new order.
**Verdict:** selected — the current order is objectively wrong for the approval use case.

### Option: Enforce cortex-drive Phase 6 with a generation formula
**Pros:** Autonomous operation produces consistent Level 1 reports. Owner always gets a human-readable summary even without human intervention.
**Cons:** Adds implementation work to cortex-drive SKILL.md. Risk that formula is too rigid for all completion states.
**Verdict:** selected — the template already exists; the work is wiring it, not designing it.

## Recommendations

- **Dossier: add `## Owner Summary` as the first section after frontmatter.** 3-bullet formula: (1) what we found, (2) what it changes for the decision, (3) what's still open. Plain English only — no file paths, no jargon, no slug references. This section must pass the necessity filter: every word earns its place.

- **Spec.md: reorder sections to decision-narrative order.** New order: (1) Problem, (2) Acceptance Criteria, (3) Scope, (4) Architecture Decision, (5) Interfaces, (6) Dependencies, (7) Risks, (8) Sequencing, (9) Tasks. Owner can approve after sections 1-2 without reading the rest.

- **cortex-drive Phase 6: codify Level 1 HITL report with a generation formula.** Formula: status line (what was built, 1 sentence, no jargon) + up to 3 delta bullets (what happened, past tense, plain language) + 1 risk line (what's not covered, or "none identified") + what's needed from the owner (explicit ask or "nothing — slug is done"). Pull inputs from: contract objective → status line; last 3 decisions.md entries → delta bullets; contract risks section → risk line.

- **Apply necessity filter to all owner-facing text.** For every sentence in the Owner Summary and Phase 6 HITL report: "Does this help the owner decide or act right now?" If no, cut it. File paths, timestamps, artifact counts do not pass this test unless the owner needs to navigate somewhere.

- **All three changes are to templates and skill instructions, not production code.** Scope is: `templates/cortex/research-dossier.md`, `templates/cortex/spec.md`, `skills/cortex-drive/SKILL.md`, `skills/cortex-spec/SKILL.md`. No new files needed.
