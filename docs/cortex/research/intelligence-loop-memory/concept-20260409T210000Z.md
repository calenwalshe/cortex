## Summary

Cortex already has most of the building blocks for a memory architecture — `facts.jsonl`, `cortex-embed.py`, `cortex-retrieve.py`, the session-start hook, the system map, and PostCompact extraction. The "memory architecture" is less about building new infrastructure and more about **connecting what exists with a coherent schema, a tiered retrieval strategy, and a structured iteration model for the intelligence loop.** The winning pattern across the industry is file-based memory with LLM-managed organization — plain text files with YAML frontmatter, organized by semantic directory structure, with the LLM acting as the indexing and retrieval engine. The key design tension is between the 150-instruction LLM ceiling (demanding extreme selectivity) and the desire to accumulate everything (demanding comprehensive storage). The resolution: store broadly in tiered files, retrieve selectively via the existing embedding pipeline, inject minimally via the hook pointer pattern.

## Findings

- **Plain text file-based memory has won the adoption war.** AGENTS.md is used by 60K+ projects across Claude Code, Cursor, GitHub Copilot, standardized under the Linux Foundation. Claude Code's auto-memory writes to hierarchical `CLAUDE.md` files, extracting learnings after ~10K tokens and updating every ~5K tokens thereafter. Letta's filesystem approach scored 74% on LoCoMo, beating Mem0's 68.5% graph variant. The consensus: "Whenever you find yourself giving the same instruction twice, add it to AGENTS.md instead." Source: voxos.ai (Forget RAG article, Feb 2026); mindstudio.ai (Claude Code auto-memory).

- **MemGPT/Letta defines the canonical tiered memory hierarchy.** Four tiers: (1) Message Buffer — recent conversation (working memory), (2) Core Memory — editable blocks pinned to context (the agent can rewrite these), (3) Recall Memory — searchable full conversation history, (4) Archival Memory — explicitly stored knowledge in external stores. The OS analogy: context window = RAM, persistent storage = disk. Key insight: "designing agent memory is essentially context engineering — determining which tokens enter the context window and how they're organized." Source: letta.com/blog/agent-memory (Apr 2026).

- **A 4-layer file-based architecture maps MemGPT tiers to plain files.** agents/ (metadata), conversations/ (raw transcripts), knowledge/ (extracted facts), graph/ (relationships). Each file uses JSON with timestamps, tags, and structured fields. The knowledge layer explicitly separates raw data from extracted facts — paralleling the "diary pattern" identified in the MemPalace fit report. Source: dev.to/oblivionlabz (4-Layer File-Based Architecture, Feb 2026).

- **LLMs follow ~150 instructions reliably; Claude Code's system prompt uses ~50.** This leaves ~100 slots for project-specific memory. A focused 30-item memory file consistently outperforms a 300-item one. Context rot is measurable: Claude Sonnet 4 drops from 99% to 50% accuracy as input length grows. The "lost in the middle" effect causes 15-30% performance drops for mid-positioned content. Implication: memory injection MUST be selective, not comprehensive. Source: voxos.ai; humanlayer.dev (CLAUDE.md research).

- **CodeMem introduces the "memory → reasoning → action" loop with supersession.** Memories are anchored to specific files and architectural layers. Decisions can supersede older ones when architecture changes, preventing outdated information from polluting reasoning. "Fragmented memories can be consolidated into canonical facts, helping the memory system improve over time rather than degrade." This directly addresses the clarify brief's concern about cross-slug accumulation. Source: linkedin.com/zhangshisimon (CodeMem, Genesis Competition).

- **xMemory cuts token costs by organizing conversations into semantic theme hierarchies.** Drops token usage from 9000 to ~4700 per query by creating searchable hierarchies instead of flat retrieval. The "write tax" (overhead of organizing memories) is worth it for the retrieval savings. Relevant to Cortex because the PostCompact extraction is already a "write" moment — organizing during extraction costs little extra. Source: venturebeat.com (xMemory, 2026).

- **Memory poisoning achieves >95% injection success and persists across sessions.** MINJA research shows poisoned memories survive session restarts. "The feature that makes agents useful (learning and remembering) is the attack surface." Detection systems miss 2/3 of poisoned entries because malicious content looks benign in isolation. OWASP ASI06 recognizes this as a top agentic risk for 2026. Defense requires layered controls — not just session isolation. Source: christian-schneider.net (memory poisoning blog); voxos.ai (security section).

- **Adaptive budgeted forgetting framework provides the retention/decay model.** arxiv 2604.02280v1 proposes combining temporal decay + usage frequency + semantic alignment to guide deletion decisions. Memory retention is formulated as optimization under fixed budget limits. Key insight: "structured forgetting with budget-aware optimization maintains stability while reducing unnecessary memory growth." This addresses the clarify brief's open question about retention/decay. Source: arxiv 2604.02280v1.

- **Reflection agents couple memory with iterative reasoning loops.** Hierarchical reflection operates at multiple temporal scales: individual action, short-term trajectory, and global task outcome. Memory-augmented agents store episodic memory for tracking recurrent errors and retrieval-augmented planning. Critical warning: "too much unchecked episodic memory accumulation may distract or destabilize the agent." Source: emergentmind.com (Reflection Agent topic).

- **Cortex already has most of the building blocks.** `facts.jsonl` = knowledge layer. `cortex-embed.py` + `cortex-retrieve.py` = retrieval pipeline. Session-start hook = injection mechanism. `system-map.md` = structural context. PostCompact hook = extraction trigger. Auto memory (`~/.claude/projects/*/memory/`) = existing file-based memory with typed frontmatter. The gap is not infrastructure — it's a coherent schema connecting these pieces and a structured iteration model for the intelligence loop. Source: codebase analysis.

## Trade-offs

### Option: Extend the existing auto memory system (~/.claude/projects/*/memory/)
**Pros:** Already file-based, already has typed frontmatter (user, feedback, project, reference), already loaded by Claude Code natively, already survives /clear and sessions. Zero new infrastructure.
**Cons:** Cortex doesn't control it — Claude Code's harness manages loading. No programmatic retrieval (no embedding-based search). Memory types are generic (user, feedback, project, reference) — doesn't capture reasoning chains, failed approaches, or cross-slug patterns. Can't enforce the 150-instruction ceiling.
**Verdict:** Use as one tier (the "core memory" / always-loaded tier) but don't rely on it as the full architecture. Add Cortex-specific memory types to the existing schema.

### Option: Evolve facts.jsonl into the full memory store
**Pros:** Already exists, already has embedding support via cortex-embed.py, already retrieved by cortex-retrieve.py, already extracted during PostCompact. JSONL is append-friendly and grep-searchable.
**Cons:** Schema is too flat — all facts have the same weight and structure. No tiering (recent vs archival). No supersession mechanism. No reasoning chain support. PostCompact extraction is lossy — discards the "why" behind decisions.
**Verdict:** Keep as the knowledge/archival tier but add richer schema fields: provenance, superseded_by, reasoning_chain_ref, usage_count, last_accessed.

### Option: Build a new tiered memory system from scratch
**Pros:** Clean design matching MemGPT tiers. Can optimize for Cortex's specific needs. No legacy constraints.
**Cons:** Most infrastructure already exists �� building from scratch wastes what's there. Higher implementation cost. Risk of creating a parallel system that competes with existing mechanisms.
**Verdict:** rejected — connect and extend what exists rather than building parallel infrastructure.

### Option: Connect existing systems with a coherent schema + iteration model
**Pros:** Minimal new code. Leverages proven infrastructure (facts.jsonl, embeddings, hooks, auto memory). Adds the missing pieces: schema enrichment, tiered retrieval, iteration exit criteria, cross-slug accumulation.
**Cons:** Evolutionary approach means some existing rough edges persist. May need refactoring if the connected system reveals deeper design issues.
**Verdict:** selected — this is the right approach. Connect, enrich, and formalize what exists.

## Recommendations

- **Define a 3-tier memory hierarchy mapped to existing Cortex systems:**
  - **Tier 1 (Core/Always-loaded):** Auto memory files (`~/.claude/projects/*/memory/`) + system map (`docs/cortex/system-map.md`) + session-start hook pointer. Loaded every session. Budget: ~100 instructions / ~2K tokens. The "RAM" tier.
  - **Tier 2 (Active/Retrieved):** Enriched `facts.jsonl` with semantic retrieval via `cortex-retrieve.py`. Retrieved selectively per-slug and per-query. Injected via hook or skill reads. The "SSD" tier.
  - **Tier 3 (Archival/Cold):** Full artifact archive (`docs/cortex/archive/`), research dossiers, clarify briefs, specs. Read on-demand by skills, never injected into hook context. The "disk" tier.

- **Enrich the facts.jsonl schema** to support memory architecture needs:
  - Add fields: `superseded_by` (null or fact ID), `reasoning_chain` (array of prior fact IDs that led to this conclusion), `usage_count` (incremented on retrieval), `last_accessed` (timestamp), `confidence` (high/medium/low), `slug_scope` (array — which slugs this fact applies to, or `["*"]` for universal).
  - Add memory types beyond current: `reasoning_chain`, `failed_approach`, `cross_slug_pattern`, `architectural_hypothesis`.

- **Add new auto memory types for Cortex intelligence context.** Extend the existing `~/.claude/projects/*/memory/` schema with types specifically for the intelligence loop: `intelligence` type for cross-slug patterns, `loop_state` type for tracking clarify ↔ research iteration state.

- **Define clarify ↔ research iteration exit criteria.** The loop should iterate when: (1) research findings invalidate clarify assumptions (reclarify_required), (2) open questions remain unanswered after research, (3) confidence on core assumptions is below threshold. The loop should exit to spec when: all critical open questions are resolved OR explicitly accepted-risk, no reclarify_required flag, and research coverage score exceeds a threshold.

- **Use PostCompact as the primary memory write trigger.** The compaction boundary is when context is about to be lost — the natural moment to extract and persist what matters. Enhance `cortex-postcompact.js` to extract richer memory types (reasoning chains, failed approaches, cross-slug patterns) alongside current fact extraction.

- **Implement a forgetting budget.** Cap total facts.jsonl at a configurable size (e.g., 500 entries). When the cap is hit, apply the adaptive forgetting formula: score = temporal_recency × usage_frequency × semantic_relevance. Prune the lowest-scoring entries. Mark superseded facts for pruning priority.

- **Add memory poisoning defenses.** Since Cortex memories are file-based and LLM-written: (1) validate memory writes against the active contract's scope — memories that reference paths outside write roots are suspicious, (2) add a `source` field to every memory (which skill/hook wrote it), (3) consider a lightweight review step for auto-extracted memories during PostCompact.

## Adjacent Findings

- **Memory poisoning is a first-order security risk for persistent agent memory.** MINJA research demonstrates >95% injection success rates against production agents, with poisoned memories surviving session restarts. "The feature that makes agents useful (learning and remembering) is the attack surface." Since Cortex's PostCompact hook auto-extracts facts from conversation context, a prompt injection during a session could plant a poisoned fact that persists indefinitely. The file-based approach doesn't help — poisoned markdown looks identical to legitimate markdown. This means memory writes need validation gates, not just extraction. Source: christian-schneider.net; OWASP ASI06 (2026).

- **The "forgetting problem" is the hardest unsolved challenge in agent memory.** No production system reliably decides when to delete old knowledge. Without automated pruning, memory stores accumulate outdated and contradictory information. The novel forgetting framework (arxiv 2604.02280v1) proposes temporal decay + usage frequency + semantic alignment, but it requires metadata that Cortex's current facts.jsonl doesn't track (usage counts, access timestamps). Adding these fields to the schema is a prerequisite for any forgetting strategy — without them, pruning is arbitrary. Source: arxiv 2604.02280v1; voxos.ai.

- **Claude Code already extracts memory at ~10K tokens and updates every ~5K tokens.** The auto-memory system applies implicit criteria: recurrence, non-obviousness, stability, and project specificity. This is essentially a forgetting-by-selection model — it only writes what passes these filters. Cortex's PostCompact extraction could adopt similar criteria rather than extracting everything, reducing noise at the write boundary rather than pruning after the fact. Source: mindstudio.ai (Claude Code auto-memory); rajiv.com (how Claude memory works).

## Open Questions

- How should the enriched facts.jsonl schema handle backward compatibility with the 53 existing facts? Migration strategy needed.
- Should reasoning chains be stored as linked fact sequences (IDs referencing other IDs) or as self-contained narrative blocks? Linked chains are more structured but harder to retrieve; narratives are noisier but self-contained.
- What's the right forgetting budget size? 500 entries was proposed but needs empirical calibration — how many facts does a typical 10-slug project produce?
- How should memory poisoning defenses interact with the autonomy system? Should there be a `memory_write_review` gate?
- The auto memory system at `~/.claude/projects/*/memory/` is managed by Claude Code's harness, not Cortex. Can Cortex add custom memory types there, or does it need a separate store?
- What specific exit criteria should trigger the transition from clarify ↔ research loop to spec? Need to define the "research coverage score" concretely.
