## Summary

A persistent system decomposition map should be a **layered Markdown document with embedded Mermaid diagrams and a YAML component registry**, targeting under 5K tokens for full context injection. The format should split cleanly into two tiers: code-derivable structure (regenerate cheaply) and human-asserted intent (persist durably). The closest existing Cortex artifact is `project-context.md` — currently per-slug, overwritten each spec run, and **never loaded by the session-start hook** (confirmed dead artifact). The map replaces it as a system-wide, cumulative, session-injected context source. A lightweight freshness envelope in frontmatter is essential: research shows LLMs consume stale context with full confidence, and 20-25% of architectural decisions go stale within two months.

## Findings

- **Markdown + Mermaid is the optimal format for LLM consumption.** A simple 3-node diagram uses 55 tokens in ASCII vs ~10 tokens in Mermaid (5.5x reduction). LLMs are "trained to understand mermaid format quite extensively" due to massive GitHub corpus exposure. Mermaid also version-controls cleanly — diffs show structural changes, not "image.png modified." Source: dev.to/darkmavis1980, Feb 2026.

- **YAML outperforms JSON and XML for nested data accuracy; Markdown is most token-efficient.** Benchmarks across GPT-5 Nano, Llama 3.2 3B, and Gemini 2.5 Flash Lite on 1,000 questions over nested data: YAML achieved 62.1% accuracy (GPT-5 Nano) vs JSON 50.3% vs XML 44.4%. Markdown used 34-38% fewer tokens than JSON across all models. XML should be avoided — worst on both accuracy and token cost. Source: improvingagents.com, Oct 2025.

- **C4's three-level zoom (Context → Container → Component) is the right granularity.** C4 abstracts systems into four hierarchical levels. An arXiv paper (2510.22787, Oct 2025) demonstrates multi-agent LLMs can auto-generate C4 models from system briefs using YAML+PlantUML output, with hybrid evaluation (deterministic structural checks + LLM-as-Judge semantic scoring). Level 4 (code) should not be pre-computed — that's what the LLM reads directly. The map helps the LLM decide *which* code to read. Source: c4model.com; arxiv 2510.22787.

- **`project-context.md` is a dead artifact.** It exists in at least 4 slug directories (`kalshi-adaptive-loop`, `readme-upgrade`, `semantic-retrieval`, `llm-judge-calibration`) and encodes tech stack, conventions, architecture rules, and write boundaries. But it is **never loaded** by `cortex-session-start.sh` — the hook only loads `current-state.md` and `facts.jsonl`. It is also per-slug and overwritten each `/cortex-spec` run. Source: direct codebase analysis of `cortex-session-start.sh` lines 13-41 and `cortex-spec` SKILL.md Phase 2b.

- **Three Cortex commands are the highest-value integration points.** `/cortex-spec` Phase 2 reconstructs interface maps from scratch per slug — scattered across prior spec artifacts. `/cortex-review` architecture lens asks "does this fit existing patterns?" with no reference artifact to check against. `/cortex-research` Outside-In query reformulation would produce better angle queries with actual system structure. Source: direct reads of cortex-spec, cortex-review, cortex-research SKILL.md files.

- **Cross-slug dependency and interface information is completely lost today.** No artifact records cumulative component dependencies across slugs. Interface contracts defined in specs go cold after archive to `docs/cortex/archive/`. The decomposition map is the only artifact positioned to capture cumulative structural evolution. Source: codebase analysis of docs/cortex/specs/ and archive structure.

- **Aider repo-map: the right model for code-derivable facts.** Uses tree-sitter to parse source into ASTs, extracts class names/function signatures/import relationships, builds a dependency graph, and applies graph ranking to select the most-referenced symbols. Default budget: 1K tokens (`--map-tokens`). Dynamically regenerated per session — zero staleness risk but no architectural semantics. Source: aider.chat/docs/repomap.html.

- **20-25% of architectural decisions go stale within two months.** A retrospective audit of 62 architectural decisions across two projects found average evidence validity of ~53 days. 86% of staleness was discovered reactively (during incidents), 14% remained dormant. The FPF paper proposes `valid_until` timestamps with a decay model where expired evidence drops to 0.1 confidence — "stale" means low-confidence, not garbage. Source: arxiv 2601.21116v1, Jan 2026.

- **Prefix caching makes stable documents dramatically cheaper to inject.** Anthropic cached tokens on Sonnet 4.6 cost $0.30/M vs $3.00/M (90% off). Thomson Reuters documented 60% cost reduction on legal document summarization by caching boilerplate context. Key requirement: place static content first, before dynamic content — any change to early tokens invalidates the cache. A stable, rarely-changing system map is an ideal prefix caching candidate. Source: tianpan.co, morphllm.com.

## Trade-offs

### Option: Monolithic Markdown Document
**Pros:** Single artifact, simple to maintain, full injection under 5K tokens, benefits from prefix caching, easy to read/edit.
**Cons:** Cannot selectively inject sections for different consumers. Risks bloating past 5K tokens as system grows. Gemini cross-reference flagged: "Is 5K tokens truly enough for a meaningful C4 model of a non-trivial system?"
**Verdict:** selected — for systems of Cortex's scale (single user, single AI, file-based), 5K is sufficient for Levels 1-2 plus crosscutting conventions. Level 3 (component interfaces) can be loaded on-demand by specific commands. Add sectioned retrieval only if token budget is exceeded.

### Option: YAML Component Graph
**Pros:** Machine-parseable, good for dependency resolution, explicit relationship typing. YAML achieves highest accuracy on nested data benchmarks.
**Cons:** Less human-readable for narrative context (intent, rationale, conventions). Splits the format between structure (YAML) and narrative (markdown).
**Verdict:** rejected as primary format — use YAML frontmatter for metadata, but the body should be Markdown + Mermaid. YAML tables within markdown sections are fine for component registries.

### Option: Auto-Generated from Code (aider repo-map style)
**Pros:** Zero maintenance burden, always fresh, no staleness risk.
**Cons:** Cannot capture intent, rationale, conventions, or architectural decisions — only structural facts derivable from ASTs. Misses the entire value proposition of the map. Gemini cross-reference: "How do LLMs bridge the gap between structural (AST) and semantic (intent) understanding?"
**Verdict:** rejected as the full solution — but the principle of regenerating code-derivable facts is correct. The map should distinguish between "derived" sections (refreshable) and "asserted" sections (human-maintained).

### Option: Separate Artifact per C4 Level
**Pros:** Granular injection — load only the level needed per command.
**Cons:** Three files to maintain instead of one. Increases coordination burden.
**Verdict:** deferred — start monolithic, split only if the artifact exceeds 5K tokens.

## Recommendations

- **Use a single Markdown file at `docs/cortex/system-map.md`** with Mermaid diagrams for C4 Levels 1-2, a component registry table, crosscutting conventions, and key decisions. Target: under 3K tokens for core content, hard ceiling at 5K.
- **Include a freshness envelope in frontmatter:** `last_verified`, `valid_until` (default 60-90 days based on FPF decay rates), `confidence` (high/medium/low), `advisory: true`. The LLM reads this and calibrates trust. Nothing blocks on expiry.
- **Inject via `cortex-session-start.sh`** alongside `current-state.md`. Place it before dynamic content to benefit from prefix caching. If the file doesn't exist, the hook proceeds silently.
- **Also inject into three commands:** `/cortex-spec` (Phase 2, interface synthesis), `/cortex-review` (architecture lens), `/cortex-research` (Outside-In query context). Full-document injection (under 5K threshold). Commands that don't find the map proceed normally.
- **Split content into "derived" and "asserted" sections.** Derived sections (module inventory, dependency edges) can be regenerated by an LLM reading the codebase. Asserted sections (component responsibilities, crosscutting conventions, key decisions, architectural intent) are human-maintained. Mark each section with provenance.
- **Generate the initial map via LLM-assisted discovery:** The LLM reads the codebase and proposes a decomposition, the user confirms/edits. Low friction to create, human validated for accuracy.
- **Replace `project-context.md` with the system map.** The new system-wide map supersedes the per-slug `project-context.md` pattern. `/cortex-spec` reads the map instead of generating a fresh project-context each time. Eliminates the dead-artifact problem.

## Adjacent Findings

- **Prefix caching economics favor stable injection:** Anthropic cached tokens cost 90% less ($0.30/M vs $3.00/M on Sonnet 4.6). A stable system map injected at session start is an ideal caching candidate — the token cost of carrying it in every session is negligible after the first call. This makes the "always inject vs. on-demand" question easy: always inject if under 5K tokens. Source: morphllm.com, tianpan.co.

- **Architectural decisions go stale at 20-25% within two months:** An empirical audit of 62 decisions found average evidence validity of ~53 days, with 86% of staleness discovered reactively during incidents. This calibrates the `valid_until` window at 60-90 days and confirms the freshness signal is grounded in measured decay rates, not paranoia. Source: arxiv 2601.21116v1 (Gilda & Gilda, Jan 2026).

- **Stale context produces confident wrongness, not uncertainty:** The FPF paper's core finding is that LLMs lack "institutional memory to flag dormant assumptions" — an LLM "cannot know that a caching decision from six months ago rested on traffic assumptions that have since doubled." This directly challenges the premise that a stale map "can only be helpful." A stale map consumed at full confidence can produce actively wrong specs. The freshness envelope is a safety mechanism, not polish. Source: arxiv 2601.21116v1 Section 4.1.

## Open Questions

- How should the map be loaded at session start — appended to the session-start hook alongside `current-state.md`, or read on-demand by individual commands? (Recommendation above favors hook injection given prefix caching economics, but needs validation.)
- What is the relationship between the system map and CLAUDE.md? Both serve as persistent project context. Should the map be a section of CLAUDE.md, a file referenced from CLAUDE.md, or fully independent?
- How should the map interact with the memory system (`~/.claude/projects/*/memory/`)? Memory stores cross-session learnings; the map stores system structure. Should one reference the other?
- What is the minimal viable schema for the component registry table? (name, responsibility, tech, interfaces, dependencies — Gemini cross-reference asks: which are load-bearing for LLM reasoning vs. nice-to-have?)
- Should there be a `/cortex-map` command to generate/refresh the decomposition, or should it be a manual artifact?
- How should the map handle the "system brief" problem — if the brief that generated the map is itself stale, the derived C4 model inherits that staleness? (Flagged by Gemini cross-reference.)
