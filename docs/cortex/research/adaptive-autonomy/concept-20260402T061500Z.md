# Research Dossier: adaptive-autonomy — concept

**Slug:** adaptive-autonomy
**Phase:** concept
**Timestamp:** 20260402T061500Z
**Depth:** standard

---

## Summary

The Cortex→GSD pipeline has 18 combined HITL gates. Of these, 6 are rubber-stamps (automatable today), 5 are genuine decision points (must remain gated), and 7 are conditionally automatable (skip when upstream context exists, gate when it doesn't). The discuss-phase is the single largest source of redundancy — it re-asks questions Cortex already answered. A shared autonomy config with three presets (full-auto, gates-only, supervised) plus per-gate overrides can eliminate the redundancy while preserving safety-critical gates. The Cortex-to-GSD bridge is ~75% automatable; the remaining 25% is "vision framing" that discuss-phase captures but Cortex clarify doesn't.

## Findings

### Cortex HITL Gates (12 total)

- **cortex-clarify** has 2 gates: slug conflict confirmation (rubber-stamp) and sparse-idea questioning (genuine — but only fires on underspecified input)
- **cortex-research** has 1 gate: eval proposal approval (rubber-stamp — rarely rejected; auto-approvable for low-risk dimensions)
- **cortex-spec** has 3 gates: reclarify check (genuine — fires on evidence conflict), critical uncertainties (genuine — blocks on unresolved questions), contract approval (rubber-stamp — specs rarely rejected outright)
- **cortex-review** has 4 gates: contract compliance verdict (genuine), eval plan validation (automatable — file existence check), eval failure triage (genuine), active contract load (conditional)
- **cortex-audit** has 1 gate: security posture verdict (genuine for threat context, automatable for CVE patterns)
- The hardcoded UX/taste eval gate (`approval_required: true`) is a Phase 05 design decision that must survive all autonomy levels

### GSD HITL Gates (6 primary)

- **discuss-phase** asks 5 sequential AskUserQuestion prompts — this is the biggest redundancy when Cortex artifacts exist
- **plan-phase** has NO documented human gate — plans proceed immediately to execution
- **execute-phase** has 3 checkpoint types: human-verify (conditional), human-action (unfixable — external dependency), decision (conditional on pre-locked choices)
- **verify-work (UAT)** is semi-genuine — rubber-stamp when everything passes, genuine when issues found
- **transition** is automatic after verification passes
- **/gsd:drive already skips discuss-phase** — auto-generates CONTEXT.md with "Claude's Discretion" but does NOT consume Cortex artifacts

### Cortex→GSD Artifact Overlap

- **100% coverage**: requirement IDs, out-of-scope rationale, done criteria → success criteria, contract phase → GSD start point, approval status
- **85% coverage**: requirements (need re-categorization), deliverables → task list
- **70% coverage**: clarify brief → CONTEXT.md (technical frame exists, vision framing missing)
- **50% coverage**: architecture decisions → key decisions (strategic trade-offs missing), dependencies
- **0% coverage**: requirement category taxonomy, traceability matrix, multi-phase roadmap sequencing (when work spans >1 phase)

### Existing Automation Machinery

- `/gsd:drive` already chains discuss→plan→execute→verify→advance with minimal stops
- `/gsd:autonomous` runs all remaining phases without intervention
- `/gsd:quick` and `/gsd:fast` skip optional agents for small tasks
- These prove the chaining machinery works — the missing piece is Cortex artifact consumption

## Trade-offs

### Option: Single autonomy config file (shared by Cortex + GSD)

**Pros:** One place to set behavior. Both systems read it. Simple mental model.
**Cons:** Couples two systems that were designed to be independent. Config schema must satisfy both systems' gate models.
**Verdict:** selected — the coupling is intentional (that's the whole point of this slug)

### Option: Per-invocation flags only (e.g., `--auto`, `--supervised`)

**Pros:** No config file to manage. Explicit per-run.
**Cons:** Can't set project-wide defaults. User must remember to pass flags every time.
**Verdict:** rejected as sole mechanism — include as override on top of config

### Option: Autonomy presets only (no per-gate overrides)

**Pros:** Dead simple. Three modes, pick one.
**Cons:** Can't express "full-auto except contract approval" — a common real-world need (e.g., high-risk slug).
**Verdict:** rejected — presets are the primary interface but per-gate overrides are necessary

### Option: Bridge command that calls GSD skills programmatically

**Pros:** Uses existing GSD skill machinery. Guaranteed format compatibility.
**Cons:** Fragile — skills are designed for human invocation, not programmatic chaining. Error handling between skills is ad-hoc.
**Verdict:** rejected — bridge should generate artifacts directly (PROJECT.md, ROADMAP.md, REQUIREMENTS.md) rather than calling skills

### Option: Bridge command that generates GSD artifacts directly from Cortex outputs

**Pros:** Fast, deterministic, no intermediate skill invocation. Can validate output before writing.
**Cons:** Must stay in sync with GSD's artifact format expectations.
**Verdict:** selected — direct artifact generation with format validation

### Option: Keep discuss-phase but pre-populate from Cortex

**Pros:** Human still gets to review and adjust vision framing.
**Cons:** Still blocks on human input even when context is sufficient.
**Verdict:** deferred — make it conditional on autonomy level. In gates-only/full-auto, skip. In supervised, pre-populate but still ask.

## Recommendations

- Implement three autonomy presets: `full-auto`, `gates-only`, `supervised` — defaulting to `supervised` (backward-compatible)
- Config lives at `.cortex/autonomy.json` (project-level) with fallback to `~/.claude/cortex-autonomy.json` (global), overridable per-invocation with `--autonomy <level>`
- Per-gate overrides in config for common needs: `"gates": { "contract_approval": true }` forces a gate regardless of preset
- Mandatory gates that survive ALL autonomy levels: UX/taste eval approval, human-action checkpoints, reclarify gate (when research contradicts assumptions)
- Build `/cortex-bridge` (or `/cortex-import`) command that reads gsd-handoff.md + spec + contract and generates PROJECT.md, ROADMAP.md, REQUIREMENTS.md, and phase CONTEXT.md directly — no intermediate GSD skill invocation
- Make discuss-phase conditional: skip entirely when Cortex artifacts exist AND autonomy is full-auto or gates-only; pre-populate and ask when supervised
- When full-auto hits genuine ambiguity (architectural decision checkpoint), log the choice made and rationale to a decisions log rather than escalating — but flag it in verification output so human can review post-hoc
- Add `--dry-run` flag that prints the gate sequence and which gates would fire/skip at the current autonomy level without executing

## Open Questions

- Should the bridge command handle multi-phase roadmaps (splitting a single Cortex spec into multiple GSD phases) or is that always a human decision?
- What's the right granularity for per-gate overrides — individual gate names or gate categories (approval, validation, checkpoint)?
- Should autonomy level be logged in commit messages or STATE.md so post-hoc review knows which mode was used?
- How does autonomy interact with `/gsd:drive` — does drive respect the autonomy config or does it have its own separate skip logic?
- Should there be an autonomy "budget" concept — e.g., full-auto for 3 phases then force supervised review?
