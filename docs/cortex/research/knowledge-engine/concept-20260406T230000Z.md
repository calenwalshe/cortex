## Summary

This dossier designs the fact extraction pipeline and procedural/lesson memory layer (E4) for the Cortex knowledge engine. It extends the prior memory-extraction research (6 fact types) with 3 new types — procedure, lesson, observation — and maps the complete data flow from compaction event through embedding to retrieval.

The extraction pipeline runs in two stages: the precompact hook (bash, sync) captures enriched snapshots from Cortex artifacts, and the postcompact hook (Node.js, sync) decomposes those snapshots into atomic facts appended to `.cortex/facts.jsonl`. A separate async script (`cortex-embed.py`) then embeds new facts for semantic retrieval.

Key design decisions: extraction stays pattern-based (no LLM calls in hooks), procedures and lessons are extracted from repair contract `Failed Approaches` sections and investigation artifacts, and retrieval surfaces relevant lessons when cortex-research or cortex-clarify encounters a similar problem domain.

## 1. Fact Extraction Pipeline

### 1.1 What Triggers Extraction

**Primary trigger:** The PostCompact hook (`cortex-postcompact.js`), which fires synchronously after every Claude Code context compaction.

**Secondary trigger:** None needed for v1. The postcompact hook is the single extraction point. Rationale: compaction events are the natural boundary where session intelligence must be preserved. Between compactions, facts live in the active context window (E1 working memory) and don't need extraction.

**Future consideration:** A `/cortex-remember` command for explicit fact capture outside compaction could be added later (noted as open question in the clarify brief). This would append directly to facts.jsonl without going through the compaction pipeline.

### 1.2 What Sources Does It Read

The extraction pipeline reads from disk only — hooks receive no stdin data.

| Source | What It Contains | Fact Types Extracted | Reader |
|--------|-----------------|---------------------|--------|
| `docs/cortex/handoffs/decisions.md` | Decision log, autonomy gate decisions, archive index | decision | postcompact.js |
| `docs/cortex/handoffs/current-state.md` | Slug, mode, artifacts, blockers | context_pointer, blocker | postcompact.js |
| `.planning/STATE.md` | GSD progress, accumulated context, decisions, blockers | decision, blocker, pattern | postcompact.js |
| `.planning/phases/*/CONTEXT.md` | Implementation decisions, deferred ideas, specifics | preference, constraint, decision | postcompact.js |
| `git log --oneline -20` | Recent commit messages | context_pointer | postcompact.js |
| `.cortex/state.json` | Pipeline state, artifacts array | context_pointer | postcompact.js |
| `docs/cortex/contracts/*/contract-*.md` | Failed Approaches, Why Previous Failed, Rollback Hints | lesson, procedure | postcompact.js (NEW) |
| `docs/cortex/investigations/*/*.md` | Root cause, findings, repair recommendations | lesson, observation | postcompact.js (NEW) |
| `docs/cortex/research/*/concept-*.md` | Research findings, alternatives considered | observation, procedure | postcompact.js (NEW) |

The precompact hook (`cortex-precompact.sh`) captures all of the above into a single enriched snapshot at `.cortex/compaction/precompact-{timestamp}.md`. The postcompact hook then reads both the snapshot and the original sources for extraction.

### 1.4 Extraction Method

All extraction is pattern-based (regex on markdown structure). No LLM calls.

#### Source: `decisions.md`
- **Section:** `## Decision Log` — each `^- ` line becomes a `decision` fact
- **Section:** `## Autonomy Decisions` — each `^- \d` line becomes a `decision` fact (prefixed "Autonomy:")
- **Already implemented** in current postcompact.js

#### Source: `.planning/STATE.md`
- **Section:** `### Decisions` — each non-empty line becomes a `decision` fact
- **Section:** `### Blockers/Concerns` — each non-empty line becomes a `blocker` fact
- **Already implemented** in current postcompact.js

#### Source: `.planning/phases/*/CONTEXT.md`
- **Tag:** `<decisions>...</decisions>` — each `^- ` line becomes a `preference` fact
- **Tag:** `<specifics>...</specifics>` — each `^- ` line becomes a `constraint` fact
- **Already implemented** in current postcompact.js

#### Source: `git log`
- Last 10 commits become `context_pointer` facts (prefixed "Recent commit:")
- **Already implemented** in current postcompact.js

#### Source: `.cortex/state.json`
- `artifacts[]` array entries become `context_pointer` facts (prefixed "Artifact:")
- **Already implemented** in current postcompact.js

#### Source: Contract `Failed Approaches` sections (NEW)
- **Pattern:** `## Failed Approaches` → scan for `### Attempt N` subsections
- **Extract from each attempt:**
  - `**Approach:**` line → becomes part of `lesson` text
  - `**Result:**` line → becomes part of `lesson` text
  - `**Root cause:**` line → becomes part of `lesson` text
- **Composite fact text:** "On {slug} (contract-{N}): tried '{approach}' — failed because '{root_cause}'"
- **Type:** `lesson`
- **Source:** path to the contract file

```
Extraction regex:
  /### Attempt (\d+).*?\n\*\*Approach:\*\* (.*?)\n\*\*Result:\*\* (.*?)\n\*\*Root cause:\*\* (.*?)(?=\n###|\n---|\Z)/gs
```

#### Source: Contract `Why Previous Approach Failed` section (NEW)
- **Pattern:** `## Why Previous Approach Failed` → text until next `## ` heading
- **Skip if:** text is "N/A" or "initial contract"
- **Type:** `lesson`
- **Fact text:** "On {slug}: previous approach failed because '{extracted text}'"

#### Source: Investigation artifacts (NEW)
- **Path:** `docs/cortex/investigations/{slug}/*-investigation.md`
- **Section:** `root cause` → each paragraph becomes an `observation` fact
- **Section:** `repair recommendations` → each `^- ` line becomes a `procedure` fact
- **Section:** `findings` → each `^- ` line with actionable content becomes an `observation` fact

```
Extraction regex for root cause:
  /## [Rr]oot [Cc]ause\n+([\s\S]*?)(?=\n## )/
```

#### Source: Research dossier `Alternatives Considered` / `Recommendations` (NEW)
- **Path:** `docs/cortex/research/{slug}/concept-*.md`
- **Section:** `Alternatives Considered` → each rejected alternative becomes an `observation` fact
- **Section:** `Recommendations` → each `^\d+\.` line becomes a `procedure` fact
- **Limited to:** most recent research dossier per slug (avoid re-extracting archived research)

```
Extraction regex for alternatives:
  /### Alternatives Considered\n([\s\S]*?)(?=\n---|\n## )/
  Then per entry: /\*\*([^*]+)\*\*.*?Rejected.*?—\s*(.*?)(?=\n-|\Z)/gs
```

### 1.5 Deduplication

**Method:** Content hash — first 8 characters of MD5 of `text.trim()`.

**Implementation:** Already in `cortex-postcompact.js` at line 37:
```js
function contentHash(text) {
  return crypto.createHash('md5').update(text.trim()).digest('hex').slice(0, 8);
}
```

**Dedup flow:**
1. Load existing `facts.jsonl`, extract hash from each fact's `id` field (last 8 chars after final `-`)
2. Build `Set<string>` of existing hashes
3. For each new fact, compute `contentHash(fact.text)`
4. Skip if hash already in set
5. Append only new facts

**Edge case — near-duplicate text:** Two facts with semantically identical content but different wording will have different hashes. This is acceptable for v1. Semantic dedup (embedding-based) is a future optimization.

**Collision probability:** MD5 truncated to 8 hex chars = 32 bits = 4.3 billion values. At 1000 facts, birthday paradox probability is ~0.01%. Acceptable.

## 2. Procedural/Lesson Memory (E4)

### 2.1 What Is a Procedure

A **procedure** is a reusable tactic: a conditional action rule of the form "when you see X, do Y." Procedures are extracted from successful outcomes and expert recommendations — they encode *what works*.

**Characteristics:**
- Actionable: contains a trigger condition and an action
- Reusable: applies beyond the slug where it was discovered
- Positive: describes what to do (not what failed)

**Schema:**
```json
{
  "id": "fact-20260406T230000Z-a1b2c3d4",
  "type": "procedure",
  "slug": "pattern-harvest",
  "text": "When a repair contract exceeds 3 cycles with >80% similar failure signatures, declare CONVERGENCE STALL and escalate to human instead of continuing the loop",
  "source": "docs/cortex/research/pattern-harvest/concept-20260403T213444Z.md",
  "extracted_at": "20260406T230000Z",
  "session_context": "pattern-harvest execute phase",
  "trigger": "repair convergence stall",
  "confidence": "high"
}
```

**Note on `trigger` and `confidence`:** These are optional extension fields for E4 types. They are not required by the current schema but are included in the design for future retrieval optimization. The `trigger` field is a short phrase describing when this procedure applies — useful for keyword-based pre-filtering before semantic search. The `confidence` field indicates extraction quality: `high` for explicit recommendations, `medium` for inferred patterns, `low` for single-instance observations.

### 2.2 What Is a Lesson

A **lesson** is a learned failure: a record of an approach that was tried and why it didn't work. Lessons are extracted from repair contracts, investigation root causes, and spec alternatives. They encode *what doesn't work and why*.

**Characteristics:**
- Negative: describes what failed (not what to do instead)
- Causal: includes the reason for failure, not just the outcome
- Contextual: tied to a specific slug and situation for relevance matching

**Schema:**
```json
{
  "id": "fact-20260406T230000Z-e5f6g7h8",
  "type": "lesson",
  "slug": "semantic-retrieval",
  "text": "sentence-transformers for batch embedding rejected on semantic-retrieval: 13s model load per subprocess invocation exceeds the 5s hook budget. Dimension mismatch (384 vs 768) also prevents mixing with ollama query embeddings.",
  "source": "docs/cortex/specs/semantic-retrieval/spec.md",
  "extracted_at": "20260406T230000Z",
  "session_context": "semantic-retrieval spec phase",
  "failure_mode": "performance",
  "confidence": "high"
}
```

**Note on `failure_mode`:** Optional extension field categorizing the failure type. Values: `performance`, `correctness`, `compatibility`, `complexity`, `scope_creep`, `architecture`. Useful for filtering lessons by category during retrieval.

### 2.3 What Is an Observation

An **observation** is a factual finding from research or investigation that may inform future work. Observations sit between procedures (actionable) and lessons (failure-based) — they are neutral facts learned through experience.

**Characteristics:**
- Factual: states what was found, not what to do about it
- Informational: may become a procedure or lesson with more evidence
- Sourced: always traceable to a research dossier or investigation

**Schema:**
```json
{
  "id": "fact-20260406T230000Z-i9j0k1l2",
  "type": "observation",
  "slug": "pattern-harvest-safety-nets",
  "text": "Context compaction must be coupled with agent state reset. OpenHands #6357 showed that history truncation without resetting self.state.start_id causes infinite loops.",
  "source": "docs/cortex/research/pattern-harvest-safety-nets/20260406T060000Z-external-research.md",
  "extracted_at": "20260406T230000Z",
  "session_context": "pattern-harvest-safety-nets research phase"
}
```

### 2.4 How Procedures and Lessons Are Captured

#### Source 1: Repair Contract `Failed Approaches` Sections

The contract template already defines a structured format:
```markdown
### Attempt N (contract-NNN.md)
**Approach:** {what was tried}
**Result:** {what happened}
**Root cause:** {why it failed}
```

Each `Attempt` block becomes a `lesson` fact. The structured format makes regex extraction reliable.

**Extraction logic (pseudocode):**
```
for each contract in docs/cortex/contracts/*/contract-*.md:
  extract slug from front matter
  find ## Failed Approaches section
  for each ### Attempt N block:
    extract approach, result, root_cause
    emit lesson: "On {slug} (attempt {N}): tried '{approach}' — failed because '{root_cause}'"
```

#### Source 2: Investigation Artifacts

Investigation artifacts have required sections: `root cause`, `findings`, `repair recommendations`.

- `root cause` paragraphs → `observation` facts
- `repair recommendations` bullet points → `procedure` facts
- `findings` bullet points → `observation` facts (filtered: skip purely descriptive lines)

**Extraction logic:**
```
for each investigation in docs/cortex/investigations/*/*-investigation.md:
  extract slug from path
  parse root cause section → observation facts
  parse repair recommendations → procedure facts
  parse findings (lines starting with "- ") → observation facts
```

#### Source 3: Spec `Alternatives Considered` Sections

The spec template's alternatives section records rejected approaches with rationale. Each rejected alternative is a `lesson`.

**Extraction logic:**
```
for each spec in docs/cortex/specs/*/spec.md:
  find ### Alternatives Considered section
  for each **Name:** ... Rejected — {reason} entry:
    emit lesson: "On {slug}: {name} rejected because {reason}"
```

#### Source 4: Research Dossier Recommendations

The `## Recommendations` section in research dossiers contains actionable guidance.

**Extraction logic:**
```
for each dossier in docs/cortex/research/*/concept-*.md:
  find ## Recommendations section
  for each numbered line (^\d+\. ):
    emit procedure: extracted text
```

### 2.5 How Procedures and Lessons Surface

Procedures and lessons are embedded alongside all other facts in `fact-embeddings.npy`. They surface through the same retrieval pipeline — `cortex-retrieve.py` doesn't distinguish by type during similarity search.

**Surfacing points:**

1. **cortex-clarify** — When framing a new problem, retrieval queries like "what approaches have been tried for {problem domain}" surface relevant lessons. This prevents repeating known failures.

2. **cortex-research** — When researching a topic, retrieval queries surface observations from prior research on related topics. This prevents re-discovering known findings.

3. **cortex-spec** — When writing alternatives, retrieval queries surface lessons about rejected approaches. This prevents proposing approaches already known to fail.

4. **cortex-investigate** — When diagnosing a failure, retrieval queries like "what causes {symptom}" surface prior root cause findings.

5. **cortex-drive** — At Phase 1 initialization, retrieval loads relevant procedures for the current slug's domain.

**Query construction:** Each skill constructs a retrieval query from the current slug, problem statement, and mode. The query is a natural-language sentence, not keywords. Example: "approaches tried for embedding facts in a hook-based system with sub-5-second budget."

**Filtering by type:** The retrieval script returns all matching facts. The consuming skill can filter by `type` field if it only wants procedures (e.g., cortex-investigate only wants `lesson` and `observation` types).

## 4. Integration: Extraction -> Storage -> Embedding -> Retrieval

### 4.1 Complete Data Flow

```
[compaction event]
       |
       v
  cortex-precompact.sh (PreCompact, sync, ~200ms)
    - Reads: current-state.md, state.json, decisions.md, STATE.md,
             CONTEXT.md files, git log
    - Writes: .cortex/compaction/precompact-{ts}.md (enriched snapshot)
       |
       v
  cortex-postcompact.js (PostCompact, sync, ~300ms)
    - Reads: state.json, precompact snapshot, decisions.md, STATE.md,
             CONTEXT.md files, git log, contracts/*, investigations/*, research/*
    - Extracts: atomic facts (9 types) via pattern matching
    - Dedup: content hash against existing facts.jsonl
    - Writes: .cortex/facts.jsonl (append), last-compact-summary.md, next-prompt.md
       |
       v
  cortex-embed.py (PostCompact, async, ~3-5s for 50 facts)
    - Reads: .cortex/facts.jsonl, .cortex/fact-embeddings.meta.json
    - Calls: ollama /api/embed (nomic-embed-text, 768-dim)
    - Incremental: only embeds facts not yet embedded (compares count)
    - Writes: .cortex/fact-embeddings.npy, .cortex/fact-index.json,
              .cortex/fact-embeddings.meta.json
       |
       v
  [facts are now embedded and indexed]
       |
       |  ... time passes ... new session or skill invocation ...
       |
       v
  cortex-retrieve.py (query time, sync, ~80ms)
    - Called by: cortex-clarify, cortex-research, cortex-spec,
                cortex-investigate, cortex-drive, session-start hook
    - Input: natural-language query string + optional --top-k N + optional --type filter
    - Reads: .cortex/fact-embeddings.npy, .cortex/fact-index.json, .cortex/facts.jsonl
    - Calls: ollama /api/embed (single query, ~77ms)
    - Computes: cosine similarity, returns top-K facts as JSON on stdout
    - Fallback: if ollama unreachable or .npy missing, load all facts (no filtering)
       |
       v
  [consuming skill/hook]
    - Receives: JSON array of {id, type, text, score, source, slug}
    - Injects: relevant facts into context/prompt
    - Optional: filters by type (e.g., only lessons for investigate, only procedures for drive)
```

### 4.2 Timing Budget

| Stage | Trigger | Sync/Async | Latency | Budget |
|-------|---------|------------|---------|--------|
| precompact.sh | PreCompact event | sync | ~200ms | <5s |
| postcompact.js | PostCompact event | sync | ~300ms (current 54 facts), ~500ms projected with E4 sources | <5s |
| cortex-embed.py | PostCompact event | **async** | ~3-5s for 50 new facts, ~10s for 200 | no hard limit (non-blocking) |
| cortex-retrieve.py | skill invocation | sync | ~80ms (77ms ollama + 2ms numpy) | <2s |

**Total sync blocking time per compaction:** ~500ms (well within 5s budget)
**Async time:** 3-10s (runs in background, doesn't block session)
**Query time:** ~80ms (effectively instant for user)

### 4.3 File Layout

```

  facts.jsonl                    # Append-only fact store (source of truth)
  fact-embeddings.npy            # numpy array, shape (N, 768)
  fact-index.json                # {fact_id: row_index} mapping
  fact-embeddings.meta.json      # {last_embedded_count, model, timestamp}
  state.json                     # Pipeline state (existing)
  supervisor.jsonl               # Hook event log (existing)

```

### 4.4 Graceful Degradation Matrix

| Condition | Embedding | Retrieval | Fact Extraction |
|-----------|-----------|-----------|-----------------|
| ollama down | Skipped (exit 0) | Falls back to all facts | Unaffected |
| .npy missing | N/A | Falls back to all facts | Unaffected |
| facts.jsonl empty | No-op | Returns empty array | Writes first facts |
| facts.jsonl missing | No-op | Returns empty array | Creates file |
| No investigations exist | N/A | N/A | Skips investigation extraction |
| No repair contracts | N/A | N/A | Skips Failed Approaches extraction |

## 5. Open Questions Resolved

| Question | Resolution |
|----------|-----------|
| Should extraction run in postcompact or separate async? | **Postcompact (sync).** Extraction is fast (<500ms). Embedding is the slow part and runs async. |
| How does knowledge engine interact with Claude auto-memory? | **Complementary.** Auto-memory stores user preferences across projects. Cortex facts store project-specific technical intelligence. No overlap. |
| Should cortex-drive or individual skills query facts? | **Individual skills.** Each skill knows what it needs. cortex-drive reads procedures at init; cortex-investigate reads lessons on demand. |
| What's the right top-k? | **Default 10, configurable.** Based on semantic-retrieval benchmarks. Skills can override (e.g., cortex-investigate might request top-20 lessons). |
| Should facts have confidence scores? | **Optional field, not required.** Useful for future ranking but not blocking for v1. Set to "high" for explicit decisions, "medium" for inferred, "low" for single observations. |
| How to handle fact contradiction? | **Recency wins at query time.** Return both contradicting facts; the consuming skill sees both and uses the more recent one. No automatic conflict resolution in v1. |
| Should there be /cortex-remember? | **Deferred.** Not in this contract scope. The compaction-triggered pipeline is sufficient for v1. |
