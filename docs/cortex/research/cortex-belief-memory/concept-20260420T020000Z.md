## Summary

The codebase audit reveals that vault writes already exist in 3 of 4 target skills (cortex-clarify Phase 4c, cortex-research Phase 2.9, cortex-spec Phase 2c) via `cortex-vault-extractor.py`, but vault reads are entirely unimplemented — Phase 0 of cortex-research states intent to query facts.jsonl but provides no code path. Chrome research via ChatGPT (thinking mode) and Gemini converge on: (1) selective promotion policy — only derived lessons/design_rules auto-promote, not all stable beliefs; (2) minimal dependency tracking beyond just logging — both recommend a dependency table so retraction cascades deterministically; (3) world-state gating for cross-project queries — stable global beliefs as priors, contested beliefs as warnings only. They diverge on namespace scoping: ChatGPT recommends explicit `scope_type`/`scope_id` columns on logical_forms for rebuild independence; Gemini recommends filtering by namespace + extraction_run to avoid schema changes. The ChatGPT recommendation is stronger — filtering-only scoping creates fragile implicit ownership that breaks on rebuild.

## Findings

### F1: Vault write infrastructure exists, vault reads are absent

The `cortex-vault-extractor.py` script is already called in 3 skills (clarify Phase 4c, research Phase 2.9, spec Phase 2c) and writes typed facts to `facts.db` via `fact_store.add_fact()`. However:
- No Cortex skill queries vault beliefs before operating
- cortex-research Phase 0 states intent to query `.cortex/facts.jsonl` but has NO implementation
- The L3 engine (`l3_engine.py`) is never invoked — facts are extracted but never processed into logical forms, worlds, or derived objects
- Source: codebase audit of all 4 skill SKILL.md files

### F2: Four exact insertion points identified

| Skill | Read insertion | Write insertion |
|-------|---------------|-----------------|
| cortex-clarify | **New Phase 3.5**: Query vault for prior constraints/exclusions before writing brief | After Phase 4c: invoke L3 engine |
| cortex-research | **New Phase 0.5**: Query vault beliefs before question routing (replace unimplemented facts.jsonl query) | **New Phase 2.9b**: invoke L3 engine after vault extractor |
| cortex-spec | **New Phase 1d.5**: Query vault for architecture decisions and failed approaches before synthesizing | **New Phase 2c.5**: invoke L3 engine after vault extractor |

- Source: codebase audit, line-level analysis of SKILL.md files

### F3: Scope model — explicit scope on logical_forms (ChatGPT recommendation)

Add `scope_type` (global|project) and `scope_id` (nullable, slug for project-scoped) to logical_forms table. This is preferred over namespace-only filtering because:
- Rebuild independence: can rebuild one slug by loading its scoped forms + all global forms without reconstructing implicit ownership
- Promotion decisions: clear provenance for what came from which project
- Cross-project recall: single DB with fan-in queries, not fan-out across multiple DBs
- At ~2000 forms, SQLite handles this trivially with `INDEX logical_forms(scope_type, scope_id)`

Schema change:
```sql
ALTER TABLE logical_forms ADD COLUMN scope_type TEXT NOT NULL DEFAULT 'global';
ALTER TABLE logical_forms ADD COLUMN scope_id TEXT NULL;
```

Optional: `origin_kind` (observed|inferred|promoted), `promoted_from_scope_id`, `canonical_hash` for dedup.
- Source: ChatGPT thinking mode research

### F4: Promotion policy — selective, not mass-promote

Both ChatGPT and Gemini converge: do NOT promote all stable beliefs. Policy:

**Auto-promote at slug close:**
- Derived objects where type IN ('lesson', 'design_rule', 'anti_pattern', 'heuristic') AND status=stable AND not contradicted by global memory
- Change scope_type from 'project' to 'global', set scope_id=NULL

**Candidate-promote (requires recurrence):**
- Raw forms only if: status=stable, appeared in 3+ distinct scopes, semantically reusable (not project-specific entities/dates)

**Never promote:**
- Project-specific tasks, deadlines, stakeholder facts
- Transient implementation details
- Contested/rejected forms
- Forms tied to non-recurring project entities

**Test:** "Would I want this retrieved as prior knowledge six months later in a different project?"
- Source: ChatGPT thinking mode + Gemini synthesis

### F5: Minimal dependency tracking (JTMS Lite)

Both sources agree: more than just logging, less than full TMS. Add dependency tables:

```sql
CREATE TABLE derived_dependencies (
    derived_object_id TEXT NOT NULL,
    source_kind TEXT NOT NULL,        -- 'logical_form' | 'derived_object'
    source_id TEXT NOT NULL,
    role TEXT NOT NULL,               -- 'support' | 'contradict' | 'supersedes' | 'evidence'
    PRIMARY KEY (derived_object_id, source_kind, source_id, role)
);
```

**Invalidation logic:** When a source form is retracted/changed:
1. Find all derived objects depending on it (via `derived_dependencies`)
2. Mark them stale/invalidated
3. Recompute affected rules for the relevant scope
4. Surface unresolved cases for review only when recomputation can't settle them

Gemini suggests: use SQLite recursive CTE to cascade contestation — cheap at 2000 beliefs.
- Source: ChatGPT thinking mode + Gemini synthesis

### F6: Cross-project query model — 3-stage retrieval

**Stage 1 (global priors):** Global stable forms, promoted lessons/design_rules, high-support derived objects
**Stage 2 (recurring project knowledge):** Project-scoped forms about the topic IF stable AND supported in 2+ past scopes
**Stage 3 (caution set):** Contested/rejected beliefs as warnings — SEPARATE section, never mixed with priors

SQL view for default retrieval:
```sql
SELECT * FROM logical_forms lf
JOIN form_status fs ON lf.id = fs.form_id
WHERE (lf.scope_type = 'global' AND fs.world_id = 'current' AND fs.status IN ('active', 'stable'))
   OR (lf.scope_id = :current_slug AND fs.world_id NOT IN ('rejected'));
```

**Ranking:** Prioritize global > stable > high support > recent > unsuperseded. Penalize single-scope, contested, high-specificity.
- Source: ChatGPT thinking mode + Gemini synthesis

### F7: Inline extraction preferred over async

Gemini recommends inline (blocking, 1-2s) over async for 2-4 cycle systems. Reasoning: async creates a "dead zone" where the agent is smarter than its belief base — if cycle 1 discovers a breaking change but doesn't believe it until cycle 2, cycle 1's remaining work is based on stale assumptions. At 2-4 cycles, every action must be informed by the most recent discovery.

Counter-consideration: if extraction involves Haiku calls per artifact, latency could be 5-10s for large dossiers. Mitigation: extract only from the current artifact, not re-extract all.
- Source: Gemini synthesis

## Trade-offs

| Decision | Option A | Option B | Recommendation |
|----------|----------|----------|----------------|
| Scope model | Explicit scope_type/scope_id on logical_forms | Namespace + extraction_run filtering | **A** — rebuild independence, clear provenance |
| Promotion | Promote all stable | Selective (lessons/rules only + recurrence filter) | **B** — prevents semantic pollution |
| TMS | Full TMS | Minimal dependency tables + cascading invalidation | **Minimal** — JTMS Lite covers 80% of value |
| Extraction timing | Inline (blocking) | Async (post-hook) | **Inline** — for 2-4 cycle systems, stale beliefs > latency |
| Cross-project queries | Flat query (all beliefs) | 3-stage with world-gating | **3-stage** — prevents contamination |

## Recommendations

1. **Add scope columns to logical_forms** — `scope_type` (global|project) + `scope_id` (nullable slug). One schema migration, massive payoff for scoping and rebuild.

2. **Wire vault reads into 3 skills** — cortex-clarify (Phase 3.5), cortex-research (Phase 0.5), cortex-spec (Phase 1d.5). Replace the unimplemented facts.jsonl query in cortex-research.

3. **Wire L3 extraction into 4 skills** — after vault extractor in each skill, call `l3_engine.py extract_forms` + `run_inference`. Inline, not async.

4. **Add derived_dependencies table** — minimal JTMS Lite for cascading invalidation. One new table, recursive CTE for propagation.

5. **Implement promotion in cortex-close** — New Phase 5.5: promote lessons/design_rules to global scope, archive the rest. Apply the "6-month test."

6. **Build CortexModule** — L3 module with namespace 'cortex', form_types specialized for discovery artifacts (plan, design_rule, open_question), rules specialized for the research loop (plan_tracking, research_gap_detection).
