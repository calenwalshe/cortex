## Summary

Of 13 Cortex gates, only 8 produce user-facing blocking output and only 5 of those actually present decisions an approver needs to act on. The current output is mostly product-framed (not implementation-heavy) — the real problem is that it's procedural ("Run X command, then edit Y file") rather than decision-framed ("Here's what changes, approve or reject"). The fix is a three-layer gate brief pattern (impact line → item list → details on demand) applied to the 5 decision-presenting gates, plus filling in the 3 gates that have undefined output.

## Findings

### A. Gate Audit Results

**13 gates total. Breakdown by user-facing behavior:**

| Category | Gates | Count |
|----------|-------|-------|
| Presents a decision the user must act on | eval_proposal, contract_approval, slug_conflict, security_verdict, compliance_verdict | 5 |
| Blocks with informational message (user runs a command to fix) | reclarify, critical_uncertainty, evidence_backing, eval_validation | 4 |
| Mandatory but NO blocking output defined | ux_taste_eval, human_action | 2 |
| Listed in presets but never implemented | spec_approval, eval_approval | 2 |

**Current output assessment:**
- `reclarify`, `critical_uncertainty`, `evidence_backing` — already product-framed. Short, clear, actionable. No changes needed.
- `eval_proposal` — product-framed but procedural. Tells user to edit a file and re-run a command. Could be an inline approve/reject prompt instead.
- `contract_approval` — writes "PENDING HUMAN APPROVAL" but has no interactive prompt. User must manually edit the contract file. Weakest gate UX.
- `slug_conflict` — says "warn and ask to confirm" but the exact output text is unspecified. Needs a defined brief.
- `security_verdict` — says "output a prompt" but exact text is unspecified. Needs a defined brief.
- `compliance_verdict` — produces a verdict line in the review artifact. Product-framed but buried in output.

### B. CLI Approval Gate Patterns (External Research)

**Three-layer information architecture** (used by Terraform, Pulumi, Helm, Lerna):

| Layer | Purpose | Always shown? |
|-------|---------|---------------|
| Impact line | Instant comprehension — count + action type | Yes |
| Item list | What specifically changes — names + state transitions | Yes (default) |
| Field details | How exactly — attribute diffs, before/after | No — behind "details" option or flag |

**Key patterns from best-in-class tools:**

1. **Pulumi's three-option prompt**: `yes / no / details` — the "details" escape hatch lets approvers drill down without forcing details upfront. Most relevant for Cortex gates.

2. **"Would" language** (Homebrew, Terraform): "Would upgrade 3 packages" / "will be created" — future conditional tense frames the gate as a decision point, not a report.

3. **Batch approval with item enumeration** (Lerna): Show count, list items with state transitions, one approval for the batch. Not per-item unless items have genuinely different risk profiles.

4. **Friction proportional to risk**: `y/N` for reversible, full `yes` for destructive. Mandatory gates should have higher friction than informational ones.

5. **CI escape hatch**: Every tool provides `--auto-approve` / `--yes`. Cortex already has this via autonomy presets (`full-auto` skips configurable gates).

6. **Confirmation fatigue warning** (NN/g research): Too many gates trains users to auto-approve. Reduce to minimum decisions needing human input.

## Trade-offs

### Option: Shared gate brief template (all gates use same format)
**Pros:** Consistent UX across all skills, single template to maintain, approvers learn the format once
**Cons:** Different gates have different decision types (approve/reject vs confirm vs select) — forcing one format may be awkward for some
**Verdict:** selected — use a shared template with sections that are conditionally included based on gate type

### Option: Per-skill formatting logic
**Pros:** Each gate gets perfectly tailored output
**Cons:** 5 different formats to maintain, inconsistent approver experience, duplication
**Verdict:** rejected

### Option: Post-processing step (generate brief from existing output)
**Pros:** No changes to existing gate logic — add a brief as an overlay
**Cons:** Requires parsing existing output which varies by skill, fragile if output format changes
**Verdict:** rejected — better to generate the brief inline where the gate data is already structured

### Option: Add confidence signal to briefs
**Pros:** Approver knows whether to dig deeper ("strong evidence" vs "limited evidence")
**Cons:** Subjective, hard to calibrate, may cause approvers to always dig into "limited evidence" items
**Verdict:** deferred — not needed for v1, can add later based on usage

## Recommendations

- **Create a `templates/cortex/gate-brief.md` template** with three sections: Impact (1-line count + action), Items (what specifically needs approval with state transitions), and Details (expandable — "show details" option or reference to full artifact). All 5 decision-presenting gates use this template.

- **Apply the Pulumi three-option pattern** to interactive gates: `approve / reject / details`. Details shows the full artifact path and relevant sections. This replaces the current "edit a file and re-run" pattern for eval_proposal and contract_approval.

- **Use "would" language** in impact lines: "Would approve contract token-efficiency-001 with 11 done criteria" not "Contract token-efficiency-001 is pending approval."

- **Define output for the 3 undefined gates**: slug_conflict (confirm overwrite with current vs new slug), security_verdict (summarize findings count by severity, ask to proceed), and the 2 mandatory gates (ux_taste_eval, human_action) which need output specs even though they can't be skipped.

- **Don't add briefs to informational gates** (reclarify, critical_uncertainty, evidence_backing, eval_validation) — these already work well. They block with a clear message and a command to fix. No decision needed, just action.

- **Scope: 5 gates need briefs, 3 gates need output definitions, 2 gates are unimplemented (leave for now).**

## Open Questions

- Should the brief template be a standalone file or inlined in each SKILL.md? Standalone is DRYer but adds a file read per gate check.
- How should multi-item gates (eval proposal with 8 dimensions) present the batch? One approval with item list, or highlight only approval_required dimensions?
- Should `contract_approval` become an interactive AskUserQuestion prompt instead of "edit file manually"?
