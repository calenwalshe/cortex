# Research Dossier: execution-supervisor — concept

**Slug:** execution-supervisor
**Phase:** concept
**Timestamp:** 20260404T015000Z
**Depth:** standard (system audit + prototype)

## Summary

The Cortex system has 13 hooks, 3 scripts, 12 skills, and multiple state files — but zero observability into whether they're working correctly. Hooks exit silently on error, state transitions aren't logged, and coherence between state files is never checked. The token-ledger.db already captures rich telemetry (482 turns, 32 codex tasks, daily rollups) but only for cost tracking — not operational health. The minimal viable supervisor is two components: (1) a one-line JSONL append added to each existing hook for event logging, and (2) a `cortex-health.py` report command that runs coherence checks and summarizes the event log. Prototyped both: JSONL appends add <2ms overhead, health report runs in <100ms and catches real issues (stale embeddings, state drift, missing artifacts).

## System Audit

### Current Surface Area

| Component | Count | Logging Today |
|-----------|-------|---------------|
| Hooks (.claude/hooks/cortex-*) | 13 | None — all exit 0 silently on error |
| Scripts (scripts/cortex/) | 3 | stderr messages only (not persisted) |
| Skills (skills/cortex-*/) | 12 | None |
| State files (.cortex/) | 5 | Overwritten, no history |
| Handoff files (docs/cortex/handoffs/) | 7 | Overwritten, no history |
| Archived slugs | 3 | decisions.md archive index only |

### What's Already Logged (token-ledger.db)

| Table | Rows | What It Captures |
|-------|------|------------------|
| claude_turns | 482 | Token usage per turn (model, cost, project, phase, skill) |
| codex_tasks | 32 | Codex execution (tokens, cost, exit code, elapsed time) |
| sessions | 4 | Session lifecycle (start, end, compaction count) |
| daily_rollup | 5 | Daily cost aggregation |

This is cost telemetry, not operational health. It answers "how much did we spend?" but not "is the system working correctly?"

### What's NOT Logged

1. **Hook fire/fail events** — Hooks exit 0 on all errors. No record of whether they ran, succeeded, or silently failed.
2. **State transitions** — Mode changes (clarify → research → spec → execute) happen in state.json but the history is overwritten.
3. **Gate evaluations** — Which gates passed, failed, or were auto-skipped is only partially recorded in decisions.md (autonomy decisions only).
4. **Coherence violations** — state.json and current-state.md can drift. No detection.
5. **Artifact lifecycle** — Files created by skills/hooks are listed in state.json but never verified for existence.
6. **Skill invocations** — No record of which /cortex-* skills ran or what they produced.

## Design Decisions — All Resolved

### 1. Event Logging → One-line JSONL append in each hook

**Decision:** Add a single `echo '{"ts":"...","event":"...","hook":"..."}' >> .cortex/supervisor.jsonl` line to each of the 13 hooks.

**Evidence:**
- JSONL append benchmarks at <2ms per write (100 appends in 162ms)
- No new process, no new dependency — pure bash `echo >>` 
- Hooks already have the context (hook name, mode, slug) available as variables
- Human-readable with `cat` or `jq`, machine-parseable for reports

**Rejected alternatives:**
- Separate logging daemon: overkill, adds a process to manage
- SQLite table in token-ledger.db: would couple supervisor to token-ledger; different concern
- Write to stderr and capture: unreliable, depends on hook runner behavior

### 2. Health Report → `cortex-health.py` CLI command

**Decision:** Standalone Python script that runs coherence checks and summarizes the event log.

**Evidence:**
- Prototyped in research: runs in <100ms, catches real issues
- Matches existing pattern (cortex-embed.py, cortex-retrieve.py, cortex-judge.py)
- Can be called manually (`python3 scripts/cortex/cortex-health.py`) or from a skill

**Report sections:**
1. **Inventory** — component count (hooks, scripts, skills, archives)
2. **Coherence** — all 6 checks with pass/fail
3. **Recent activity** — last N days from token-ledger (cost, turns)
4. **Event log summary** — hook fires, errors, state transitions from supervisor.jsonl
5. **Pipeline status** — current slug, mode, gates

### 3. Log Storage → `.cortex/supervisor.jsonl` with rotation

**Decision:** Single JSONL file in .cortex/, rotated when it exceeds 10K lines.

**Evidence:**
- .cortex/ is already gitignored — supervisor logs are operational, not versioned
- 10K lines ≈ 2-3MB — negligible storage
- Rotation: rename to `supervisor.jsonl.1` and start fresh (keep one backup)
- JSONL is human-readable (`cat`), filterable (`jq`), and greppable

### 4. Event Taxonomy → 4 event types

**Decision:** Log these event types only:

| Event | Source | Fields |
|-------|--------|--------|
| `hook_fire` | Each hook's entry point | `{ts, event, hook, slug, mode, exit_code}` |
| `hook_error` | Each hook's error handler | `{ts, event, hook, slug, error}` |
| `state_transition` | session-end hook (detects mode change) | `{ts, event, from_mode, to_mode, slug}` |
| `gate_eval` | phase-guard, task-completed | `{ts, event, gate, result, slug}` |

4 event types. Not logging every tool use or file write — that's too noisy and already covered by token-ledger.

### 5. Review UX → `cortex-health.py` command + optional `/cortex-status` integration

**Decision:** Primary UX is `python3 scripts/cortex/cortex-health.py` for an on-demand health report. Optionally, `/cortex-status` skill can call it to add a health section.

**Evidence:**
- The user reviews "infrequently" (from clarify brief assumptions)
- An on-demand command is simpler than continuous monitoring
- The report is self-contained — no context needed to read it

### 6. "According to Plan" → Contract done criteria + gate progression

**Decision:** "On track" means: gates are advancing in order, artifacts listed in state.json exist, and the active contract's done criteria are being worked toward (validators passing over time).

**Evidence:**
- Contracts already have done_criteria and validators — the supervisor checks if they've been run and what the results were
- Gate progression (clarify → research → spec → execute) is the canonical workflow — deviations are visible in the event log

## Implementation Scope

### What to build:

1. **`scripts/cortex/cortex-health.py`** — health report CLI (coherence checks + event log summary + activity)
2. **Hook instrumentation** — add 1-line JSONL append to each of the 13 hooks (~1 line change per hook)
3. **Log rotation** — in cortex-health.py, rotate supervisor.jsonl when >10K lines

### What NOT to build:

- No daemon or background process
- No alerting or notifications
- No new hooks (piggyback on existing 13)
- No new state files (supervisor.jsonl is a log, not state)
- No UI

### Estimated changes:

- 13 hooks: +1 line each (JSONL append)
- 1 new script: cortex-health.py (~200 lines)
- 1 test file: test_supervisor.py

## Trade-offs

| Decision | Chosen | Alternative | Why |
|----------|--------|-------------|-----|
| Event logging | JSONL append in hooks | Separate daemon / SQLite | <2ms overhead; no new process; human-readable |
| Health report | On-demand CLI | Continuous monitoring / scheduled | User reviews infrequently; simpler |
| Log location | .cortex/supervisor.jsonl | docs/cortex/supervisor/ | Operational log, not a versioned artifact |
| Event types | 4 types (hook_fire, hook_error, state_transition, gate_eval) | Log everything | Signal-to-noise balance; tool use already in token-ledger |
| Rotation | 10K lines, keep 1 backup | Time-based / size-based | Simple; 10K ≈ weeks of activity |
| Coherence checks | 6 specific checks | Generic "diff all state" | Targeted checks catch known failure modes; generic diff is noisy |
