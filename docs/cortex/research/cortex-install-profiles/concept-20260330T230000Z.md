## Summary

The clarify brief assumed a shell script installer — the actual installer is `bin/install.js` (Node.js), entirely driven by `runtime-manifest.json`. This is a clean foundation for profiles. The critical finding is that **the cortex repo already only contains framework skills** — tool skills (web, ai, google, cli) live as standalone real directories in `~/.claude/skills/` outside the repo. This means the existing install behavior is already equivalent to a `core` profile. Implementing `--profile=full|core` requires: (1) moving tool skill source files into `skills/` in the cortex repo, (2) tagging each skill in the manifest with its profile membership, (3) adding `--profile` flag parsing to `install.js`, and (4) writing a `~/.claude/.cortex-profile` marker for idempotency. Phabricator/arc compatibility is confirmed with standard git best practices.

## Findings

- **Installer is Node.js, not shell**: `bin/install.js` is the real entry point. The clarify brief assumed `install.sh` — this assumption was wrong. The installer already supports `--dry-run`, `--project`, and `--verbose` flags.
- **`runtime-manifest.json` is the single source of truth**: Skills, agents, hooks, and hook events are all arrays in this JSON file. The installer iterates them without any conditional logic — profiles are not yet a concept.
- **Framework skills only in the repo**: `~/projects/cortex/skills/` contains exactly: cortex-audit, cortex-clarify, cortex-investigate, cortex-research, cortex-review, cortex-spec, cortex-stash, cortex-status, cortex-fit, reup. No tool skills.
- **Tool skills are currently unmanaged by the cortex installer**: web, ai, google, cli exist as real directories under `~/.claude/skills/` — they were installed manually, not via `bin/install.js`. They have no presence in the cortex repo.
- **Current install == effective core profile**: Running `bin/install.js` today produces what we're calling the `core` profile. Making `core` the default is therefore 100% backwards compatible.
- **No cross-skill hard dependencies**: Framework skill SKILL.md files reference Gemini API (`import google.generativeai as genai`) in code snippets but this is the Gemini API directly — not an import of the `/google` tool skill. Zero hard dependencies from framework skills to tool skills.
- **skill-sync.sh is a separate tool**: `~/.claude/skills/skill-sync.sh` handles Google Drive sync for skill portability between machines (OD ↔ Mac). It explicitly skips symlinks — Cortex framework skills are symlinks and will never be synced by it. Tool skills (real dirs) would be synced. This is relevant for the Meta workflow.
- **Manifest already has a clean hook wiring system**: `hook_events` in the manifest drive `settings.json` injection. Profile-scoped hooks are not needed — all hooks are framework-level.
- **Phabricator/arc is git-level, not GitHub-level**: `arc diff` works with any git remote. Gotchas: need `.arcconfig` with `phabricator.uri` + `repository.callsign`; must rebase before diffing; `git fetch` before `arc diff`; no auto-sync with GitHub PRs. All solvable with documented workflow.
- **Manual API key setup steps in install.js currently assume full profile**: The post-install summary in `printSummary()` always shows `TAVILY_API_KEY`, `PPLX_API_KEY`, `FIRECRAWL_API_KEY`, `GEMINI_API_KEY` setup instructions. These should only appear for `--profile=full`.

## Trade-offs

### Option: Separate manifest arrays (`core_skills: []`, `full_skills: []`)
**Pros:** Trivially simple to parse; no schema change to existing skill entries.
**Cons:** Skills in both profiles duplicated; brittle when adding a third profile; hard to see at a glance what profile a skill belongs to.
**Verdict:** rejected

### Option: Tagged skill objects (`{"name": "...", "profiles": ["core", "full"]}`)
**Pros:** Single source of truth per skill; extensible to N profiles without schema changes; `api_dependency` and other metadata can be added to same object; filter logic in install.js is one line.
**Cons:** Breaking change to existing `runtime-manifest.json` schema (skills currently a flat string array); install.js needs to handle both old (string) and new (object) formats during transition, or migrate all at once.
**Verdict:** selected — migrate all skills to object format in one commit; test suite already checks against the manifest so the transition will be caught if missed

### Option: Default profile = `full`
**Pros:** Existing users who manually installed tool skills would see them re-managed by the installer.
**Cons:** Breaks backwards compatibility — existing users cloning fresh today get framework skills only; defaulting `full` would suddenly install tool skills requiring unconfigured API keys, producing errors on first use.
**Verdict:** rejected

### Option: Default profile = `core`
**Pros:** 100% backwards compatible (matches current install output); principle of least privilege; no broken API key errors on fresh install; explicit opt-in for external dependencies.
**Cons:** Users who want full profile must pass `--profile=full`; first-time documentation must be clear.
**Verdict:** selected

### Option: Profile marker as `~/.claude/.cortex-profile` (plain text)
**Pros:** Dead simple; no JSON parse risk; no collision with Claude Code's own `settings.json`.
**Cons:** Not extensible if other config fields are needed later.
**Verdict:** selected for v1 — a dedicated file avoids any collision risk with Claude Code's own `~/.claude/settings.json`; can migrate to config.json in v2 if needed

### Option: Keep tool skills outside the cortex repo (user-managed)
**Pros:** No changes to repo structure; cortex repo stays focused on framework.
**Cons:** `--profile=full` has no source to install from; users must still manually install tool skills; the profile flag for `full` becomes meaningless without the files in the repo.
**Verdict:** rejected — tool skills must move into `skills/` in the cortex repo to make `--profile=full` meaningful

## Recommendations

- **Move tool skill directories into the repo**: Copy `~/.claude/skills/{web,ai,google,cli}/` into `skills/` in the cortex repo. These become first-class citizens managed by `bin/install.js` under the `full` profile.
- **Migrate `runtime-manifest.json` skills to tagged objects**: Change `"skills": ["cortex-clarify", ...]` to `"skills": [{"name": "cortex-clarify", "profiles": ["core", "full"]}, ...]`. Tool skills get `"profiles": ["full"]` only.
- **Add `--profile=core|full` flag to `install.js`**: Parse it (support both `--profile=full` and `--profile full`). Default to `core`. Write chosen profile to `~/.claude/.cortex-profile`.
- **Make install idempotent across profile changes**: If `.cortex-profile` exists and differs from the requested profile, remove old profile-exclusive symlinks before installing new ones.
- **Gate post-install API key instructions on profile**: Only show `TAVILY_API_KEY` etc. in the summary when `--profile=full` was used.
- **Add `.arcconfig` template for downstream forks**: Document the `phabricator.uri` + `repository.callsign` fields needed to get `arc diff` working. Include in a `docs/cortex/downstream/` directory or a README section so Meta-fork users have a copy-paste starting point.
- **Document the `git fetch → rebase → arc diff` workflow** in a `DOWNSTREAM.md` or similar for Meta users.
- **Update installer test suite (`test/installer.test.sh`)**: Add tests for `--profile=core` and `--profile=full` — verify core gets only framework symlinks, full also gets tool skill symlinks.

## Open Questions

- **Where to store the tool skill source files in the repo?** Flat `skills/web/`, `skills/ai/` etc. (consistent with current framework skills) vs a `skills/tool/` subdirectory to visually separate them. Flat is simpler and consistent.
- **Should the skill-sync.sh tool be made profile-aware?** Currently it syncs all real-dir skills and skips symlinks. If tool skills become symlinks (like framework skills), they'll stop syncing via Google Drive to Mac — which is probably fine, but needs a decision.
- **What happens to existing manually-installed tool skill directories when `--profile=core` is run?** The installer should detect them as real dirs (not cortex-managed symlinks) and leave them alone, not delete them.
- **Should `arc diff` workflow notes go in the repo itself?** Since Meta engineers will be cloning and reading this repo, inline docs are valuable — but it may be out of scope for this feature.
