## Finding 1: Context Capacity Gate — EXISTS, Needs Reliability Fix

### What's Already Built

| Component | Status | Location |
|-----------|--------|----------|
| `context_capacity` gate in resolve-autonomy.js | **DONE** | `scripts/cortex/resolve-autonomy.js` line 18 — mandatory gate, cannot be disabled |
| `cortex-context-capacity.sh` PostToolUse hook | **EXISTS, buggy** | `hooks/cortex-context-capacity.sh` — installed in user settings.json line 148-154 |
| Warning at 25% remaining, block at 15% remaining | **Implemented** | Hook lines 71-83, thresholds configurable via `.cortex/autonomy.json` |

### The Reliability Bug

The hook reads `context_window.remaining_percentage` from PostToolUse stdin. **This field is NOT documented as available in PostToolUse hooks.** Claude Code officially provides `context_window` data only to the `statusLine` mechanism, not to hook events. GitHub issues #34340 and #11008 request exposing context data to hooks and remain open.

If the field is absent, the hook silently exits 0 — meaning **it never fires**.

### The Proven Fix

Other hooks in the system already solve this via a **bridge file pattern**:

1. `gsd-statusline.js` (statusLine provider) writes `/tmp/claude-ctx-{session_id}.json` on every turn
2. PostToolUse hooks read from that bridge file using `session_id` from stdin

Working implementations:
- `gsd-context-monitor.js` lines 63-84 — fires context warnings at 35% and 25% remaining
- `context-checkpoint.js` line 70-71 — reads bridge file with 60s staleness check

### What Needs to Change

1. **Rewrite `cortex-context-capacity.sh`** to read from the bridge file (`/tmp/claude-ctx-{session_id}.json`) instead of stdin `context_window`
2. **Add staleness check** — ignore bridge file older than 60s (same as context-checkpoint.js)
3. **Switch warning case to JSON stdout** with `additionalContext` for in-conversation warning (keep exit 2 + stderr for hard block)
4. **Register in project settings.json** — currently only in user-level settings, not project-level

### Thresholds (Already Configured)

| Level | Remaining % | Behavior |
|-------|-------------|----------|
| Normal | > 25% | Proceed |
| Warning | 15-25% | Warn in conversation, suggest /compact |
| Block | < 15% | Hard block via exit code 2 |

Note: Original Pattern Harvest spec said 75/85% used (=25/15% remaining). The hook already uses the inverted form — these are the same thresholds.

### Open Question Resolved

> "How does a PostToolUse hook detect context window usage in Claude Code?"

**Answer:** Via the bridge file written by the statusLine provider. Direct PostToolUse stdin access is not reliable.

## Finding 2: Circuit Breaker + Iteration Budget — ALREADY IMPLEMENTED

| Task router (Codex vs Claude classification) | **DONE** | `scripts/cortex/task-router.js` — 10-rule first-match decision tree |

### Circuit Breaker Design

- **State:** `/tmp/gsd-codex-circuit-breaker-$(basename "$PWD")` — plain integer file
- **Threshold:** 3 consecutive failures (configurable via `$CODEX_CIRCUIT_BREAKER` env var)
- **Triggers:** timeout (exit 124), crash (non-zero exit), test failure, iteration budget exceeded
- **Recovery:** File deleted on any success — immediate reset
- **Scope:** Persists across tasks within a wave and between waves (keyed by project dir in /tmp), resets on reboot

### Iteration Budget Design

- **Formula:** `FILE_COUNT * MAX_STEPS_MULTIPLIER` (default multiplier: 10), minimum floor: 20
- **Counting:** Parses Codex JSONL output, counts `turn.completed` events
- **Enforcement:** Post-hoc only — checked after Codex exits. Cannot kill mid-execution (relies on `timeout` for that)
- **Fallback:** Records failure and returns `"fallback"` status to execute-plan orchestrator

### Gaps Identified

| Gap | Severity | Description |
|-----|----------|-------------|
| No test coverage | High | `test/codex-exec-wrapper.test.sh` has 15 tests but none cover circuit breaker or iteration budget |
| `parse_error` doesn't record failure | Medium | Unparseable Codex output doesn't increment breaker counter |
| `merge_conflict` doesn't record failure | Medium | Worktree merge failures don't increment breaker counter |
| No half-open recovery | Low | Once tripped, breaker stays open until success or reboot — no time-based auto-recovery |
| Post-hoc step counting | Low | Cannot kill runaway task mid-execution; `timeout` is the only mid-run kill |

### Open Questions Resolved

> "Where does circuit breaker state persist between Codex task invocations?"

**Answer:** `/tmp/gsd-codex-circuit-breaker-$(basename "$PWD")` — a plain integer file in /tmp. Survives across tasks and waves, resets on reboot.

> "Should iteration budget (max_steps) be configurable per-task or global default?"

**Answer:** Already configurable via `$CODEX_MAX_STEPS_MULTIPLIER` env var (default 10). Per-task override not implemented but the multiplier × file count formula adapts to task size.

> "What happens when a budget/breaker fires mid-wave?"

**Answer:** The wrapper returns `"fallback"` status. The execute-plan orchestrator checks `codex.fallback_on_failure` config and moves the failed task to the Claude task list. Only the current task is affected — the wave continues with remaining tasks.

### Repair Budget Defaults

| Parameter | Default | Configurable? |
|-----------|---------|---------------|
| `max_repair_contracts` | 3 | Per-contract |
| `cooldown_between_repairs` | 1 (phase) | Per-contract |

### Convergence Detection Algorithm

**Already specified as Jaccard similarity:**
- Extract set of failing validators/criteria from each of the 3 most recent repair contracts
- Compute: `|failing_intersection| / |failing_union|`
- Threshold: >80% similarity across 3+ consecutive repairs
- Action: Generate `convergence-stall-{timestamp}.md`, set `reclarify_required: true`

### Gaps Identified

| Gap | Severity | Description |
|-----|----------|-------------|
| Budget sync: contract → state.json | High | No logic reads `max_repair_contracts` from contract, counts existing contracts, and writes `repair_budget` to state.json. cortex-drive reads from state.json but nothing populates it from the contract. |
| Budget enforcement in cortex-investigate | High | cortex-investigate creates repair contracts without checking budget. Only cortex-drive checks budget before dispatching repair. |
| Repair budget population in cortex-spec | Medium | cortex-spec Phase 4 doesn't explicitly mention populating repair budget fields when creating contract-001. |
| Failed Approaches carry-forward | Medium | When creating repair contract-NNN+1, nothing reads prior contracts' Failed Approaches to populate the new one. |
| Convergence detector untested | Medium | No repair contracts (contract-002+) have ever been created. The convergence detector has never fired. |
| Cooldown enforcement | Low | `cooldown_between_repairs` field exists in template but no logic checks time/phase distance between repairs. |
| Stall detection in cortex-drive | Low | cortex-drive doesn't check for convergence-stall files before dispatching repair (row 11). |
| pattern-harvest/contract-001.md | Low | Created before repair budget fields were added — missing the field (but defaults apply). |

### The Enforcement Chain (What Should Happen)

```
cortex-investigate detects failure
  → checks repair_budget (remaining > 0?)
    → YES: create contract-NNN+1 with Failed Approaches from prior contracts
    → NO: escalate to human, do NOT create repair contract
      
cortex-review runs on repair contract
  → convergence detector fires if 3+ contracts with >80% Jaccard similarity
    → generates convergence-stall.md
    → sets reclarify_required: true
    
cortex-drive reads state
  → row 11: repair budget > 0 AND no convergence stall → dispatch repair
  → row 12: repair budget exhausted → stop, escalate
  → (new) convergence stall detected → stop, escalate
```

### Open Questions Resolved

> "What constitutes 'similar' failures for convergence detection?"

**Answer:** Jaccard similarity on the set of failing validator/criterion identifiers. Already specified in cortex-review SKILL.md. No fuzzy/NLP comparison needed — validators have discrete identifiers.

> "Should repair_budget be per-slug or per-contract?"

**Answer:** Per-contract. `max_repair_contracts: 3` in the contract template means max 3 repair contracts for that specific contract chain. Different slugs get independent budgets.
