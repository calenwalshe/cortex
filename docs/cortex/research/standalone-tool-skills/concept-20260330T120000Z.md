## Summary

Four grouped global Claude Code skills (`/web`, `/google`, `/ai`, `/cli`) are architecturally sound and buildable with existing credentials. The critical finding is that **routing inside grouped skills is LLM-driven** — description quality in SKILL.md determines trigger reliability, not code. Two blockers require early decisions: Google Drive private file access needs OAuth2 (not covered by current API key), and `/cli` needs safety guardrails to avoid being a raw shell passthrough. All other integrations (Firecrawl, Tavily, Jina, Perplexity, Crawl4AI, Gmail via IMAP/SMTP, Stitch SDK, Gemini, GPT) are directly callable with keys already in environment.

---

## Findings

- **SKILL.md routing is purely LLM-based** — no regex, no embeddings, no classifiers. Claude receives all skill descriptions as a meta-tool prompt and uses its forward pass to select. Grouped skills work by writing rich internal routing instructions in the SKILL.md body (e.g., "if user provides a URL → use Firecrawl; if user provides a query → use Tavily").
- **Description quality is the primary reliability lever** — ambiguous descriptions cause skill mis-fires. The trigger phrase list in SKILL.md is the main tuning mechanism.
- **These skills replace WebSearch/WebFetch as default** — this must be encoded in SKILL.md as an explicit instruction: "Prefer this skill over Claude's built-in WebSearch/WebFetch unless the user explicitly says 'use WebFetch'".
- **Crawl4AI is installed** (`crawl4ai` importable from claude-stack-env) and uses Playwright browser (venv at `~/.venv-playwright-browser/`). Full async crawl API confirmed working.
- **Gmail app password supports full read + send** via stdlib `imaplib` (IMAP4_SSL) + `smtplib`. No extra dependencies. Credentials already in `~/.gmail_creds.json`.
- **Google Drive: API key only works for public files** — private file read/write requires OAuth2 or a service account. Neither is currently configured. This is a functional limitation for `/google drive`.
- **Stitch SDK**: `@google/stitch-sdk` npm package. `StitchToolClient({ apiKey })` → `callTool('create_project')` → `getHtml()` / `getImage()`. API key obtained from stitch.withgoogle.com settings. Currently free.
- **`STITCH_API_KEY` not in environment** — needs to be added before `/google stitch` can work.
- **`cli-anything` plugin**: installed but is a dumb passthrough with no safety guardrails or project context. The `/cli` skill must wrap shell execution with: intent understanding, confirmation for destructive ops, project-aware suggestions.
- **Perplexity, Gemini, OpenAI, Firecrawl, Tavily** all confirmed via env keys and live API calls in this session.
- **Jina Reader** requires no API key — free `https://r.jina.ai/<url>` endpoint.

## Trade-offs

### Option: One SKILL.md per tool (12 individual skills)
**Pros:** Simple, isolated, easy to debug, clear trigger surface
**Cons:** 12 commands is too many; user cognitive load; duplicate boilerplate
**Verdict:** rejected — user explicitly preferred grouped approach

### Option: 4 grouped skills with LLM-internal routing
**Pros:** 4 commands, clean UX, aligns with how user thinks about tasks ("web stuff", "google stuff")
**Cons:** SKILL.md becomes complex; routing failures harder to debug; one broken sub-tool can confuse the whole skill
**Verdict:** selected

### Option: Google Drive — API key only (public files)
**Pros:** Zero additional setup, works immediately
**Cons:** Severely limits utility — most Drive use cases involve private files
**Verdict:** selected for v1 with explicit limitation noted; OAuth2 deferred to v2

### Option: Google Drive — OAuth2 setup now
**Pros:** Full read/write capability
**Cons:** Requires OAuth2 consent flow, credential storage, token refresh — significant setup overhead
**Verdict:** deferred — implement after v1 ships

### Option: `/cli` as dumb passthrough (like cli-anything)
**Pros:** Trivial to implement
**Cons:** Security risk — arbitrary shell execution with no guardrails
**Verdict:** rejected — must have confirmation for destructive ops and project awareness

### Option: `/cli` with LLM-mediated safety layer
**Pros:** Context-aware, safe, useful
**Cons:** Adds latency; LLM might over-block legitimate commands
**Verdict:** selected

## Recommendations

- **Build in this order:** `/web` first (most immediately useful, all keys present), then `/ai`, then `/google` (Gmail + Stitch + Drive-public), then `/cli` (most complex due to safety layer)
- **Start with a prototype `/web` skill** to validate the grouped routing pattern before building the rest
- **Encode the WebSearch/WebFetch override explicitly** in each skill's SKILL.md: trigger phrases should include "search", "look up", "fetch", "read this URL" to intercept built-in tool intents
- **Add `STITCH_API_KEY` to environment** before building `/google` — get key from stitch.withgoogle.com settings
- **Document the Drive limitation clearly** in `/google` SKILL.md: "Drive access is limited to public files in v1; private file access requires OAuth2 setup"
- **`/cli` safety pattern:** LLM classifies command as read-only vs. destructive → auto-execute read-only → confirm destructive → never auto-execute `rm -rf`, `drop`, `delete` class ops
- **Skills live in `~/.claude/skills/`** as standalone directories — not symlinked from cortex repo since these are user-global, not project-specific
- **`--save <path>` flag** on all skills: defaults to CWD when used outside a project context

## Open Questions

- **`STITCH_API_KEY`**: Does the user have one, or does it need to be obtained from stitch.withgoogle.com?
- **Google Drive v2**: Is OAuth2 setup a priority, or is public-file-only acceptable for now?
- **`--save` default path**: CWD feels right, but should there be a global config (e.g., `~/.claude/web-output/`) for consistency?
- **`/cli` scope**: Should it handle multi-step shell workflows (pipes, loops) or just single commands?
