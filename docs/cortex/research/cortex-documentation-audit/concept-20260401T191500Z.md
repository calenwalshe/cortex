## Summary

The core documentation (COMMANDS.md, AGENTS.md, CONTINUITY.md, EVALS.md, INTELLIGENCE_FLOW.md, DISCOVERY_LOOP.md) is substantively accurate and covers the 8-command surface well. The single biggest gap is a complete absence of hook documentation — 12 hooks fire on 9 Claude Code events, none have a dedicated reference. Secondary gaps are: 3 stale phrases in CORTEX.md, an incomplete state.json schema in CONTINUITY.md (3 missing fields), and no documentation for the cortex-close and cortex-stash commands that exist as installed skills outside the "surface" 8. The fix is additive: one new file (HOOKS.md), small patches to CORTEX.md and CONTINUITY.md, and a decision on whether cortex-stash and cortex-close belong in the surface docs.

## Findings

### CORTEX.md — 3 stale references, 1 structural omission
- The intro paragraph reads "via 7 commands" — should be 8.
- The `docs/` section of the File Structure listing says `COMMANDS.md — 7-command reference` — should be 8.
- The `docs/` section omits `DISCOVERY_LOOP.md` entirely (it exists and is a key reference).
- The `skills/` section of the File Structure does not list cortex-stash, cortex-close, or cortex-fit (intentionally outside the 8-command surface, but worth a note).

### COMMANDS.md — accurate, but missing two doc dimensions
- All 8 surface commands are documented with correct IO tables, rules, and examples. ✓
- **Missing: state effects.** No command entry documents which `.cortex/state.json` fields it reads or writes. A reader cannot tell from COMMANDS.md alone that `/cortex-clarify` sets `gates.clarify_complete: true` or that `/cortex-research` may write `reclarify_required: true`.
- **Missing: block conditions.** No command entry documents what preconditions cause the command to block (e.g., `/cortex-spec` blocks if `reclarify_required: true` or a critical open question exists, but this is only discoverable by reading SKILL.md).

### CONTINUITY.md — solid, but state.json schema is stale
- Cover is excellent: continuity stack, resume protocol, compaction flow, repair loop, LOOP-01 through LOOP-04 mechanisms all documented. ✓
- **state.json schema is missing 3 fields** that exist in production:
  - `reclarify_required: bool` — written by `/cortex-research` when evidence invalidates the frame; read by `/cortex-spec` as a blocker
  - `experiment_complete: bool` — written by `/cortex-experiment close`; read by `/cortex-spec` as a gate
  - The `eval_complete` gate flag (used at close)
- The "Session Hooks" table lists 4 hooks. The installed hook set is 12 scripts:
  `cortex-distribute`, `cortex-phase-guard`, `cortex-postcompact`, `cortex-precompact`,
  `cortex-session-end`, `cortex-session-start`, `cortex-sync`, `cortex-task-completed`,
  `cortex-task-created`, `cortex-teammate-idle`, `cortex-validator-trigger`, `cortex-write-guard`
- No dedicated HOOKS.md exists — the 8 non-continuity hooks are completely undocumented.

### AGENTS.md — accurate, missing team-mode composition
- All 4 agents documented with role, write scope, read scope, invocation, and output artifacts. ✓
- **Missing:** what the `--team` flag composition is — which agents are invoked, what each does in team mode, how they coordinate. The flag is mentioned in COMMANDS.md but team composition is not described anywhere.
- **Minor:** cortex-scribe's invocation section says "invoked by hooks" but doesn't list which hooks trigger it.

### EVALS.md — accurate, minor omission
- Eval lifecycle, candidate matrix, repair loop, artifact paths all correct. ✓
- **Missing:** `--write-plan` flag is not mentioned in the Invocation table. The table shows "Eval plan — Written by eval-designer after human approves" but the actual mechanism is `/cortex-research --write-plan`.

### INTELLIGENCE_FLOW.md — accurate and up to date
- ASCII spine diagram with discovery loop backtracking paths is correct. ✓
- Gate conditions table reflects all 3 spec-readiness blockers. ✓
- No gaps found.

### DISCOVERY_LOOP.md — accurate and up to date
- Comprehensive coverage of all 6 sections. ✓
- No gaps found.

### Missing: Hooks Reference
- **Biggest single gap in the documentation.** 12 hooks exist; none have a dedicated reference page.
- CONTINUITY.md covers 4 continuity hooks informally. The other 8 have no documentation at all:
  - `cortex-phase-guard` — PreToolUse Write|Edit: blocks writes outside permitted roots in pre-execute modes
  - `cortex-validator-trigger` — PostToolUse Write|Edit: appends to dirty-files.json in execute/repair mode
  - `cortex-task-created` — TaskCreated: validates new tasks have objective, deliverable, and contract link
  - `cortex-task-completed` — TaskCompleted: blocks false completion if evals failing
  - `cortex-teammate-idle` — TeammateIdle: feeds actionable feedback to idle agent workers
  - `cortex-sync` — PostToolUse Write|Edit: syncs cortex skills to GitHub
  - `cortex-distribute` — PostToolUse Write|Edit async: distributes recipes to email, research to NotebookLM
  - `cortex-write-guard` — agent-invoked only (not a Claude event hook): enforces agent write roots

### Missing: cortex-close and cortex-stash documentation
- `cortex-close` is an installed user-facing skill (archives a completed slug) but appears nowhere in public docs.
- `cortex-stash` is an installed user-facing skill (idea capture during active work) but appears nowhere in the 8-command surface docs. It was delivered in v1.1 (13 requirements satisfied) but docs/COMMANDS.md was not updated to include it.
- Decision needed: are cortex-stash and cortex-close part of the documented surface, or are they intentionally "operator utilities" separate from the intelligence spine?

### Missing: Installation / Quick-Start Guide
- No document describes how to install Cortex on a new project (the installer, what gets symlinked, how to verify it works).
- No "getting started" path for a new operator. The README may cover this — not audited here.

## Trade-offs

### Option: Minimal patches — fix stale refs, add HOOKS.md, update state.json schema
**Pros:** Targeted, low risk, fast to execute. Each fix is in exactly the right place.
**Cons:** Doesn't resolve the cortex-stash/cortex-close surface decision or add a quick-start guide.
**Verdict:** selected — right scope for a docs audit milestone. Cortex-stash/close surface question is a separate decision.

### Option: Full surface expansion — add cortex-stash and cortex-close to COMMANDS.md
**Pros:** Complete surface documentation; operators can discover all installed commands from one place.
**Cons:** COMMANDS.md was deliberately scoped to the 8-command intelligence spine. Adding utility commands conflates two different categories of capability.
**Verdict:** deferred — needs a design decision first: define what "the surface" means and whether it includes lifecycle utilities (stash, close) or only intelligence commands.

### Option: Per-command pages (replace COMMANDS.md with individual files)
**Pros:** Each command gets full depth without size constraints; easier to link from CORTEX.md.
**Cons:** COMMANDS.md is already the right length and well-organized. Splitting would break existing references.
**Verdict:** rejected — current single-file structure works. Add depth to existing entries instead.

## Recommendations

- **CORTEX.md patch (3 lines):** Change "7 commands" → "8 commands" in intro; update `COMMANDS.md` description in file structure to "8-command reference"; add `DISCOVERY_LOOP.md` to the docs/ section of the file structure.
- **Write `docs/HOOKS.md`:** New reference page documenting all 12 hooks — trigger event, conditions, inputs (stdin schema), outputs (files written), side effects, async/sync, and interaction with state.json. This is the highest-priority gap.
- **CONTINUITY.md state.json schema:** Add `reclarify_required`, `experiment_complete`, and `eval_complete` field descriptions to the schema table and example JSON block.
- **EVALS.md invocation table:** Add `--write-plan` row to the invocation table.
- **COMMANDS.md per-command state effects:** Add a "State Effects" row to each command's IO section listing which state.json fields are read and written.
- **COMMANDS.md per-command block conditions:** Add a "Block Conditions" row to each command entry listing preconditions that cause the command to refuse to run.
- **Decide: cortex-stash and cortex-close surface status.** Are they part of the documented surface? If yes, add to COMMANDS.md. If no, create a separate `docs/UTILITIES.md` or add a brief note in COMMANDS.md directing readers to their SKILL.md files.
