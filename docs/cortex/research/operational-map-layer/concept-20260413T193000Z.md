## Owner Summary

- **What we found:** PostToolUse with session_id grouping is the best available capture mechanism given the hook payload constraints — Stop and TaskCompleted hooks carry no file-edit data, and neither existing file (dirty-files.json or token-ledger.db) can seed the ledger without new capture infrastructure.
- **What it changes:** The clarify brief's core assumptions hold: PostToolUse + session_id + JSONL is the recommended design. Two genuine open questions remain (hotspot noise threshold and actual edit velocity ground truth) that the spec must resolve via live validation ACs.
- **What's still open:** One edge case to handle in the spec: `/clear` starts a new session_id mid-work, potentially fragmenting co-change grouping for edits that are logically part of the same task.

## Summary

All 7 research questions were answered from direct codebase inspection — no web research needed. The core design (PostToolUse + session_id grouping + JSONL ledger) is confirmed: `cortex-session-end.sh` explicitly states "Stop fires after EVERY agent response" and carries no file-path payload; `cortex-task-completed.sh` reads only state.json and eval-status.md with no file-edit data; token-ledger.db exists at `~/.cortex/token-ledger.db` but has no `file_path` column; dirty-files.json only records execute/repair mode edits with no timestamps. PostToolUse is the best available hook: it delivers both `session_id` (confirmed: `token-ledger.js:39 const sessionId = data.session_id`) and `tool_input.file_path` in its payload — no other hook provides both fields. JSONL append matches the existing facts.jsonl pattern and is the correct storage format. The minimum useful payload is `{file_path, edit_count, co_change_partners}` — file name alone is insufficient for coupling detection. Rolling window of 500 entries is appropriate for the measured velocity of ~17 sessions over 10 days (April 3–13).

## Findings

**Q1 — Stop hook firing and payload:**
- `cortex-session-end.sh` comment line 4: "Stop fires after EVERY agent response" — confirmed, not at session termination
- Stop payload: the hook reads `mode`, `slug`, `approval_status`, `active_contract`, `artifacts` from state.json via `jq`; it does NOT receive `file_path` or `session_id` from hook stdin
- Stop is disqualified as co-change grouping boundary on both grounds: fires too frequently (every response turn) and carries no file-edit data

**Q2 — dirty-files.json / token-ledger.db as ledger seed:**
- `dirty-files.json`: 240 file paths accumulated; only populated during `execute|repair` mode (validator-trigger.sh line: `case "$MODE" in execute|repair)`); no timestamps; no session_id; paths include worktree paths — not a general edit ledger
- `token-ledger.db` lives at `~/.cortex/token-ledger.db` (not in `.cortex/` project dir); schema: `claude_turns(session_id, model, input_tokens, …, remaining_pct)` — no `file_path` column; 5,617 turns from 58 total sessions, 17 cortex-specific sessions (April 3–13)
- Neither can seed the operational ledger: dirty-files.json is mode-gated and lacks timestamps; token-ledger.db has session_id but no file paths

**Q3 — TaskCompleted hook payload:**
- `cortex-task-completed.sh` reads `active_contract` from state.json, then reads `eval-status.md` for FAIL rows
- No file list, no task ID in payload; blocking mechanism is `{continue: false, stopReason: "..."}` output on stdout
- TaskCompleted is a validation gate only — carries no file-edit data; disqualified for co-change grouping

**Q4 — Co-change grouping unit (comparison):**
- Stop: disqualified (fires every response turn, no file payload)
- TaskCompleted: disqualified (no file payload at all)
- PostToolUse session_id: confirmed present in payload — `token-ledger.js` line: `const sessionId = data.session_id;` — already used by existing hook infrastructure
- Verdict: PostToolUse session_id is the natural and only viable co-change grouping key. Files edited under the same session_id constitute a co-change group. Implementation complexity is low — field already available in payload.
- Edge case: `/clear` starts a new session_id mid-work. Edits before and after a `/clear` in the same logical task will have different session_ids and won't be co-grouped. Document this limitation explicitly in the spec.

**Q5 — Storage format (JSONL vs per-session JSON):**
- JSONL append (`.cortex/edit-ledger.jsonl` — matches `facts.jsonl` pattern):
  - Append: O(1) write
  - Pruning: read all lines + rewrite; measured ledger entry size = ~230 bytes (`{timestamp, session_id, file_path, tool_name, slug}` — sampled directly); at 500 entries = ~115KB max → rewrite is fast (<5ms in Python on local disk)
  - Read for injection: read all, parse, aggregate hotspot counts — O(N), acceptable for N ≤ 500
  - Matches existing facts.jsonl pattern (same directory, same format)
- Per-session JSON files (`.cortex/edit-ledger/{session_id}.json`):
  - Pruning: delete old files → no rewrite; clean
  - Read: list directory + merge files → more complex
  - Directory proliferation: 17 sessions already logged; at 1-2 sessions/day = 30+ files in 30 days
- Verdict: JSONL is superior for this use case. Single file, O(1) append, matches established patterns. 100KB rewrite for pruning is fast. Per-session adds directory management complexity without meaningful benefit at the measured velocity.

**Q6 — Minimum payload for scope decisions (codebase):**
- Structural-map-layer brief Q1 asked "which Python files to index in corpus" — with hotspot data, we'd know that `.claude/hooks/cortex-session-end.sh` was edited 5× more frequently than `scripts/cortex/cortex-embed.py`, informing corpus priority
- Structural-map-layer write root decision: spec chose 8 write roots; co-change data would show that `.claude/settings.json` and `~/.claude/skills/cortex-clarify/SKILL.md` always change together — this pattern is exactly why the spec listed them as co-located in Section 8 (Sequencing), but the insight was intuitive rather than data-driven
- Operational-map-layer (this brief): with hotspot data, we'd know cortex-session-end.sh is volatile (high edit frequency) before deciding to depend on it for co-change grouping — which would reinforce the PostToolUse decision
- Minimum payload that changes scope decisions: `{file_path, edit_count}` enables hotspot ranking (identify which files are volatile before choosing write roots). Adding `{co_change_session_ids, top_co_change_partners}` enables coupling detection (identify which files always change together). The edit_count alone would have changed the corpus prioritization decision in structural-map-layer Q1.
- Conclusion: minimum viable payload is `file_path + edit_count`. Co-change partners are the next-highest value add. Injection format: top-5 hotspots by edit_count + top-3 co-change pairs is sufficient; estimated ~300-400 chars, fits within per-skill inline read budget (bypasses 1,604-char additionalContext limit).

**Q7 — Rolling window size and pruning:**
- Measured velocity: 17 cortex-specific sessions in 10 days (April 3–13) = ~1.7 sessions/day
- At estimated 10-30 Edit/Write events per session = 17-51 edit events/day
- Edit events per session are not directly measured (dirty-files.json is execute-only; token-ledger.db tracks turns, not edit tool calls). Estimating from token-ledger.db: 17 cortex sessions over 10 days = 1.7 sessions/day; assuming 10-30 Edit/Write calls per session based on project history (worktree sessions average higher). This is a bounded estimate, not an empirical count. Spec should include an AC to observe actual ledger growth after 5 sessions.
- At this velocity estimate: 500-entry window ≈ 10-30 days of history; 30-day age window ≈ 500-1,500 entries
- Both 500-entry and 30-day windows capture similar history at current velocity — either is appropriate
- Pruning trigger: at append time, if len(entries) > 500, drop oldest entries and rewrite (100KB max → fast)
- Alternatively: at inject-read time, prune entries older than 30 days before generating the hotspot summary
- Verdict: 500-entry cap is simpler and implementation-complete. Prune at append time, not read time, to prevent unbounded ledger growth even during periods of inactivity.

## Trade-offs

### Option: Stop hook as co-change grouping boundary
**Pros:** Conceptually clean — "everything before this response" is one unit
**Cons:** Fires after every response turn, not at conversation end; no file-path data in payload; would produce hundreds of tiny "co-change groups" per session with 1-3 files each — signal is too noisy
**Verdict:** rejected

### Option: TaskCompleted hook as co-change grouping boundary
**Pros:** Semantically meaningful — "everything done for this task" is a natural unit
**Cons:** No file-edit data in payload; doesn't fire for non-contract work (clarify, research); would require a separate tracking mechanism anyway
**Verdict:** rejected

### Option: PostToolUse session_id as co-change grouping key
**Pros:** session_id is in every PostToolUse payload (confirmed); already used by token-ledger.js; natural "everything done in this conversation" grouping; implementation is simple (one field read from stdin JSON)
**Cons:** `/clear` fragments session_id — logically related edits across a `/clear` won't be co-grouped; workaround is to note the limitation rather than fix it (complex fix, low-frequency event)
**Verdict:** selected

### Option: Per-session JSON storage
**Pros:** Clean pruning (delete old files); no rewrite needed
**Cons:** Directory management overhead; more complex read (merge multiple files); 30+ files at current velocity
**Verdict:** rejected

### Option: JSONL append storage
**Pros:** Matches facts.jsonl pattern; O(1) append; single file; simple implementation; 100KB max rewrite for pruning is fast
**Cons:** Full-file rewrite on prune; slightly slower read than per-session (must parse all lines)
**Verdict:** selected

## Recommendations

- Implement edit ledger as `.cortex/edit-ledger.jsonl` with one entry per Edit/Write event; schema: `{timestamp, session_id, file_path, tool_name, slug}` — `slug` from state.json at capture time enables per-slug filtering
- Group co-changes by `session_id`; document the `/clear` fragmentation limitation in the spec without attempting to fix it
- Cap at 500 entries; prune at append time when `len > 500` (drop oldest entries, rewrite file)
- Minimum injection payload: top-5 hotspot files by edit_count + top-3 co-change file pairs; surface via per-skill inline reads (not SessionStart additionalContext injection) to bypass the 1,604-char budget constraint
- Do NOT modify Stop, TaskCompleted, or dirty-files.json — the operational layer hook is an additive PostToolUse registration alongside cortex-validator-trigger.sh
- Add `slug` field to ledger entries: lets the injection step filter to "files relevant to this clarify brief's corpus" rather than all-time hotspots across all slugs

## Adjacent Findings

- **`/clear` silently severs co-change grouping across session boundaries:** When a user runs `/clear` mid-work, the subsequent conversation starts with a new `session_id`. Files edited before and after the `/clear` in the same logical task will be placed in separate co-change groups, underreporting their coupling. This matters for this slug's spec: the co-change signal is bounded by conversation sessions, not logical task sessions. The spec must document this limit clearly so intelligence phases don't over-trust co-change data for tasks that typically span multiple sessions or compactions. Source: `token-ledger.js` session_id handling + Claude Code session lifecycle.

## Open Questions

- **Hotspot noise threshold (min edit_count):** What minimum edit count distinguishes a true hotspot from incidental single-session edits? A file edited once is not a hotspot; a file edited 3+ times across different sessions probably is. Threshold is not empirically determined from this research pass — resolve in spec via AC that requires live ledger data after 5+ sessions. Tentative recommendation: edit_count ≥ 3 AND edited in ≥ 2 distinct sessions.
- **Edit velocity ground truth:** Actual Edit/Write events per session were not directly measured (see Q7 finding). Spec should include an AC to log observed ledger size after 5 real sessions and validate the 500-entry window assumption.
