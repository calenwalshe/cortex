## Summary

**The seven-terminal taxonomy is already partially implemented in Cortex** — the existing `/cortex-spec` necessity gate produces four verdicts (BUILD, NARROW, DEFER, REJECT) that map onto the seven terminals as a 4→7 refinement. This collapses the implementation work from "design a new resolution model" to "refine an existing 4-verdict system into 7 terminal states and elevate it from a `/cortex-spec` internal gate to a loop-level model." The minimum viable implementation is **even smaller than iter-2 estimated**: add a `--terminal {name}` flag to `/cortex-close` (a skill that currently takes zero arguments), extend the decisions.md archive line to record the terminal, and add a `current-understanding.md` template with a Possible Terminals section. **No new commands are needed for the pilot** — `/cortex-decompose`, `/cortex-hold`, and per-terminal artifacts can defer until a slug actually reaches one of those terminals. Outside-in research validates 5 of 6 non-transitional terminals against RFC process literature (steady state, abandoned, retired, on hold, stabilization); the one ambiguous case (RFC "steady state") is covered by Hold-on-Dependency with a "manual re-entry" trigger. CLI design literature recommends specialized subcommands over polymorphic flags for user-facing tools — but for the MVP, a single polymorphic `--terminal` flag is correct because we don't yet know which terminals will be used in practice; specialization can come later as a hybrid (subcommands dispatching to shared logic). **The pilot scope is now: 1 SKILL change + 1 template + 1 doc convention.**

## Findings

### The necessity gate already names the terminals (the load-bearing finding)

- **`/cortex-spec` SKILL.md lines 116-164 implement a "Necessity Attack" that produces one of four verdicts:** BUILD, NARROW, DEFER, REJECT. Each verdict maps onto the seven-terminal taxonomy as a 4→7 refinement:

| Necessity Verdict | Maps to Terminal(s) | Refinement |
|---|---|---|
| **BUILD** | Commit-to-Build | 1:1 (no refinement needed) |
| **NARROW** | Decompose OR Reframe-and-Continue | 1:2 — split by whether scope is heterogeneous (Decompose) or just oversized (Reframe) |
| **DEFER** | Experiment-Required OR Hold-on-Dependency | 1:2 — split by whether the gap is closeable by a bounded test (Experiment) or by external change (Hold) |
| **REJECT** | Kill-with-Learning OR Already-Exists | 1:2 — split by whether the rejection is "no value" (Kill) or "value exists elsewhere" (Already-Exists). The current REJECT description literally says: *"This solves a problem that doesn't exist, OR the existing system already handles it."* — both terminals are already named in the verdict text. |

- **This changes the implementation story.** The seven-terminal model is not a new system; it is a *refinement of an existing one*. The work is: (a) elevate the verdicts from "internal `/cortex-spec` gate output" to "loop-level state," (b) split the 1:2 verdicts into their two child terminals, (c) make the terminal recordable at close time. Most of the conceptual machinery is already there.

- **The necessity gate fires per slug at `/cortex-spec` time.** It logs verdict + confidence + slug to decisions.md. There is *already* an audit trail of which verdict each slug received. We can grep decisions.md for prior verdicts as ground truth.

### Codebase audit (q5, q6) — minimum viable change set

- **`/cortex-close` currently takes zero arguments.** Adding `--terminal {name}` is purely additive. The skill is a pure state-transition machine: copy artifacts to archive, append a line to decisions.md, reset state.json. The terminal value plugs into the Phase 5 archive line with a single field extension. No structural blockers.
- **`decisions.md` archive index format is pipe-delimited:** `- {ts} | {slug} | closed | contract: {path} | eval-plan: {path}`. Adding `terminal: {name}` as another field is backward compatible; legacy entries simply lack it.
- **`/cortex-spec` is already decoupled from "spec is the only commit action."** Necessity gate verdict is advisory, not a hard route. A REJECT verdict produces a block message but does not force a particular close path. `/cortex-close --terminal kill` can coexist with `/cortex-spec` without changes to either.
- **Zero terminal artifacts exist on disk.** No `kill-rationale.md`, no `decomposition.md`, no `use-existing.md`, no `hold-trigger.md`, no `learning-contract.md` files anywhere in the repo. The `experiments/` directory does not exist for any slug. This is the empty-state confirmation: the model is genuinely net-new at the artifact level, even though the verdict vocabulary is partially existing.
- **`current-understanding.md` does not exist anywhere.** Net-new template, ~40 lines, lives at `templates/cortex/current-understanding.md`.
- **No precedent for cross-artifact frontmatter sync** in Cortex (e.g., a script that reads brief frontmatter and updates another file). The Possible Terminals section in current-understanding.md must be either manually maintained or written by `/cortex-clarify` at brief-write time. Manual is sufficient for MVP.

### RFC process terminal states (q1) — taxonomy validation

- **RFC processes (Rust, Fuchsia, IETF) recognize multiple resolution states beyond go/no-go**, validating that the seven-terminal model is not a Cortex novelty:
  - **Abandoned** ≈ Kill-with-Learning ✓
  - **Retired** ≈ Already-Exists (or post-Commit retirement) ✓
  - **On Hold** ≈ Hold-on-Dependency ✓
  - **Proposed Standard / Stabilization** ≈ post-Commit-to-Build downstream states (out of scope for pre-spec phase)
  - **Steady State** = "Discussion reaches consensus on pros/cons and alternatives, without deciding to proceed" — *ambiguous match*. This is intellectually-resolved-but-action-deferred, distinct from Hold (which has an external blocker) and from Reframe (which produces a new iteration). Best mapped to Hold-on-Dependency with a "manual re-entry" trigger meaning "future-me decides if it's worth the effort." Adding an 8th terminal for this case is rejected as marginal.
- **Five of the six non-transitional terminals have direct RFC analogs.** The two without direct analogs are Decompose (which is a Cortex-specific concern about heterogeneous scope) and Experiment-Required (which is Cortex's hypothesis-test pathway). Both are sound additions because they reflect Cortex's structure (clarify→research→spec pipeline) rather than RFC's flat-list structure.
- **Result: the seven-terminal taxonomy is validated.** No missing terminal surfaced. No terminal needs to be added or merged.

### CLI command shape (q4)

- **Specialized subcommands beat polymorphic `--type` flags for user-facing CLIs** in discoverability and invocation clarity. Real-world examples: `git submodule add/update/init` (specialized, won) vs. hypothetical `git submodule --type=add` (polymorphic, lost). `kubectl get/apply/delete` is verb-first specialized; flags are used sparingly.
- **For the MVP, this is the wrong recommendation.** The MVP should use the polymorphic `--terminal {name}` flag on `/cortex-close` because: (a) we don't yet know which terminals will be invoked in practice — premature specialization risks building commands nobody uses; (b) the surface-area cost of adding 4-5 new top-level commands is high relative to the marginal discoverability benefit at this stage; (c) the hybrid pattern (specialized subcommands dispatching to shared close logic) can be added later as a refinement once usage patterns are known.
- **Long-term recommendation: hybrid.** Start with `/cortex-close --terminal {name}` for all six terminals. If `--terminal kill` and `--terminal experiment-required` see heavy use while `--terminal hold-on-dependency` is rare, promote the heavily-used ones to specialized commands (`/cortex-kill`, `/cortex-experiment open` already exists) and leave the rare ones as flag-driven. This is the standard "evolve from polymorphic to specialized as usage data arrives" pattern.

### Wait — what did I not consider?

- **The current-understanding.md doc could be derived from the brief at `/cortex-clarify` time, not maintained separately.** The brief already declares `initial_terminal_set` in YAML frontmatter (this slug's iter-3 brief is the working example). `/cortex-clarify` could generate the initial `current-understanding.md` skeleton — including the Possible Terminals table — at brief-write time. Subsequent passes update only the "ruled out" column, not the schema. This makes the doc partially derived rather than fully manual, with no need for a sync script.
- **The pilot can succeed with retroactive testing.** Grep `decisions.md` for prior necessity verdicts on closed slugs. Map each verdict to its terminal candidates. For slugs that received NARROW or DEFER or REJECT historically: were they handled correctly? This is a retrospective audit that produces baseline data without requiring new slugs to be run through the new system. It's a form of bounded micro-experiment on the design itself.

## Trade-offs

### Option A: Ship the pilot as 1 SKILL change + 1 template + 1 convention
**Scope:** Add `--terminal {name}` flag to `/cortex-close`, write `templates/cortex/current-understanding.md`, document the brief frontmatter convention (`initial_terminal_set`, `ruled_out`).
**Pros:** Minimum viable; ships in days not weeks; no new commands; no new artifacts beyond the template; can be retroactively tested against decisions.md history; matches Shape Up "smallest unit that reduces uncertainty meaningfully."
**Cons:** Doesn't yet implement the per-terminal artifacts (decomposition.md, hold-trigger.md, use-existing.md, kill-rationale.md). A slug reaching one of those terminals during the pilot would have only the `--terminal` record in decisions.md, not a structured artifact for the learning.
**Verdict:** **selected.**

### Option B: Add per-terminal commands and artifacts up front
**Scope:** A + `/cortex-decompose`, `/cortex-hold`, `/cortex-kill` commands + four new artifact templates.
**Pros:** Complete vision shipped at once; specialized subcommands match CLI design best practice (long-term).
**Cons:** Speculative — builds commands and templates that may be unused for months; reproduces the dormant-discovery-loop failure mode at higher cost; per-terminal artifact schemas would be designed without empirical input from real use.
**Verdict:** rejected. This is the iter-2 9-gap trap recurring at finer resolution.

### Option C: Subsume the necessity gate, not just compose with it
**Scope:** Modify the necessity gate to produce one of seven terminals instead of one of four verdicts, then everything else (close action, current-understanding sync) reads from that single source.
**Pros:** True 1:1 mapping; one source of truth; cleanest model; maximum re-use of existing infrastructure.
**Cons:** Touches `/cortex-spec` which is core; changes the verdict vocabulary that decisions.md history is keyed on (backward compatibility burden); introduces a hard fork between pre-change and post-change verdict semantics.
**Verdict:** deferred. The pilot in Option A produces enough data to know whether the verdict refinement is correct *before* touching `/cortex-spec`. Premature subsumption risks the same backward-compat burden the SKILL refactor would create.

### Option D: Auto-derive current-understanding.md from brief at clarify time
**Scope:** A + `/cortex-clarify` extension that writes the initial `current-understanding.md` skeleton from the brief's `initial_terminal_set` frontmatter.
**Pros:** No manual sync; the doc is always consistent with the brief; one less thing for humans to maintain.
**Cons:** Adds writing logic to `/cortex-clarify`; the doc has fields that aren't in the brief (durable findings, provisional thoughts) which still need manual or skill-driven population.
**Verdict:** **selected as part of A.** The clarify extension is small (~10 lines in artifact-write phase) and removes a coordination cost.

### Option E: Retroactive baseline audit before any code changes
**Scope:** Grep `decisions.md` for historical necessity verdicts, manually classify each closed slug as the terminal it should have reached, compute whether the new model would have produced different/better outcomes.
**Pros:** Empirical case for the model; produces a metric ("X of Y closed slugs would have benefited"); validates the 4→7 refinement claim with real data; cheapest possible test; matches the iter-3 brief's "little tests" philosophy by being a self-experiment.
**Cons:** Sample size is small (~10 closed slugs); historical verdicts may be missing for slugs that bypassed the necessity gate.
**Verdict:** **selected as part of A** — run before writing the SKILL change, as a 30-minute micro-experiment that validates the design.

## Recommendations

**Final scope: a 3-piece pilot, plus a 1-piece pre-pilot validation.**

### Pre-pilot validation (~30 min, no code changes)

1. **Retroactive necessity-verdict audit.** Grep `docs/cortex/handoffs/decisions.md` for historical `gate: necessity | verdict:` entries. For each non-BUILD verdict, classify which of the seven terminals it should have mapped to in retrospect. Produce a small results table: `slug | verdict | terminal | confidence`. If at least 60% of historical NARROW/DEFER/REJECT verdicts can be cleanly assigned a finer-grained terminal, the 4→7 refinement is validated and the pilot proceeds. If not, the model needs more work before any code is written. **This is itself the first micro-experiment under the new philosophy** — a sub-1-hour bounded test that closes uncertainty about the design before committing to spec.

### Pilot scope (assuming validation passes)

1. **Add `--terminal {name}` flag to `/cortex-close`.** Single SKILL change. Required value, must be one of the seven terminal slugs. Phase 5 of close extends the decisions.md line with a `terminal: {name}` field. No other behavior changes — close still copies artifacts, resets state.json, and so on. Backward-compatible: legacy entries lack the field.
2. **Add `templates/cortex/current-understanding.md`.** New template with sections: Possible Terminals (table), Durable Findings, Provisional Thoughts, Open Questions, Iteration History. Lightweight; ~40 lines.
3. **Extend `/cortex-clarify` to auto-write initial `current-understanding.md`.** When a clarify brief is written and contains an `initial_terminal_set` field in YAML frontmatter, `/cortex-clarify` also writes (or updates) `docs/cortex/research/{slug}/current-understanding.md` from the template, populating the Possible Terminals table from the frontmatter. This is ~10 lines of additional logic in the existing artifact-write phase.

### Convention (no code, doc only)

4. **Document the `initial_terminal_set` and `ruled_out` brief frontmatter fields** in `templates/cortex/clarify-brief.md` and the `/cortex-clarify` SKILL doc. Most slugs use the default (all six terminals); some can pre-rule-out.

### Explicit deferrals (preserve in deferred-gaps.md)

- New commands `/cortex-decompose`, `/cortex-hold`, `/cortex-kill` — defer until a slug actually reaches one of those terminals. The polymorphic `--terminal` flag is sufficient for the pilot.
- Per-terminal artifact templates (`kill-rationale.md`, `decomposition.md`, `use-existing.md`, `hold-trigger.md`) — defer until a slug actually reaches one. Then design the schema empirically from the slug's needs, not speculatively.
- Modifying the `/cortex-spec` necessity gate to produce 7 verdicts instead of 4 — defer until the pilot proves the 4→7 refinement is correct in practice.
- Cross-artifact frontmatter sync mechanism (script that updates current-understanding.md when the brief changes) — defer; manual update at clarify time is sufficient for the pilot.

### How this avoids the dormant-loop failure mode

- **The pre-pilot retroactive audit is the first micro-experiment.** It costs nothing and produces empirical data before any code is written. If the audit fails (the 4→7 refinement isn't clean against history), the pilot doesn't ship and we go back to clarify with more information. This is the "little tests build to decision gates" philosophy applied to the meta-problem of designing the philosophy.
- **The pilot is unconditional, not opt-in.** Every `/cortex-close` invocation after the change requires a `--terminal` value. There is no "optional terminal" mode. This forces the pattern into use immediately.
- **The pilot dogfoods on this slug itself.** When `clarify-research-loop` eventually closes (assuming Commit-to-Build is the verdict), it will close via `/cortex-close --terminal commit-to-build`. The current-understanding.md doc for *this* slug will be the working example included in the spec deliverable.

## Open Questions

- The retroactive audit (recommendation 1) needs a clear pass/fail threshold. Working hypothesis: ≥60% of non-BUILD historical verdicts cleanly mapping to a finer terminal = pass. Is 60% the right threshold or should it be higher/lower?
- When `/cortex-clarify` auto-writes the initial `current-understanding.md`, what happens on iteration N>1 of the brief? Overwrite the doc, append a new section, or write a new file `current-understanding-iter{N}.md`? Working hypothesis: the doc is single-file living, updated in place, with iteration history tracked inside it (not via filename versioning).
- The Possible Terminals table needs an "evidence" column linking to the artifact that ruled each terminal out. Should this be a literal Markdown link, an artifact path string, or both?
- Should the `/cortex-close` skill validate that the chosen terminal was actually in the brief's `ruled_out: []` complement set? I.e., refuse `--terminal kill` if the brief explicitly excluded Kill from the initial set? (Working hypothesis: yes — this catches the case where someone closes a slug at a terminal that was never on the table.)
- Is there a 7th terminal hidden in RFC "Steady State" that we should add despite the marginal-case argument? (Working hypothesis: no — Hold-on-Dependency with manual re-entry trigger covers it.)
- For the long-term hybrid command shape (recommendation: evolve from polymorphic to specialized), what's the trigger to promote a flag value to a dedicated command? Usage frequency? Specific user request? Let's defer this question to a follow-up slug.
