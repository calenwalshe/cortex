## Idea

Close the observation→action loop during GSD execution. Currently cortex-drive dispatches `/gsd:drive` and waits — it has no visibility into what's happening mid-execution and can't adapt. The supervisor logs events (255+ in supervisor.jsonl), the circuit breaker trips after 3 Codex failures, and the task router classifies tasks as Codex-safe vs Claude-required. But these are all reactive (post-failure) not adaptive (mid-execution). The system should detect patterns during execution — Codex struggling on a task type, context degradation mid-phase, a wave producing low-quality output — and reroute, pause, or escalate before the circuit breaker trips.

This is the difference between a fire alarm (circuit breaker — reacts after damage) and a smoke detector (adaptive execution — reacts to early signals before failure).

---

## Goal

During GSD execution, the system detects early warning signals from supervisor events, Codex JSONL output, and validator results — and adapts mid-wave by rerouting tasks, adjusting parallelization, pausing for human review, or escalating — so that execution self-corrects before hitting circuit breaker thresholds.

---

## Non-Goals

- [owner-intent] No code without contract.
- [owner-intent] Disk is truth.
- [owner-intent] GSD owns execution. Cortex does not write to .planning/ except via /cortex-bridge.
- Not replacing the circuit breaker — that stays as the hard stop. Adaptive execution is the soft layer before it.
- Not replacing the task router's classification logic — that stays static. Adaptive execution adjusts routing based on runtime signals.
- Not building a real-time dashboard — signals are file-based and consumed by hooks/scripts.
- Not modifying how GSD plans or phases work — only how tasks are dispatched and monitored within an existing GSD execution.
- Not adding mid-task intervention (can't kill a running Codex task and restart it differently) — adaptation happens at task boundaries.

---

## Constraints

- [owner-intent] Validators must run.
- [owner-intent] Cortex will never require a database, external service, or network dependency for core operation.
- Must work within the existing hook architecture — no new daemon processes
- Adaptation decisions must be logged to supervisor.jsonl (full audit trail)
- Must not add >100ms latency to task dispatch (check signals, don't block on analysis)
- Must be backward compatible — projects without adaptive execution continue to work (fallback to current static routing)
- The GSD execution boundary must be respected — Cortex observes and influences dispatch, but GSD's execute-plan orchestrator owns the inner loop

---

## Assumptions

- supervisor.jsonl events are sufficient signal source (hook_fire, hook_error, state_transition, gate_eval events)
- codex-exec-wrapper.sh already emits rich JSONL with token counts, step counts, elapsed time, and failure reasons — this is consumable
- The execute-plan orchestrator reads task classifications and can accept rerouted tasks (Codex→Claude fallback already exists)
- Task-level adaptation (reroute one task) is more valuable than wave-level adaptation (abort entire wave)
- The main failure patterns are: Codex consistently failing on a file type, context degradation across tasks, test failures indicating wrong approach, and timeout patterns indicating task complexity mismatch

## Open Questions

- Where does the adaptation logic live? In cortex-drive (between GSD dispatch calls)? In a PostToolUse hook during execution? In codex-exec-wrapper.sh itself?
- How does Cortex influence GSD execution without violating the ownership boundary? Can it write signals that GSD reads?
- What early warning signals exist before circuit breaker trips? (1 failure with high token count? Slow task completion? Specific error patterns?)
- Should adaptation be automatic (reroute silently) or advisory (log recommendation, let execute-plan decide)?
- How does this interact with the existing `codex.fallback_on_failure` config in GSD?
- Is mid-wave adaptation even possible with the current execute-plan architecture, or does it only support pre-wave task classification?
- What's the minimum viable adaptation: just "after 1 Codex failure on task type X, reroute remaining type X tasks to Claude"?
