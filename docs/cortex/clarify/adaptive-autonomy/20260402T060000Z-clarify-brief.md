## Idea

Configurable autonomy levels for the Cortex-GSD pipeline so the entire flow (clarify, research, spec, contract, evals, import, plan, execute, verify) can run fully autonomous, gates-only, or supervised, controlled by a shared config that both systems read. The Cortex-to-GSD handoff currently requires redundant HITL steps (new-milestone, discuss-phase) that re-discover context Cortex already produced. Autonomy should be a dial, not a switch.

---

## Goal

A single autonomy configuration controls how much human intervention both Cortex and GSD require, enabling the full pipeline from problem framing through verified execution to run with zero stops (full-auto), approval-only stops (gates-only), or step-by-step stops (supervised).

---

## Non-Goals

- Not replacing GSD's file-level planning — that granularity is what makes execution reliable
- Not merging Cortex and GSD into one system — they remain distinct layers (intelligence vs. workflow)
- Not removing the ability to run Cortex or GSD independently — autonomy config is additive
- Not building a web UI or dashboard for autonomy control — CLI/config-file only
- Not changing the artifact format (specs, contracts, plans) — only changing when/whether humans approve them

---

## Constraints

- Must be backward-compatible: existing Cortex and GSD commands continue to work without autonomy config present (defaults to current supervised behavior)
- Config must work per-project (repo-local) and globally (~/.claude/) with project overriding global
- GSD's existing /gsd:drive and /gsd:autonomous already chain steps — build on that machinery, don't replace it
- Cortex skill files are read-only at runtime (SKILL.md) — gate logic must live in the skill execution path, not in static templates
- Human gate on eval approval for UX/taste dimension is a hardcoded safety constraint (Phase 05 decision) — full-auto must still respect mandatory gates

---

## Assumptions

- The current Cortex artifact chain (clarify, research, spec, contract, evals) produces sufficient context that GSD discuss-phase is redundant when artifacts exist
- GSD plan-phase still adds value (file-level task decomposition) even when Cortex artifacts are complete
- A single config file can express the gate logic for both systems without becoming unwieldy
- The cortex-spec gsd-handoff.md artifact contains enough structure to auto-generate PROJECT.md, ROADMAP.md, and REQUIREMENTS.md without human Q&A
- Users will primarily use 2-3 preset levels rather than fine-tuning individual gates

---

## Open Questions

- Should autonomy level be settable per-invocation (e.g., `/cortex-clarify --auto`) in addition to config, or config-only?
- How does the Cortex-to-GSD bridge command work mechanically — does it call GSD skills programmatically or generate the equivalent artifacts directly?
- Should there be a "dry-run" mode that shows what would happen at full-auto without actually executing?
- What happens when full-auto hits a genuine ambiguity that normally requires human judgment — does it make a choice and log it, or does it escalate despite the autonomy level?
- Should the autonomy config support per-slug overrides (e.g., "this slug is high-risk, use supervised even though default is full-auto")?
