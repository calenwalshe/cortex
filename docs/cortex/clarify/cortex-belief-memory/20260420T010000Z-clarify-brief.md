# Clarify Brief: cortex-belief-memory

**Slug:** cortex-belief-memory
**Timestamp:** 20260420T010000Z
**Status:** draft
**Complexity:** complex

---

## Idea

Wire the SCAPE belief engine (beliefs.db) into the Cortex discovery loop as a dual short-term/long-term memory system. Short-term: each slug's clarify→research→spec cycle accumulates beliefs in a scoped namespace (cortex:{slug}), so research cycle 2 knows what cycle 1 established as stable vs contested, and spec generation reads from the belief state instead of just the dossier text. Long-term: when a slug closes, stable beliefs and lessons promote to the global namespace, so future slugs can query "what do we already know about X" and skip re-covering settled ground. Concrete integration points: (1) auto-ingest Cortex artifacts (clarify briefs, research dossiers, specs) into sources.db + beliefs.db on creation, (2) research agents query vault beliefs before researching to avoid re-covering stable knowledge, (3) spec generation reads stable beliefs as acceptance criteria, contested beliefs as risks, open threads as tasks, (4) /cortex-close promotes durable beliefs to long-term. The belief engine (sources.db, beliefs.db, l3_engine.py, l3_module.py) already exists at ~/memory/vault/scripts/ — this is about wiring it into the Cortex skill pipeline.

---

## Goal

Every Cortex discovery cycle (clarify→research→spec) accumulates typed, provenanced beliefs that persist across session boundaries, so research doesn't re-cover stable ground, specs are generated from the belief state, and knowledge earned during discovery survives slug closure to inform future work.

---

## Non-Goals

- Building a new belief engine (already exists at ~/memory/vault/scripts/)
- Modifying the belief engine schema (beliefs.db, sources.db are stable)
- Replacing the existing Cortex fact extraction system (.cortex/facts.jsonl) — this complements it
- Adding new inference rules beyond the 4 already built (conflict, supersede, stable, lesson)
- Implementing Datalog/Soufflé, TMS/ATMS, or any formal logic engine (deferred to later slug)
- Modifying GSD execution — this is about the discovery loop only
- Building a UI for beliefs (memory.calenwalshe.com dashboard already has a Beliefs tab)

---

## Constraints

- [system-map] All work follows the sequential spine: clarify → research → spec → execute → validate → repair → assure → done
- [system-map] Artifact roots: `docs/cortex/` (human-readable), `.cortex/` (machine state) — both in target repo
- [system-map] Disk is truth — all state lives in repo artifacts, never in chat
- [system-map] File-based only — no database, no external service for core operation (NOTE: beliefs.db is a global vault resource, not per-project — this constraint applies to Cortex state files, not the vault)
- [system-map] Hooks wired to 9 Claude Code events via `.claude/settings.json`
- The vault lives at `~/memory/vault/` and is global — not per-project. Cortex skills must import from there.
- All `claude -p` calls must use `env -u ANTHROPIC_API_KEY` for subscription billing
- Belief extraction via Haiku adds ~1-2s per artifact. Must not block interactive skill execution if avoidable.
- Existing Cortex skills (16 skills, 15 hooks) must continue working unchanged when belief integration is disabled or vault is unavailable

---

## Assumptions

- The belief engine (beliefs.db, sources.db, l3_engine.py, l3_module.py, belief_store.py, source_store.py) is stable and deployed at ~/memory/vault/scripts/
- The vault is always accessible from any project directory via absolute paths
- Haiku extraction of logical forms from Cortex artifacts (clarify briefs, research dossiers) will produce useful claims/decisions/plans/warnings
- The existing namespace column in derived_objects is sufficient for slug-scoped beliefs (no separate database needed)
- Soft-fail is acceptable — if the vault is unavailable, Cortex skills should proceed without belief integration rather than blocking

## Open Questions

- Which Cortex skills need modification to call vault ingest/l3 extract? (cortex-clarify, cortex-research, cortex-spec, cortex-close at minimum)
- How should slug-scoped namespaces work — is the existing `namespace` column on derived_objects sufficient, or do logical_forms also need a namespace/slug column?
- What is the right promotion policy when a slug closes — promote all stable beliefs, or only beliefs that survived the full clarify→spec cycle?
- How should /cortex-research query existing beliefs — inject into the research agent's prompt, or add a pre-research step that writes a "known beliefs" section into the dossier?
- Should belief extraction happen inline (blocking the skill, adding 1-2s latency) or async (post-hook that runs after the skill completes)?
- What TMS-style dependency tracking is needed? If a research finding is retracted in cycle 2, should downstream beliefs auto-retract, or just get flagged?
- How do cross-project belief queries work? The vault is global, but each Cortex project has its own .cortex/ state. Should beliefs carry project provenance?
