# Clarify Brief: repo-consistency-fixes

**Slug:** repo-consistency-fixes
**Timestamp:** 20260405T053000Z
**Status:** draft
**Complexity:** standard

---

## Idea

The Cortex repo has accumulated structural inconsistencies across its documentation, manifest, and implementation. README says 7 commands, CORTEX.md says 8, manifest installs a different 8. CORTEX.md says "Cortex never writes to .planning/" but cortex-bridge writes the entire .planning/ scaffold. Hook count is wrong in docs. Eval gate ordering is ambiguous. These inconsistencies undermine the repo's credibility as a framework and will block autonomous operation.

---

## Goal

Every documentation file, the runtime manifest, and the installer agree on one canonical command surface, hook inventory, and ownership model — verified by a machine-checkable consistency test.

---

## Non-Goals

- Not redesigning the command surface or lifecycle (just making docs match reality)
- Not adding new commands or removing existing ones
- Not changing the eval system (just clarifying the gate ordering)
- Not building the full self-healing docs pipeline (that's a separate slug)
- Not refactoring cortex-bridge (just documenting its .planning/ exception correctly)

---

## Constraints

- Changes must be backward-compatible (no breaking existing installs)
- runtime-manifest.json is the source of truth for installable components
- CORTEX.md is the source of truth for architecture and ownership model
- All changes must be verifiable by a simple script (grep-based consistency check)

---

## Assumptions

- The manifest's current skill list (8 skills including cortex-bridge) reflects intended state
- cortex-experiment is a real command (documented in COMMANDS.md) that should be in the manifest
- The 5 hook files not in the manifest (cortex-distribute.sh/py, cortex-postcompact.sh, cortex-supervisor-log.sh, nlm-refresh.py) are either legacy or supplementary — need to determine which belong in manifest
- The .planning/ exception for cortex-bridge is intentional and correct behavior

---

## Open Questions

- **Command surface:** Should it be 8 commands (README catches up) or 9 (add cortex-bridge as a command)? Or is bridge a skill, not a command?
- **cortex-experiment in manifest:** It's documented in COMMANDS.md and CORTEX.md but NOT in the manifest skills list. Should it be added?
- **Unmaniested hooks:** Which of the 5 hooks not in manifest should be added? Are any legacy/dead?
- **Eval gate ordering:** Should eval plan be required before spec writes contract, or required before contract can close? What's the intended sequencing?
- **.planning/ ownership language:** What's the right way to document the bridge exception without weakening the ownership boundary?

---

## Next Research Steps

1. Determine the canonical command surface by cross-referencing manifest, skills/, docs, and CORTEX.md
2. Audit each unmanifested hook file to determine if it's live, legacy, or supplementary
3. Determine the intended eval gate ordering from the skill implementations
4. Draft the .planning/ ownership language that accounts for the bridge exception
5. Design a consistency check script that can verify all docs match
