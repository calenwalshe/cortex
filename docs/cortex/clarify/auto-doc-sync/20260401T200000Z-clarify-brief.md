## Idea

what doe it look like to build in some auto doc updating systems wehenver we change the code we chagne the docs?

(Clarified: a pre-commit hook that auto-generates documentation updates when SKILL.md files or hook scripts are modified.)

---

## Goal

When a SKILL.md file or hook script is changed, a pre-commit hook invokes an LLM to update the corresponding documentation sections automatically so that docs never drift from implementation without a manual audit.

---

## Non-Goals

- Not generating docs from scratch for brand-new commands or hooks — initial docs are still written manually
- Not syncing docs to external platforms (that is cortex-distribute's responsibility)
- Not replacing human judgment on architectural or design documentation
- Not updating GSD planning files (`.planning/`, `REQUIREMENTS.md`, `ROADMAP.md`)
- Not auto-updating docs outside the Cortex doc surface (`COMMANDS.md`, `HOOKS.md`, `CONTINUITY.md`, `AGENTS.md`)
- Not a linter or doc-style enforcer — only concerned with factual accuracy vs. source files

---

## Constraints

- Must not introduce incorrect documentation — a doc update that contradicts the source file is strictly worse than no update; accuracy is the hard constraint
- Must soft-fail if the LLM API is unavailable — warn the committer but do not block the commit
- LLM call in a pre-commit hook adds latency; must stay under a tolerable threshold (TBD in research) or be made opt-out
- Write scope must be narrow — only `docs/` paths that map directly to the changed source file; no broad rewrites
- Must not modify product code or GSD state as a side effect
- Requires API credentials at commit time — this is a deployment constraint for every developer machine

---

## Assumptions

- The mapping from source file to target doc section is knowable and enumerable: `SKILL.md` → `COMMANDS.md` entry; hook script → `HOOKS.md` entry; state.json schema field additions → `CONTINUITY.md` schema table
- An LLM call (Claude API or Claude Code CLI) can be made synchronously from a git pre-commit hook with acceptable latency for most commits
- The Cortex doc surface (`COMMANDS.md`, `HOOKS.md`, `CONTINUITY.md`, `AGENTS.md`) is the primary target — not arbitrary project documentation
- The hook reads the git diff of the staged change, not the full file, to minimize tokens and scope

---

## Open Questions

- **Source-to-doc mapping:** What is the complete mapping table? Which changes to which source files should trigger updates to which doc sections? Is there a config file or is it hardcoded?
- **Validation:** Does the generated doc update get committed automatically, or staged for human review before the commit proceeds? What happens if the human rejects the suggested update?
- **Architectural change detection:** How does the hook distinguish a minor fix (update a description) from an architectural change (new flag, removed behavior, new state field) that should flag for human review rather than auto-update?
- **Invocation mechanism:** How is the LLM called from a git pre-commit hook? Options: Claude Code CLI (`claude -p`), direct Anthropic API curl, a dedicated Python/shell script using the SDK
- **Failure mode:** If the API call times out or returns an error, does the hook warn-and-allow or block the commit?
- **Scope of update:** Does the hook update only the section directly corresponding to the changed file, or does it also scan for downstream doc dependencies (e.g., a SKILL.md change that should also affect AGENTS.md)?
- **Multi-file commits:** If a commit touches 3 SKILL.md files simultaneously, does the hook make 3 separate LLM calls or one batched call?

---

## Next Research Steps

1. Map the complete source-to-doc dependency graph: which source file changes should trigger which doc section updates — produce a mapping table
2. Survey pre-commit hook patterns that invoke LLM APIs — latency benchmarks, auth approaches, failure mode handling
3. Evaluate invocation mechanisms: `claude -p` (Claude Code CLI headless mode) vs. direct API curl vs. SDK script — compare latency, auth complexity, portability
4. Research validation approaches: auto-commit vs. stage-for-review vs. warn-only — precedents in doc-from-code tools
5. Assess architectural change detection: how to classify a diff as "safe to auto-update" vs. "flag for human review" before writing anything
