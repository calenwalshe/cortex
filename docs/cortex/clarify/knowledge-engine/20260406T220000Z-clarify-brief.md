## Idea

Build Cortex's knowledge engine — the system that makes Cortex smarter over time instead of starting from scratch every session. Two layers: (1) Fact extraction at compaction — decompose session intelligence into atomic typed facts (decisions, preferences, patterns, procedures, lessons) stored in .cortex/facts.jsonl. (2) Semantic retrieval — embed facts, retrieve only what's relevant to the current task instead of loading all handoff files into context. Together these replace the current "dump everything" approach with targeted knowledge retrieval — 14x token savings per the semantic-retrieval benchmarks.

Prior work exists: memory-extraction slug (researched, architecture designed, not built), semantic-retrieval slug (fully specced with live benchmarks, contract drafted, archived without execution). This slug combines both into a single build, using the prior research as the foundation.

Source: autonomous-builder-ideas.md items E3 (semantic memory) and E4 (procedural/lesson memory).

---

## Goal

After compaction or session restart, Cortex retrieves only the facts relevant to the current slug and task — not entire handoff files — so that context is used for reasoning rather than wasted on stale information, and lessons learned in prior slugs inform decisions in future slugs.

---

## Non-Goals

- [owner-intent] No code without contract.
- [owner-intent] Disk is truth.
- Not building E5 (slow consolidation / parametric path) — that's future research
- Not building graph memory (GraphRAG) — vanilla vector retrieval is sufficient for current scale (<10K facts)
- Not building adversarial memory security (trust-aware retrieval, A-MemGuard) — premature until the base system works
- Not replacing the existing continuity system (current-state.md, next-prompt.md, decisions.md) — the knowledge engine supplements it, doesn't replace it
- Not building a memory UI or interactive memory browser
- Not changing how /cortex-status works — it continues to read handoff files. The knowledge engine is an additional input, not a replacement.

---

## Constraints

- [owner-intent] Validators must run.
- [owner-intent] Cortex will never require a database, external service, or network dependency for core operation. It is a file-based system. **Exception:** ollama is a local service, not external. Graceful degradation required when ollama is unavailable — system must work without embeddings (falls back to loading full handoff files).
- PostCompact hooks must complete in <5 seconds (blocks session)
- No LLM calls in hooks — fact extraction must be pattern-based
- Embedding must be async (non-blocking) — run after postcompact, not during it
- Must work with the existing .cortex/ directory structure
- Retrieval latency must be <100ms (benchmarked at 77ms with pre-computed numpy)
- Must be backward compatible — projects without facts.jsonl or embeddings continue to work unchanged

---

## Assumptions

- ollama with nomic-embed-text is available on the development machine (verified in prior benchmarks)
- The postcompact hook can be enhanced to capture richer data (decisions.md, STATE.md, CONTEXT.md, git log) without exceeding the 5s budget
- JSONL append-only format is sufficient for fact storage at current scale (<100 facts per milestone)
- 768-dimensional embeddings via nomic-embed-text provide sufficient semantic resolution
- numpy .npy files are adequate for vector storage at <10K facts (no need for FAISS/ANN)
- The two-phase architecture (embed at compaction, retrieve at query) resolves the cold-start timing constraint
- Prior benchmark data (77ms retrieval, 2.4s embedding for 53 facts) is still valid

## Open Questions

- Should fact extraction run in the enhanced postcompact hook (Node.js, sync, <5s) or as a separate async script triggered after postcompact?
- How does the knowledge engine interact with Claude Code's built-in auto-memory system (~/.claude/projects/*/memory/)? Complementary or overlapping?
- Should cortex-drive read retrieved facts at Phase 1 initialization, or should individual skills (research, spec, review) query facts on demand?
- What's the right top-k for retrieval? Prior spec said configurable, default 10. Is that enough context without being too much noise?
- Should facts have confidence scores? (High confidence: explicit decision. Low confidence: inferred pattern.)
- How do we handle fact contradiction? (Fact A from slug-1 says "prefer X", fact B from slug-5 says "prefer Y".)
- Should there be a /cortex-remember command for explicit fact capture outside of compaction?
