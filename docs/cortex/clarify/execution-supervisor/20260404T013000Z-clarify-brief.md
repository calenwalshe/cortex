# Clarify Brief: execution-supervisor

**Slug:** execution-supervisor
**Timestamp:** 20260404T013000Z
**Status:** draft
**Complexity:** complex

---

## Idea

This system got mighty complex and I need some kind of supervisor to observe and maintain its coherence and see that things are done according to plan. Over time I can observe and look and if things are not going well we've got logs and explanations.

---

## Goal

A supervision layer that continuously observes Cortex operations — hooks firing, state transitions, skill invocations, contract progress — and maintains a structured log that a human can review at any time to answer: "Is the system working correctly? Are things happening according to plan? Where is it drifting?"

---

## Non-Goals

- Not an auto-repair system (observes and reports, does not fix)
- Not a real-time dashboard or UI (file-based logs, reviewed on demand)
- Not replacing existing state files (supplements them with observability)
- Not monitoring system resources (CPU, memory, disk) — only Cortex-level behavior
- Not an alerting system (no notifications — the human checks when they want to)

---

## Constraints

- Must not add latency to existing hooks (observation must be async or append-only)
- Logs must be human-readable without tooling (plain text or markdown, not binary)
- Must work across sessions (logs persist, not cleared on session start)
- Must not require additional dependencies (use what's available: bash, node, python, jq)
- The supervision surface is the existing 13 hooks + 12 skills + 3 scripts — no new entry points to monitor
- Storage must be bounded (rotate or cap log size — can't grow unboundedly)

---

## Assumptions

- Hooks already fire at the right times (SessionStart, PreCompact, PostCompact, etc.) — the supervisor piggybacks on these events
- state.json transitions (mode changes, gate updates) are the authoritative record of progress
- The human reviews logs infrequently (daily or weekly), not in real-time
- A structured event log (JSONL) is sufficient for both human reading and future analysis
- The main failure modes are: hooks silently failing, state drift (inconsistent files), stale artifacts, and contract violations (writes outside roots)

---

## Open Questions

- **What exactly to observe:** Which events matter? Every hook fire? Only state transitions? Errors only? What's the signal-to-noise sweet spot?
- **Log format:** JSONL with structured events? Markdown append log? Both?
- **Where to store:** `.cortex/supervisor.jsonl`? `docs/cortex/supervisor/`? Separate from operational state?
- **Coherence checks:** What specific coherence properties should the supervisor verify? (e.g., state.json matches current-state.md, artifacts listed in state.json exist on disk, gates are monotonically advancing)
- **Review UX:** How does the human consume the log? `cortex-supervisor report` command? Just read the file? A summary skill?
- **Scope of "according to plan":** Does "plan" mean the contract's done criteria? The spec's sequencing? The GSD plan? What's the reference for "on track"?

---

## Next Research Steps

1. Catalog the failure modes — what has actually gone wrong in past sessions? Stale state, silent hook failures, inconsistent files?
2. Design the event taxonomy — what events are worth logging (hook fires, state transitions, errors, validator results)
3. Evaluate where to inject observation — existing hooks (add logging), new wrapper, or PostToolUse hook
4. Design coherence checks — specific properties to verify (state consistency, artifact existence, gate monotonicity)
5. Design the review interface — how does the human ask "is everything OK?" and get a useful answer
6. Evaluate storage and rotation — JSONL with size cap, or time-windowed logs
