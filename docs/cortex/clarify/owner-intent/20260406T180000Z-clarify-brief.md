## Idea

Add a durable "why" layer to Cortex: an owner-intent.md artifact that captures outcomes, success metrics, non-negotiables, tradeoff preferences, and kill criteria — the stable intent that survives across slugs. Paired with a preferences.json that captures structured owner preferences (scope, strength, confidence, source, last_confirmed). Together these give cortex-drive and cortex-clarify the ability to rank work by alignment to stated objectives, make tradeoff calls (speed vs thoroughness, token cost vs coverage), and kill slugs that drift from mission. Currently Cortex tracks execution state but has zero awareness of why it's building anything.

Source: autonomous-builder-ideas.md items D1 (owner-intent.md) and D3 (preferences.json).

---

## Goal

cortex-drive can autonomously rank, prioritize, and kill work based on explicit owner intent — not just execution state — so that unattended runs align with the owner's actual objectives and preferences.

---

## Non-Goals

- Not building the full objective hierarchy (D2: mission → objective → initiative → slug). That's a future layer on top of intent.
- Not building /cortex-sync reconciliation command (D4). That consumes intent but is a separate slug.
- Not building the cortex-goal-steward agent (D5). That's a future ownership model.
- Not changing how slugs are created or how the pipeline works — just adding an input signal that existing commands can read.
- Not building a UI or interactive preference-setting workflow — files are edited directly.

---

## Constraints

- owner-intent.md must be a single human-readable markdown file, not a database or JSON blob
- preferences.json must be machine-readable (JSON) so cortex-drive can parse tradeoff preferences programmatically
- Both artifacts live in the target project repo (not ~/.cortex/) — they're project-scoped, not global
- Must be backward compatible — projects without these files continue to work unchanged (commands treat missing intent as "no constraint")
- Must not add runtime dependencies — consumed via file reads in SKILL.md instructions
- Intent artifacts must survive /cortex-close (they're not per-slug, they're per-project)

---

## Assumptions

- cortex-drive is the primary consumer — it reads intent to rank stash items (row 1) and make tradeoff decisions
- cortex-clarify could use intent to auto-populate non-goals and constraints from the owner's standing preferences
- The necessity gate (already built) could reference intent to determine if a slug aligns with stated objectives
- preferences.json is structured enough for programmatic reads but simple enough to hand-edit
- One owner-intent.md per project is sufficient (not per-slug, not per-milestone)
- Preferences have a decay/staleness model — old preferences should be re-confirmed periodically

## Open Questions

- Where do these files live? `.cortex/owner-intent.md` + `.cortex/preferences.json`? Or `docs/cortex/intent/`? The .cortex/ directory is gitignored in some setups.
- Should owner-intent.md have a structured schema (YAML frontmatter + markdown sections) or be freeform?
- How does cortex-drive use preferences for ranking? Weighted scoring against stash items? Or a simpler heuristic (filter by alignment, then rank by leverage)?
- Should preferences have expiry dates? ("Prefer token efficiency" may be a temporary constraint during a cost-sensitive period.)
- How do we bootstrap intent? Is there a `/cortex-intent` command, or is it manually authored once?
- Should cortex-clarify auto-inject owner non-negotiables into every clarify brief's Constraints section?
- What's the interaction between owner-intent.md and the existing CLAUDE.md project instructions? Overlap? Complementary?
