# Clarify Brief: human-reports

**Slug:** human-reports
**Timestamp:** 20260406T210000Z
**Status:** draft
**Complexity:** standard

---

## Idea

The reports and HITL gate outputs from Cortex are written in implementation language (test counts, file paths, token dimensions, API costs) rather than decision language (what changed, what it means, what to do next, what the risks are). The human at a HITL gate needs to make a go/no-go decision, but the output reads like a git commit message, not a briefing. The reporting format should be configurable — an executive summary for the project owner, a technical detail view for the implementer, and the raw artifact data for audit.

---

## Goal

Every HITL gate output (research complete, spec ready, build done, verification result) includes a human-readable summary section that answers: what was done, what it means, what changed for you, what the risks are, and what decision you need to make — written in plain language with no implementation jargon unless the audience profile requests it.

---

## Non-Goals

- Not changing the underlying artifact format (dossiers, specs, contracts stay technical)
- Not removing technical detail (it lives in the artifact, just not in the HITL summary)
- Not building a dashboard or UI (still terminal output)
- Not changing commit messages (those serve git audit, different audience)
- Not auto-generating reports for every mode transition (only at HITL gates where a human is present)

---

## Constraints

- Must be backward-compatible — existing HITL gates still work without configuration
- The summary must be derivable from existing artifacts (no new data collection)
- Must be fast — no API calls for report generation (LLM reasoning within the session is fine)
- Audience profiles must be stored as a simple config, not a complex preference system
- The default profile should be "project owner" (plain language), not "implementer" (technical)

---

## Assumptions

- There are 3 useful audience profiles: owner (plain language, decision-focused), implementer (technical detail, file paths), and auditor (full artifact dump with evidence)
- The HITL gate already has all the information needed — it just presents it wrong
- A structured template per gate type (research, spec, build, verify) can standardize the output
- The summary is generated by the LLM in-session, not by a script — it needs judgment about what matters

---

## Open Questions

- **Where does the audience profile live?** `.cortex/autonomy.json`? A new config file? An environment variable? A flag on `/cortex-drive`?
- **What are the exact sections per gate type?** Research HITL needs different sections than build-complete HITL. What's the template for each?
- **How does this interact with cortex-drive?** Drive loop hits a HITL gate → generates summary → presents to human. Does the summary format change what the drive loop does?
- **Should the summary be written to a file?** Or is terminal output enough? A file would be useful for async review (human comes back later).
- **What does "plain language" actually mean here?** Need concrete examples of the same information written for owner vs implementer vs auditor.

---

## Next Research Steps

1. Take 3 actual HITL outputs from this session and rewrite them in owner/implementer/auditor styles — establish the concrete difference
2. Design templates per gate type (research-complete, spec-ready, build-done, verify-result)
3. Research how other tools handle audience-specific reporting (Jira, Linear, GitHub PR summaries)
4. Design the audience profile config format and where it lives
5. Prototype a template that transforms a research dossier summary into an owner-facing HITL output
