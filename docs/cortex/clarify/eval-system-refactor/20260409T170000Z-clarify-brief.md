## Idea

Evaluate whether the Cortex eval system (cortex-eval-designer, eval proposals, eval artifacts) is optimally designed given the current system architecture, or whether it should be refactored. Looking at: the eval-designer agent, eval artifact structure, how evals integrate with the rest of the pipeline (specs, contracts, execution), and whether the current design serves its purpose well.

---

## Goal

Determine whether the eval system's current design maximizes the "honest quality signal" objective from owner-intent — and if not, identify specific structural changes that would improve eval accuracy, reduce ceremony, and tighten pipeline integration.

---

## Non-Goals

- Not redesigning the entire Cortex pipeline — only the eval subsystem
- Not building a new eval execution engine or test runner
- Not changing the 8-dimension candidate matrix itself (functional, regression, integration, safety, performance, resilience, style, UX/taste)
- Not adding external eval infrastructure (databases, CI services, cloud-based eval runners)
- Not changing the contract or spec format beyond eval-related fields

---

## Constraints

- [owner-intent] No sycophantic evals. Eval rubrics must test for actual correctness, not surface compliance. A passing rubric score on broken code is worse than a failing score on working code.
- [owner-intent] Validators must run. No slug closes without validators passing.
- [owner-intent] Disk is truth. All state lives in repo artifacts.
- [owner-intent] Simplicity > Generality. Solve the concrete case well before abstracting.
- [owner-intent] False positive rate on validators must be <10%.
- [owner-intent] Kill criterion: if validators consistently produce false positives (>25% rate over 10 slugs), the eval system is unreliable.
- Must remain file-based — no external services or databases
- Eval artifacts must remain human-readable markdown
- Must not break existing eval artifacts already on disk (10 slugs with proposals/plans)

---

## Assumptions

- The 8-dimension candidate matrix is the right set of eval dimensions (this brief is about structure and integration, not the dimension taxonomy)
- The current eval-proposal → eval-plan → results artifact chain is the intended lifecycle (question is whether it's optimal)
- Eval proposals are currently produced by the cortex-eval-designer agent and triggered via `/cortex-research --phase evals`
- The eval-plan is a human-approved subset of the eval-proposal (approval gate exists but auto-skips when no dimensions require it)
- Eval results are written manually during execution — there is no automated eval runner
- The proposal-to-plan step appears to be largely duplicative (plan copies approved dimensions from proposal with minimal transformation)

---

## Open Questions

- Is the eval-proposal → eval-plan two-step split justified, or is the plan just a rubber-stamp copy of the proposal? Could they be collapsed into a single artifact?
- Are eval results actually being verified against the rubrics, or are they self-reported by the executing agent (potential sycophancy vector)?
- The eval-designer is a separate agent — does agent isolation add value here, or does it create unnecessary context loss between spec/contract and eval design?
- How do eval results feed back into the repair loop? Is the repair trigger well-defined or ad-hoc?
- Is eval-status.md (the composite scoring template) actually being produced and used, or is it dead artifact structure?
- Are the "run instructions" in eval-plan.md actually executable by the system, or are they advisory text that gets ignored?
- Should evals be executable (scripts/commands) rather than descriptive (markdown prose that a human or agent interprets)?
- Does the current design satisfy the <10% false positive rate from owner-intent? What evidence exists?

---

## Next Research Steps

1. Audit all 10 eval-proposal/eval-plan pairs to measure content duplication between proposal and plan artifacts — quantify whether the two-step split adds value
2. Trace the eval execution path: how does the system actually run evals during execute mode? Is it the validator-trigger hook, manual agent invocation, or something else?
3. Examine the repair loop integration: when evals fail, what exactly triggers repair and how does the system track repair → re-eval cycles?
4. Assess eval result honesty: are results independently verified or self-reported by the same agent that wrote the code?
5. Check whether eval-status.md (composite scoring) is produced for any slug — if not, determine whether it's aspirational or dead
6. Compare the eval system to the owner-intent kill criteria and success metrics — does current design have the instrumentation to even measure false positive rates?
7. Identify concrete refactoring candidates: artifact consolidation, executable evals, tighter hook integration, anti-sycophancy measures
