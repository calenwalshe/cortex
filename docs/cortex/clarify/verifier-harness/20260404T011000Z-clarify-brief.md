# Clarify Brief: verifier-harness

**Slug:** verifier-harness
**Timestamp:** 20260404T011000Z
**Status:** draft
**Complexity:** standard

---

## Idea

Reuse the verifier harness across multiple phases: instead of each phase defining its own validator scripts, a shared harness reads a `validators.json` manifest and dispatches to per-task checker functions. This would eliminate duplicated bash validation logic in every plan and make the `gate-check` skill composable with any phase's deliverables without per-phase wiring.

---

## Goal

A single `cortex-verify.py run <slug>` command reads a `validators.json` manifest from the contract directory, executes all validators (both `[external]` and `[judgment]`), and produces a structured pass/fail report — so that contract validation is declarative and reusable instead of ad-hoc bash per contract.

---

## Non-Goals

- Not replacing the contract format (validators still defined in contract markdown as the source of truth)
- Not automating contract closure (verification is a check, not a state transition)
- Not building a CI/CD pipeline or pre-commit hook system
- Not modifying GSD's gate-check skill (this is a Cortex-side tool that gate-check can optionally call)
- Not handling non-contract validation (this is scoped to Cortex contract validators only)

---

## Constraints

- Must parse existing contract markdown to extract validators — no format migration required
- `[external]` validators are shell commands that must return exit code 0 to pass
- `[judgment]` validators delegate to `cortex-judge.py` (already built) — the harness orchestrates, not duplicates
- Must work with zero config beyond pointing at a slug — auto-discovers contract and validators
- Output must be both human-readable (terminal) and machine-readable (JSON) for downstream consumption
- Must not break existing manual validator workflow — the harness is additive

---

## Assumptions

- All contracts follow the existing `## Validators` section format with `- [ ] [external]` and `- [ ] [judgment]` prefixes
- The contract markdown format is stable enough to parse reliably with regex
- `cortex-judge.py` handles all `[judgment]` validator scoring (no need to duplicate that logic)
- A `validators.json` manifest is generated from the contract at verify time, not manually authored
- The number of validators per contract is small enough (<20) that sequential execution is fine

---

## Open Questions

- **Manifest format:** Should `validators.json` be auto-generated from contract markdown on each run, or pre-generated and cached? Auto-gen is simpler but parsing on every run adds fragility.
- **Parallel execution:** Some `[external]` validators are independent and could run in parallel. Worth the complexity for <20 validators?
- **Timeout handling:** What timeout per validator? Global timeout? Per-type timeout ([external] vs [judgment])?
- **Report format:** Markdown report like judge-report.md? JSON only? Both? Where does it live?
- **Integration with cortex-judge:** Should the harness call `cortex-judge.py` as a subprocess, or import its functions directly?
- **Partial results:** If one validator fails, do we continue running the rest or stop early?

---

## Next Research Steps

1. Audit all existing contracts for validator patterns — catalog the formats, count validators per contract, identify edge cases
2. Prototype contract markdown parser — extract `[external]` and `[judgment]` validators with regex
3. Design manifest format — evaluate auto-gen from contract vs cached JSON vs hybrid
4. Design report format — evaluate markdown, JSON, or combined output
5. Evaluate integration with cortex-judge.py — subprocess vs import vs shared library
6. Design timeout and error handling strategy
