## Idea

Make the cortex-bridge step optional for autonomous runs. Currently, cortex-drive row 5 dispatches /cortex-bridge when the spec is approved, and row 8 dispatches GSD execution when .planning/ exists. In `full-auto` mode this already works seamlessly (contract_approval gate is false → auto-approve → auto-bridge → auto-execute). In `gates-only` mode, contract_approval is true so the human must approve before bridge fires.

The ask is: add a separate `auto_bridge` gate so that `gates-only` users can allow the bridge step to proceed automatically after contract approval, without jumping all the way to `full-auto`. This is a fine-grained autonomy control — "I want to approve the contract, but once approved, bridge and execute should flow without me."

Currently the bridge→execute transition has no independent gate. If contract_approval passes (human approves), bridge fires immediately (row 5) and execution starts on the next loop iteration (row 8). The gap is that in `gates-only` mode, some users might want to approve the contract but NOT auto-bridge (they want to review the .planning/ scaffold before execution starts). This slug adds the optionality.

---

## Goal

cortex-drive can optionally auto-bridge after contract approval in gates-only mode, controlled by a new `auto_bridge` gate — so users who trust the bridge output can get seamless spec→execute flow without switching to full-auto.

---

## Non-Goals

- [owner-intent] No code without contract.
- [owner-intent] GSD owns execution. Cortex does not write to .planning/ except via /cortex-bridge.
- Not changing how /cortex-bridge itself works — it remains the same skill
- Not adding auto-execution control — that's separate (GSD's own autonomy)
- Not changing the `full-auto` preset behavior (already works)
- Not changing the `supervised` preset (always requires human at every step)

---

## Constraints

- [owner-intent] Validators must run.
- Must be backward compatible — existing autonomy configs without `auto_bridge` gate default to current behavior (`true` = human decides)
- The gate should follow the existing 4-layer resolution pattern (invocation > project > global > preset)
- Must not be a mandatory gate — it's user-configurable, not forced

---

## Assumptions

- The resolve-autonomy.js 4-layer resolution system can accommodate a new gate without schema changes
- The current drive decision table (rows 5-8) handles the bridge→execute transition correctly — this slug only adds a gate check, not new rows
- Most `gates-only` users will want `auto_bridge: false` (default to current behavior) — the opt-in is for power users who've validated their bridge output
