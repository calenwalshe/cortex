# Clarify Brief: necessity-gate

**Slug:** necessity-gate
**Timestamp:** 20260405T060000Z
**Status:** draft
**Complexity:** standard

---

## Idea

Add a mandatory necessity attack gate before /cortex-spec. The cortex-critic should try to prove one of four things: this should not be built, this should be smaller, this can reuse existing capability, or this needs more evidence. Returns build/narrow/defer/reject verdict. This is the gate that would have killed the verifier harness before we wasted time building it — the critic should catch "solutions looking for problems" before they reach spec.

---

## Goal

Before /cortex-spec writes a spec and contract, a necessity check runs that reads the clarify brief and research dossier and returns one of four verdicts: BUILD (proceed), NARROW (scope is too big, reduce it), DEFER (not enough evidence, needs more research), or REJECT (this solves a problem that doesn't exist). If the verdict is not BUILD, /cortex-spec blocks with a clear explanation.

---

## Non-Goals

- Not replacing the existing cortex-critic (that reviews specs/contracts after they're written — different job)
- Not adding a human approval step (the necessity check is automated, not interactive)
- Not blocking /cortex-spec permanently (the verdict can be overridden with a flag)
- Not changing the clarify or research phases (this consumes their outputs, doesn't modify them)
- Not scoring every possible dimension (this is specifically about "should this exist?", not quality)

---

## Constraints

- Must run as part of /cortex-spec's Phase 1 (prerequisite validation), not as a separate command
- Must be autonomy-gate-controllable (can be disabled in full-auto preset)
- Must use Claude's own reasoning (not an external API call) — this is a judgment gate, not a mechanical check
- Must produce a structured verdict that can be logged in decisions.md
- Must be fast — adds judgment latency but not external service latency
- Must not block when overridden (`--gate necessity=false`)

---

## Assumptions

- The clarify brief and research dossier contain enough information to assess necessity (they should — that's what they're for)
- Four verdicts (build/narrow/defer/reject) cover the decision space adequately
- The existing cortex-critic agent can be extended with a necessity lens (or a new prompt can be used inline)
- The verifier-harness case is representative: we built something, realized it solved no real problem, and killed it — this pattern is worth preventing

---

## Open Questions

- **Implementation approach:** Should this be a cortex-critic agent call, an inline LLM judgment in /cortex-spec, or a new lightweight script? The critic agent is read-only and currently doesn't return verdicts — extending it vs. building a focused check.
- **Evidence for verdicts:** What specific evidence should trigger NARROW, DEFER, or REJECT? Need concrete heuristics, not just "use judgment."
- **Override UX:** When the gate blocks, what does the user see? How do they override? Just `--gate necessity=false`?
- **Logging:** Where does the verdict get logged? decisions.md? A new artifact?
- **False positive risk:** How do we prevent the gate from being too aggressive and blocking legitimate work? The verifier-harness case was obvious — but would this gate also block things that are actually worth building?

---

## Next Research Steps

1. Analyze past slugs: which ones should have been caught? Which ones were correctly built? Establish ground truth for the gate's decision criteria.
2. Design the verdict heuristics — specific patterns that trigger NARROW/DEFER/REJECT vs BUILD
3. Prototype the necessity check as an inline prompt — test it against the verifier-harness clarify brief and research dossier to see if it correctly returns REJECT
4. Test against semantic-retrieval and llm-judge-calibration to verify it correctly returns BUILD
5. Decide on implementation approach (critic agent extension vs inline prompt vs script)
6. Design the gate integration into /cortex-spec Phase 1
