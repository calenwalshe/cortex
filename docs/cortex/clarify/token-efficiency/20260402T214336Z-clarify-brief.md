## Idea

Token tracking and token efficiency methodologies for the Cortex system. Also exploring a Codex handoff mode — passing context and instructions to Codex for autonomous execution and/or verification, treating Codex as a cheaper execution layer for suitable tasks. Codex CLI is available and enabled.

<!-- Verbatim input: the exact idea, problem, or feature as stated by the human -->

---

## Goal

Cortex automatically tracks token consumption across all orchestration activity, applies efficiency strategies to reduce waste, and intelligently offloads suitable tasks to Codex — producing stored telemetry data suitable for infrastructure planning and usage analysis. As a prerequisite, cortex-research is refactored to use power-search as its backend, unifying provider routing and gaining cost tracking for free.

## Non-Goals

- No budgets, caps, or spend limits — this is observability, not enforcement
- No real-time dashboards or UI — data is stored for offline analysis
- No inline per-command cost display — telemetry is background/silent
- No integration with RTK or other external token-saving tools
- No billing or cost-conversion calculations (raw token counts only)
- Codex handoff is for execution and verification — not for planning, clarify, or spec phases (those require interactive context)
- Not replacing the existing /codex-review or /gsd-codex-verify skills — extending the pattern into a general-purpose handoff mechanism

## Constraints

- Must not add noticeable latency to Cortex commands — tracking is lightweight/async
- Must work within the existing Cortex skill/hook architecture — no new runtime dependencies
- Storage format must be simple and queryable (JSON lines, SQLite, or CSV — not a custom binary)
- Efficiency strategies must be transparent — no silent quality degradation (e.g., don't secretly route to haiku when the user expects opus)
- Must not require API key access or billing API — derive token data from what's observable locally

## Prerequisites

- **Refactor cortex-research to use power-search as backend** — cortex-research currently makes raw API calls (curl to Perplexity, direct Tavily client, manual Jina fetches). Power-search already has unified routing, provider fallback chains, and SQLite cost tracking. Wiring it in gives: (1) better research quality via smarter routing, (2) cost data for free, (3) ~80 fewer lines of raw API calls, (4) YouTube/crawling support through the unified interface.

## Assumptions

- Token counts can be approximated or extracted from Claude Code session data, tool call patterns, and agent spawn metadata
- The Cortex hook/skill system provides enough interception points to instrument without modifying upstream Claude Code
- Efficiency gains come from four levers: smarter model selection, context window management, reducing redundant agent spawns, and Codex offloading for suitable tasks
- Local file storage is sufficient for the data volumes involved (no external database needed)
- Power-search's SQLite cost database can serve as the foundation for external API cost tracking (extending it to cover Claude token usage is incremental)
- Codex CLI (`codex exec --full-auto`) is installed and available for autonomous task execution
- Codex is best suited for well-scoped, self-contained tasks with clear acceptance criteria (GSD executor tasks, verification passes, test writing)
- The existing /codex-review and /gsd-codex-verify skills prove the handoff pattern works — extending it to execution is feasible

## Open Questions

- What token data is actually observable from within a Claude Code session? (input tokens, output tokens, cache hits, tool call overhead — what's exposed?)
- Where do the biggest token sinks live in current Cortex workflows? (subagent spawns, research phases, large file reads?)
- What storage format best supports the "analyze later" use case — extend power-search's existing SQLite, or a separate store?
- Can Cortex hooks intercept agent spawns and tool calls at a level where token estimation is feasible?
- What efficiency strategies can be automated without user-visible quality loss? (e.g., model routing for simple tasks, deduplicating repeated file reads, smarter context pruning)
- How much of cortex-research's current API surface maps cleanly onto power-search intents? Are there research patterns that don't fit the search() interface?
- What's the right boundary for Codex handoff? Which GSD task types are safe to offload vs which need Claude's interactive context?
- How should handoff context be structured? (full plan + task description, or minimal scoped prompt?)
- Should Codex verification replace or supplement the existing /gsd-codex-verify flow?
- What's the failure/retry model when Codex times out or produces incomplete work?
- Can Codex execution token costs be tracked in the same ledger as Claude usage for unified analysis?

7. Analyze existing Codex integration (/codex-review, /gsd-codex-verify) to identify the handoff pattern and where it can be extended to autonomous execution
8. Research Codex exec capabilities — what context format produces the best results, timeout behavior, how to capture and validate output
9. Determine which GSD task types are Codex-safe (self-contained, clear criteria) vs Claude-required (interactive context, multi-file reasoning)
