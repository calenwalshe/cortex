## Idea

Implement Pattern Harvest Phases 1-3 as a single batch: (1) Context Capacity Gate — mandatory context_capacity gate in resolve-autonomy.js and PostToolUse hook that monitors context window usage, warning at 75-85% and blocking at >85%. (2) Repair Budget + Convergence Detector — add repair_budget and cooldown fields to contract template, add convergence detector to cortex-review that identifies 3+ repeated similar failures and generates convergence-stall.md. (3) Circuit Breaker + Iteration Budget — add circuit breaker logic and iteration budget (max_steps) to codex-exec-wrapper.sh so Codex dispatch stops after 3 consecutive failures and runaway tasks are killed. These are the safety net prerequisites for trusting autonomous operation via /cortex-drive. Sources: Praetorian (context gate, failed approaches), Swarm-IOSM (repair budget), OpenHands (iteration budget), Ralph Loop (convergence detection). Existing research at docs/cortex/research/pattern-harvest/concept-20260403T213444Z.md and spec at docs/cortex/specs/pattern-harvest/spec.md.

---

## Goal

Autonomous Cortex runs (/cortex-drive) self-terminate safely when context degrades, repairs loop without converging, or Codex tasks fail repeatedly — eliminating the three highest-risk failure modes for unattended operation.

---

## Non-Goals

- Not implementing Phases 4-8 of Pattern Harvest (repair quality, intelligence depth) — those come later
- Not adding semantic memory, LLM routing, or other Tier 4 advanced patterns
- Not redesigning the repair loop or contract lifecycle — just adding budget/convergence guardrails to the existing flow
- Not changing how /cortex-drive makes decisions — just giving it new signals to act on
- Not building a dashboard or UI for monitoring — these are programmatic gates and logs

---

## Constraints

- All changes must fit within the existing SKILL.md instruction architecture — no new runtime dependencies
- Context capacity detection must work within Claude Code's hook system (PostToolUse hook has access to conversation metadata)
- Convergence detector must work with existing contract/review artifact format — no schema breaks
- Circuit breaker state must survive across Codex task invocations within a single wave (codex-exec-wrapper.sh manages this)
- Repair budget fields must be backward-compatible — existing contracts without these fields should work unchanged
- No changes to the sequential spine or mode transitions

## Assumptions

- Claude Code PostToolUse hooks can access context window usage percentage (or a proxy for it) — needs verification
- codex-exec-wrapper.sh maintains state across task invocations within a wave (consecutive failure tracking is feasible)
- The existing contract template at templates/cortex/contract.md is the single source for contract structure
- cortex-review SKILL.md is the right place for convergence detection logic (it already evaluates repair recommendations)
- resolve-autonomy.js is the right place for the context_capacity gate (it already manages all other gates)
- Three consecutive failures is the right threshold for the circuit breaker (sourced from multi-agent failure playbooks)
- 80% similarity threshold for convergence detection is a reasonable starting point (sourced from Praetorian/Ralph Loop)

## Open Questions

- How does a PostToolUse hook detect context window usage in Claude Code? Is there an environment variable, API field, or must we estimate from token counts?
- Should the context capacity gate produce a hard block (refuse to proceed) or a strong warning with an override flag?
- For convergence detection: what constitutes "similar" failures? Exact string match on failure messages, or fuzzy comparison of failure signatures?
- Should repair_budget be per-slug (total repairs across all contracts) or per-contract (max repair iterations of one contract)?
- Where does circuit breaker state persist between Codex task invocations — environment variable, temp file, or .cortex/ artifact?
- Should the iteration budget (max_steps) be configurable per-task in the contract, or a global default in codex-exec-wrapper.sh?
- What happens when a budget/breaker fires mid-wave: kill only the current task, or abort the entire remaining wave?
