# Clarify Brief: policy-loop

**Slug:** policy-loop
**Timestamp:** 20260405T070000Z
**Status:** draft
**Complexity:** complex

---

## Idea

Outer policy loop — an orchestration layer that reads Cortex state (current-state.md, state.json, active contract, eval-status) and decides the next action automatically. Today the human decides "run /cortex-research" or "run /cortex-spec" — this replaces that with a controller that follows the lifecycle spine (clarify → research → spec → bridge → execute → validate → repair → done) and makes adaptive decisions: which research tracks to run, when to escalate depth, when to cross the GSD handoff seam, when to stop and ask the human. This is the brain that turns Cortex from a supervised workflow into a 10-hour unattended builder.

---

## Goal

A single command (`/cortex-auto` or `cortex-drive.py`) that takes a clarify brief (or a raw idea) and autonomously drives it through the entire lifecycle — clarify → research → spec → bridge → execute → validate → repair → done — making adaptive decisions at each transition, respecting autonomy gates, and stopping only when a mandatory gate requires human input or the work is complete.

---

## Non-Goals

- Not replacing individual commands (clarify, research, spec still work standalone)
- Not building a daemon or background service (runs in the current Claude session)
- Not making decisions the human should make (mandatory gates like ux_taste_eval and human_action remain HITL)
- Not handling multiple slugs concurrently (one slug at a time through the spine)
- Not replacing GSD's execution engine (Cortex intelligence drives decisions; GSD still executes)
- Not building a scheduler or cron system (this is an in-session controller, not a detached agent)

---

## Constraints

- Must respect all autonomy gates — mandatory gates always stop for human input
- Must run within a single Claude Code session (no detached processes)
- Must be resumable after compaction or /clear (reads state from files, not memory)
- Must log every decision to decisions.md (full audit trail of what it chose and why)
- Must stop gracefully when budget/context limits are approached
- Must not modify the existing skill implementations — the policy loop calls them, doesn't replace them
- The loop is the controller; skills are the workers. Separation of concerns.

---

## Assumptions

- The lifecycle spine (clarify → research → spec → execute → validate → repair → done) is the correct default sequence for most work
- state.json and current-state.md provide enough information to determine the next action
- The clarify brief's open questions and research steps provide enough signal to decide which research tracks to run
- The existing autonomy gate system (supervised/gates-only/full-auto) is the right mechanism for controlling how much the loop does vs. asks
- A single session has enough context window to complete the loop for most slugs (compaction + resume handles the rest)
- The necessity gate (just built) provides the "should this exist?" check before spec — the loop trusts that gate

---

## Open Questions

- **Decision model:** Is the next-action decision a simple state machine (mode → next command), or does it need LLM reasoning? The spine is sequential, but research track selection and depth escalation need judgment.
- **Research strategy:** How does the loop decide which research tracks to run? All three (concept/implementation/evals)? Only concept first, then escalate? Based on what signal?
- **Depth escalation:** When does the loop choose quick vs standard vs deep research? What triggers escalation?
- **GSD handoff seam:** The loop needs to cross from Cortex spec to GSD execution. How? Call /cortex-bridge directly? Call /gsd:execute-phase? What's the minimal safe bridge?
- **Stopping conditions:** Beyond mandatory gates, when should the loop stop and surface to the human? Budget limits? Confidence drops? Repeated failures?
- **Error recovery:** If a step fails (e.g., research finds nothing, spec gets rejected by necessity gate), what does the loop do? Retry? Fall back? Ask the human?
- **Entry points:** Can the loop start from any point in the spine (e.g., pick up mid-research), or only from the beginning?
- **Observability:** How does the human see what the loop is doing? Real-time progress? Post-hoc report? Both?
