# Clarify Brief: hitl-gate-briefs

**Slug:** hitl-gate-briefs
**Timestamp:** 20260403T205522Z
**Status:** draft

---

## Idea

Cortex commands that present decisions at gates (cortex-review, cortex-spec readiness, eval approval) should auto-generate product-level summaries framed for a non-technical approver. Current behavior dumps implementation details. Desired behavior: frame each decision as what the user/product experiences, reduce to minimum decisions needing human input, use plain language, handle implementation details silently.

---

## Goal

Every Cortex human-approval gate presents a concise, product-framed brief that tells the approver what changed for the user/system, what they need to decide, and why — without requiring them to parse implementation details like table schemas, line counts, or function names.

---

## Non-Goals

- Not redesigning the gate system itself (autonomy config, mandatory gates, gate resolution stays as-is)
- Not removing implementation details from artifacts — the spec/contract/review still contain full technical detail. The brief is an overlay, not a replacement
- Not adding a new approval workflow — the existing approve/reject flow remains unchanged
- Not building a UI or dashboard for gate approvals — this is text output in the CLI

---

## Constraints

- Must work within existing SKILL.md instruction format — no new runtime dependencies
- Brief generation must be inline (not a separate command) — appears automatically when a gate blocks
- Must not slow down the gate check — brief is generated from data already in context, not from new research
- Must preserve the ability to see full technical details on demand (e.g., "show details" option or reference to the full artifact)
- Mandatory gates (ux_taste_eval, human_action, reclarify) cannot be skipped regardless of brief quality

---

## Assumptions

- The approver is the same person who initiated the Cortex workflow — they have project context but may not remember implementation specifics
- Gate decisions are binary (approve/reject) or selection-based (pick an option) — the brief just needs to frame the choice, not change the mechanism
- All data needed for the brief is already present in the artifacts the gate reads (spec, contract, eval proposal, review findings) — no additional data gathering needed
- The 5 gate-patched skills (cortex-clarify, cortex-research, cortex-spec, cortex-review, cortex-audit) are the complete surface area

---

## Open Questions

- Which gates actually block with user-facing output today? Need to audit each of the 13 gates to identify which ones present decisions vs which silently pass/fail
- What's the right abstraction — a shared "gate brief" template that all skills use, or per-skill formatting logic?
- Should the brief include a confidence signal (e.g., "research strongly supports this" vs "limited evidence")?
- How should the brief handle gates with multiple items (e.g., eval proposal with 8 dimensions) — summarize all, or highlight only the ones needing human judgment?
- Should the brief format differ based on gate type (approval vs decision vs verification)?

---

## Next Research Steps

1. Audit all 13 Cortex gates — for each, document: which skill checks it, what output the user sees when it blocks, what decision they need to make
2. Read the current blocking output for each gate in the 5 gate-patched SKILL.md files — capture the exact text/format presented to the user
3. Identify which gates produce the most implementation-heavy output and which are already product-framed
4. Research how other CLI tools present human approval gates — look at Terraform plan summaries, GitHub PR review requests, and CI/CD approval gates for framing patterns
5. Design a "gate brief" template or post-processing approach that transforms implementation details into product-level summaries
