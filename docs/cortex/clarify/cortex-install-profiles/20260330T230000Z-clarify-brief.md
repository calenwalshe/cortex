## Idea

I want to work on a feature of the install of cortex that lets me basically go ahead install two different versions. One is the system with all the tools like google tools and API stuff. Another is a self contained "cortex logic only" system. I am working at Meta behind a firewall that doesn't let me use those tools. I want to fork this for use there and basically pull things downstream and build on top of cortex, so I can always propagate and merge. Basically I will build the full "suite" here, but then fork it over there for use and building into a downstream version that is similar but different.

**Clarification answers:**
- Profile mechanism: single repo, install script with a profile flag (`install.sh --profile=full|core`)
- Core profile strips tool skills only (web, ai, google, cli) — all Cortex framework logic remains
- Downstream distribution: GitHub → git clone at Meta → push to internal Phabricator diff system (no direct git remote from this repo into Meta infra)
- Merge direction: one-way propagation from upstream (this repo) downstream (Meta internal); Meta-specific additions stay internal

---

## Goal

Add a `--profile` flag to the Cortex install script that installs either the full suite (all skills including external-tool integrations) or the `core` profile (Cortex framework logic only, no tool skills), enabling a clean downstream fork at Meta that can pull upstream Cortex framework updates without conflict from tool-skill files that will never exist in that environment.

---

## Non-Goals

- Bidirectional sync — Meta internal additions never flow back into this repo automatically
- Managing the Phabricator/Arcanist workflow itself — that is the user's responsibility; the install profile just ensures the repo is structured to make it feasible
- Private file access, OAuth flows, or any network-dependent functionality in the core profile
- Separate branch strategy — both profiles live on `main`; the profile is a runtime install choice, not a code split
- Packaging or distributing Cortex as an npm/pip package
- Automated CI that tests the core profile in isolation

---

## Constraints

- Install script must remain a single file (not split into profile-specific scripts)
- Core profile must contain zero references to external API keys, tool SDKs, or network endpoints — safe to commit to a corporate repo without scrubbing
- The directory layout under `~/.claude/skills/` must be identical for both profiles except for which skill subdirectories are present — no path remapping
- Must not break existing `install.sh` behavior (assume current users run the equivalent of `--profile=full`)
- The Cortex framework files (skills, templates, docs structure) must be identical across both profiles so that upstream merges apply cleanly
- Core profile SKILL.md files must not `import` or `require` anything from the stripped tool skills

---

## Assumptions

- The current install script is a shell script (bash) that copies/symlinks files into `~/.claude/skills/`
- "Tool skills" to strip in core profile are exactly: web, ai, google, cli — no others
- All other installed artifacts (cortex-clarify, cortex-spec, cortex-research, cortex-review, cortex-audit, cortex-stash, cortex-fit, gsd-*, reup, etc.) are in scope for both profiles
- Meta engineers will clone this GitHub repo directly and run `install.sh --profile=core`; there is no intermediary packaging step
- The Phabricator workflow (`arc diff`, `arc land`) is compatible with a standard git repo cloned from GitHub
- A simple `--profile=full|core` flag is sufficient; no sub-profiles needed at this stage
