---

## Goal

Every Cortex command, hook, agent, and state transition is fully documented with inputs, outputs, state effects, and error behaviors so that any operator can understand and use the system without reading a single SKILL.md or source file.

---

## Non-Goals

- Not rewriting or refactoring the skill implementations themselves
- Not building a website or external documentation site — repo-local docs only
- Not documenting GSD internals (GSD owns its own docs)
- Not user-facing tutorials for end-users of projects that use Cortex — this is operator/developer documentation
- Not auto-generating docs from code (no tooling build step)

---

## Constraints

- Docs must stay co-located with the repo and committed to git — no external systems
- Documented behavior must match actual skill behavior — drift is worse than a gap
- Must not duplicate SKILL.md content verbatim; reference or summarize instead
- The 8-command surface is the stable scope — no new commands added during this work
- Output lives in `docs/` only — no writes to `skills/` or hook files

---

## Assumptions

- `docs/COMMANDS.md`, `docs/INTELLIGENCE_FLOW.md`, `docs/CONTINUITY.md`, `docs/EVALS.md`, `docs/AGENTS.md`, `docs/DISCOVERY_LOOP.md`, and `CORTEX.md` are the canonical documentation locations
- The primary reader is a Claude Code operator setting up or extending Cortex — not an end-user of a project Cortex is applied to
- "IO" means: what inputs each command accepts (arguments, flags, file prerequisites), what files it writes, and what state it modifies
- The 8-command surface is: /cortex-clarify, /cortex-research, /cortex-spec, /cortex-experiment, /cortex-investigate, /cortex-review, /cortex-audit, /cortex-status

---

## Open Questions

- Which existing docs are accurate vs stale vs missing sections entirely? (requires audit — do not assume)
- Is `docs/COMMANDS.md` the right structure, or do commands need individual reference pages to cover IO in full depth?
- Should hook behavior (SessionStart, PostToolUse, PreToolUse, Stop, etc.) be documented at the same depth as commands — with IO, trigger conditions, side effects?
- Should agent behaviors (cortex-specifier, cortex-critic, cortex-scribe, cortex-eval-designer) each have a reference entry with tools allowed, write roots, and when to invoke?
- Is there a quick-start or "how to use Cortex on a new project" onboarding section anywhere? If not, is that in scope?
- What does "standard good documentation" look like for a system of this type — is there a reference model (e.g. a well-documented CLI tool or framework) to benchmark against?

---

## Next Research Steps

1. Audit all existing docs (`CORTEX.md`, `docs/COMMANDS.md`, `docs/INTELLIGENCE_FLOW.md`, `docs/CONTINUITY.md`, `docs/EVALS.md`, `docs/AGENTS.md`, `docs/DISCOVERY_LOOP.md`) against actual skill implementations — for each: is it accurate, stale, or missing sections?
2. For each of the 8 commands, enumerate: documented inputs/flags, documented outputs (file paths), documented state effects (state.json fields touched), documented error/block behaviors — identify gaps
3. Identify whether hooks and agents are documented to the same depth as commands; flag what's missing
4. Research analogous well-documented CLI/AI systems for structural patterns (what sections, what level of IO detail, how examples are handled)
5. Propose a documentation structure: single COMMANDS.md with deep IO tables, or per-command pages, or a reference index — with a recommendation
