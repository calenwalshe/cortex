## Idea

Add GitHub as a first-class platform in the Cortex autonomous loop. Currently cortex-drive can clarify, research, spec, bridge, execute, validate, and close — but all work stays local. It can't open PRs, check CI status, read issue context, respond to review comments, or close issues. The `gh` CLI is installed and authenticated (calenwalshe, GH_TOKEN), but nothing in Cortex or GSD orchestrates GitHub operations as part of the lifecycle.

This is the last mile for "idea to merged PR" autonomy. Without it, every cortex-drive run ends with code on a local branch that a human must manually push, PR, and merge.

Source: autonomous-builder-ideas.md item H1 ("GitHub platform — typed PR/issue/check ops. Most important single addition for autonomous building").

---

## Goal

cortex-drive can take a slug from clarify through to a merged PR on GitHub — creating a branch, pushing code, opening a PR with structured description, waiting for CI, requesting review, and closing the associated issue — so that autonomous runs produce shipped code, not just local commits.

---

## Non-Goals

- [owner-intent] No code without contract.
- [owner-intent] Disk is truth.
- Not building a generic GitHub API wrapper — using `gh` CLI which is already installed and authenticated
- Not building GitHub Actions / CI pipelines — using whatever CI is already configured on the repo
- Not building a code review bot — Cortex reviews code via /cortex-review, then opens the PR with the review already done
- Not supporting GitLab, Bitbucket, or other forges — GitHub only for now
- Not automating merge — the PR is opened, CI passes, but merge requires human approval (safety gate)
- Not building issue triage or project management — just reading issue context and closing issues linked to completed slugs

---

## Constraints

- [owner-intent] Validators must run. PRs should only be opened after validators pass.
- [owner-intent] GSD owns execution. GitHub operations happen AFTER execution, not during it.
- [owner-intent] Correctness > Speed. Never push code that hasn't been validated.
- Must use `gh` CLI (already installed, authenticated) — no direct GitHub API calls or new dependencies
- Must work with any GitHub repo (not hardcoded to calenwalshe/cortex)
- PR descriptions must be structured (summary, test plan, linked issue) not just commit dumps
- CI status checking must have a timeout — don't block indefinitely on slow CI
- Branch naming must be deterministic from the slug (e.g., `cortex/{slug}`)
- Must handle the case where the repo has no CI configured (skip CI check, proceed to PR)

---

## Assumptions

- `gh` CLI v2.67+ is available and authenticated via GH_TOKEN
- The target repo is a GitHub repo with push access
- PRs are the standard shipping mechanism (not direct pushes to main)
- CI runs automatically on PR creation (if configured)
- The human wants to review and merge PRs manually (merge is not automated)
- Most slugs produce work on the main branch that needs to be PR'd from a feature branch
- Issue context (if any) is available via `gh issue view`

## Open Questions

- Where in the cortex-drive loop does GitHub integration go? New rows after row 10 (validators pass) and before row 13 (done)? Or a new phase between "assure" and "close"?
- Should Cortex create the branch at execution start (so commits land on a feature branch) or at PR time (cherry-pick or rebase from main)?
- How does PR description get generated? From the spec + contract + review? From commit messages? From a template?
- Should cortex-drive read GitHub issues at row 1 (backlog ranking) to find work items? Or is the stash the only backlog source?
- How to handle repos where main is protected (no direct pushes)? Feature branch workflow is assumed but needs to be explicit.
- Should CI failure trigger a repair loop? (CI fails → investigate → repair contract → re-execute → re-push → re-check CI)
- What's the right timeout for CI status polling? 10 minutes? 30 minutes? Configurable?
- Should PR review comments from GitHub be ingested back into Cortex? (Reviewer says "change X" → cortex-investigate → repair)
