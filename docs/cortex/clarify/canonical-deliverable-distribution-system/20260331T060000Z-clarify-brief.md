## Idea

A system that's like a canonical deliverable format — it works via email, NotebookLM, tasks, all kinds of things, and it stores it in a singular place. When any AI workflow (Cortex or otherwise) produces a deliverable — recipe, doc, plan, report, artifact — that deliverable lives in one canonical location and gets distributed automatically to wherever the human actually needs to find and use it: inbox, notebook, task list, calendar, phone.

## Goal

A single-store, multi-surface distribution layer where any Cortex deliverable is written once to a canonical location and automatically pushed to human-native surfaces (email, NotebookLM, tasks, etc.) in the right format for each surface — so the artifact is always findable in context, not just in git.

## Non-Goals

- Replacing git/markdown as the canonical store — the goal is to distribute FROM it, not replace it
- Building a new document editor or authoring tool
- Real-time collaboration or multi-author editing on deliverables
- Versioning or diff-tracking on the distributed copies (canonical source is the single source of truth)
- General-purpose document management (Notion, Confluence competitor)
- Two-way sync — surfaces receive, they don't write back to canonical

## Constraints

- Canonical store must remain the existing Cortex repo structure (`docs/cortex/`)
- Must work with surfaces already available: Gmail (SMTP), NotebookLM (MCP), Tasks (tool)
- No new infrastructure — runs as hooks or post-artifact steps within the existing agent stack
- Distribution must be opt-in or configurable per deliverable type — not everything should be emailed
- Must not duplicate or fragment state — distributed copies are read-only references, not sources of truth

## Assumptions

- The canonical store is the local git repo at `/tmp/test` (or equivalent project root)
- The user is the sole consumer — this is a personal system, not a team system
- "Distribution" means push, not pull — the system sends to surfaces rather than surfaces polling
- Each surface has different format requirements (email = plain text, NotebookLM = source doc, tasks = structured checklist)
- The current set of surfaces (email, NotebookLM, tasks) is the v1 scope — others (calendar, Slack, phone) are future

## Open Questions

- **What is the trigger?** Does distribution fire automatically when a Cortex artifact is written (post-hook), or does the user explicitly invoke a distribute command per deliverable?
- **Which surfaces per deliverable type?** Should there be a routing table (e.g. recipes → email + NotebookLM, plans → tasks + email, reports → NotebookLM only), or does the user select surfaces at distribution time?
- **Format transformation:** Is each surface given a reformatted version of the content (markdown stripped for email, structured for tasks), or the raw artifact content? Who owns the transformation logic?
- **What is the canonical "publish" event?** Is it when a contract is marked complete, when a recipe is written, when the user runs a command — what exactly fires the distribution?
- **NotebookLM model:** Does each deliverable become its own notebook, or do all deliverables of a type get added as sources to a single persistent notebook (e.g. "Recipes" notebook)?
- **Discoverability index:** Is there a single manifest / index of all distributed deliverables (what was sent where, when), or is the git log sufficient?

## Next Research Steps

1. Audit existing Cortex artifact lifecycle — map every point where a deliverable is written and what metadata is available at that moment (type, slug, path, format)
2. Research hook and trigger options in the current agent stack — what can fire automatically post-artifact vs. requiring explicit invocation
3. Map surface-specific format requirements: email (MIME plain/text), NotebookLM (source document API), Tasks (structured checklist schema)
4. Research NotebookLM source management — per-deliverable notebook vs. aggregated notebook by type; source update vs. add-new behavior
5. Design the routing table schema — deliverable type → surfaces → format transformer
6. Review prior art: how do systems like Zapier, n8n, or Linear webhooks handle single-source fan-out distribution
