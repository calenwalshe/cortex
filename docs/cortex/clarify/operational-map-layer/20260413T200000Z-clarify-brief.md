# Clarify Brief: operational-map-layer

## Idea

add an operational layer to the Cortex system map — track which files get edited frequently (hotspots) and which files change together (co-change patterns) by recording Edit/Write events via the Stop and TaskCompleted hooks, storing a rolling edit ledger in .cortex/, and surfacing hotspot and co-change context alongside the structural graph in clarify briefs and specs so intelligence phases know which files are volatile and which are coupled before making scope decisions

---

## Goal

The Cortex system map gains an operational layer — a rolling edit ledger tracking file-level hotspots and session-level co-change patterns — so that every clarify brief and spec is written with knowledge of which files are volatile and which are coupled, enabling better write root selection and more accurate risk assessment.

---

## Non-Goals

- Structural layer (function/import extraction via Python ast) — already shipped as `structural-map-layer`
- Distilled layer (human-curated `docs/cortex/system-map.md`) — already shipped as `system-map-memory`
- Cross-session historical analysis beyond a rolling window — scope is limited to recent operational signal
- Git log-based co-change analysis (blame, diff history) — separate concern; requires git integration outside stdlib
- Code quality metrics (complexity, test coverage, lint scores) — out of scope
- Surfacing operational data in GSD execution phases — intelligence phases only (clarify, research, spec)
- Real-time or keystroke-level edit tracking — events fire at tool boundaries only
- Multi-project operational tracking — Cortex project only

---

## Constraints

- [owner-intent] No code without contract — operational ledger and hooks cannot be written before a contract is approved
- [owner-intent] No external service or database — pure Python stdlib; no pip dependencies; no SQLite for core operation
- [owner-intent] Disk is truth — edit ledger must be file-resident in `.cortex/` as JSONL or JSON; never in-memory only
- Must not break or replace existing PostToolUse, Stop, or TaskCompleted hooks — operational layer hooks are additive
- Operational layer is advisory — intelligence phases soft-fail and proceed without it if ledger absent or corrupt
- additionalContext budget constraint: worst-case 1,604-char headroom; per-skill inline reads bypass budget entirely (proven pattern from structural-map-layer and system-map-memory)
- Rolling window must be enforced to prevent unbounded ledger growth; pruning must not block tool execution
- Hook payload schema for Stop and TaskCompleted must be verified before relying on it for grouping — confirmed unreliable assumption in structural-map-layer research

---

## Assumptions

- The PostToolUse hook (already proven for structural-indexer) is the right event for capturing individual Edit/Write events, not Stop or TaskCompleted — Stop fires after every response turn, not just session end
- A JSONL append file (`.cortex/edit-ledger.jsonl`) is sufficient storage — one line per edit event with timestamp, file path, and session/task context
- Co-change grouping can be approximated by session ID (from PostToolUse payload) — files edited with the same session ID are "co-changed" in that session
- The rolling window of the last N edit events (or last K days) is sufficient for meaningful hotspot signal given this codebase's edit velocity
- The structural graph (`.cortex/structural/`) can be cross-referenced to annotate hotspot entries with function names — the two layers compose
