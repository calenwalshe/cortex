# Clarify Brief: claude-code-status-line

**Slug:** claude-code-status-line
**Timestamp:** 20260410T010000Z
**Status:** draft
**Complexity:** trivial

---

## Idea

best way to improve my claude code status line right?

(Clarification: user wants to add missing info fields to the status line, not reduce clutter or start from scratch.)

---

## Goal

The Claude Code status line displays the Cortex signals that actually matter during active work (current slug, mode, approval status, and any pending gates) so the user can see at a glance what state they're in without running `/cortex-status`.

---

## Non-Goals

- Not changing the status line framework or rendering engine — working within Claude Code's existing status line API
- Not redesigning the status line layout to reduce clutter — the user wants more info, not less
- Not building a real-time dashboard — the status line is a passive readout
- Not adding every possible Cortex signal — curate to the high-value ones
- Not requiring network calls or external services to render — status line must be local-only

---

## Constraints

- [owner-intent] No code without contract. Production code must not be written before a contract is approved.
- [owner-intent] Validators must run. No slug closes without validators passing.
- [owner-intent] Disk is truth. All state lives in repo artifacts. Chat is ephemeral.
- [owner-intent] GSD owns execution. Cortex does not write to .planning/ except via /cortex-bridge.
- [owner-intent] No sycophantic evals. Eval rubrics must test for actual correctness.
- Must use Claude Code's documented status line mechanism (`statusLine` in settings.json)
- Status line updates must be fast — no blocking calls that would delay prompt readiness
- Status line must gracefully degrade if `.cortex/state.json` doesn't exist (fresh project case)

---

## Assumptions

- Claude Code supports a configurable status line via settings.json (confirmed — update-config skill mentions it)
- The status line is rendered from a command/script whose stdout becomes the display
- `.cortex/state.json` is the canonical source for Cortex state and is cheap to read
- Adding Cortex signals is additive — can coexist with any current fields (git branch, model, etc.)
