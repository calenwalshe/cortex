---

## Goal

Design and implement a memory architecture for Cortex's intelligence phases (clarify → research) that enables structured iteration between rounds, preserves reasoning context across sessions and compactions, and accumulates cross-slug lessons — so that each new slug starts with the intelligence of all prior work, not from zero.

---

## Non-Goals

- Not a general-purpose conversation memory system (like MemPalace) — this is scoped to the intelligence phases of the Cortex lifecycle
- Not a replacement for the existing artifact system (clarify briefs, dossiers, specs remain the primary outputs)
- Not a change to the execution phases (GSD, validate, repair) — those are downstream consumers, not targets
- Not a database or external service — must remain file-based per owner anti-goals
- Not a chat history replay system — the goal is structured intelligence accumulation, not verbatim conversation storage

---

## Constraints

- [owner-intent] No code without contract. Production code must not be written before a contract is approved.
- [owner-intent] Validators must run. No slug closes without validators passing.
- [owner-intent] Disk is truth. All state lives in repo artifacts. Chat is ephemeral.
- [owner-intent] GSD owns execution. Cortex does not write to .planning/ except via /cortex-bridge.
- [owner-intent] No sycophantic evals. Eval rubrics must test for actual correctness.
- Must be file-based — no ChromaDB, no SQLite, no external vector store for core operation (optional enhancements are fine but core must work without them)
- Must survive /clear, /compact, and session crashes — the memory is disk-resident, not chat-resident
- Must not bloat context — memory retrieval must be selective, not "dump everything"
- Must work within the 10K char additionalContext hook cap (pointer injection pattern, as established in system-decomposition-map)
- The clarify → research loop already has a backtrack path (reclarify_required in DISCOVERY_LOOP.md) — memory must enhance this, not replace it

---

## Assumptions

- The intelligence phases (clarify → research) would produce better outputs if they could iterate more before committing to spec — currently the pressure is to move forward because context degrades
- Cross-slug intelligence accumulation is valuable — lessons from debugging slug A's API client are relevant when building slug B's pipeline on top of it
- The existing `facts.jsonl` extraction is too lossy — it captures decisions and lessons but discards the reasoning chain that led to them
- A structured memory layer would reduce the "starting from zero" problem on each new slug without requiring the user to manually curate context
- The 10K hook cap and 60% effective context window mean memory injection must be highly selective — retrieval quality matters more than storage completeness

## Open Questions

- What should the memory schema look like? Types of memories (reasoning chains, failed approaches, cross-slug patterns, architectural hypotheses) and their structure
- How should memories be written — automatically during clarify/research phases, or explicitly via a command? What triggers memory creation?
- How should memories be retrieved — by slug similarity, by topic embedding, by recency, or by explicit query? What's the retrieval strategy that fits the 10K hook cap?
- What's the iteration model for clarify → research? Currently it's linear with an optional backtrack. Should it become a deliberate loop with exit criteria?
- How does this interact with the system map (just built)? The map captures structural context; memory captures experiential context. Do they reference each other?
- How does this interact with the auto memory system (`~/.claude/projects/*/memory/`)? That system already stores user preferences and feedback. Should Cortex memory layer on top of it, replace it, or stay independent?
- What's the retention/decay model? Do memories expire? Are some types more persistent than others?
- What's the difference between a "memory" and a "fact" in facts.jsonl? Should facts.jsonl evolve into the memory store, or should they be separate systems?

## Next Research Steps

1. Analyze the current clarify → research → spec flow to identify exactly where context is lost and where iteration would add value — map the information lifecycle through the intelligence phases
2. Survey memory architectures in AI agent systems (MemGPT, Letta, MemPalace knowledge_graph.py standalone, Zep, Mem0) — focus on file-based and local-first approaches that could work without a database
3. Design candidate memory schemas — what types of memories, what fields, what provenance metadata — and evaluate each against the "selective retrieval within 10K cap" constraint
4. Prototype the clarify ↔ research iteration model — what are the exit criteria for moving to spec? How does memory enable more productive iterations?
5. Define the relationship between memory, facts.jsonl, system map, and auto memory — draw the boundary between experiential context (memory) and structural context (map) and extracted facts (facts.jsonl)
