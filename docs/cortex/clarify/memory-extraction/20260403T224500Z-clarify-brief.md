# Clarify Brief: memory-extraction

**Slug:** memory-extraction
**Timestamp:** 20260403T224500Z
**Status:** draft
**Complexity:** standard

---

## Idea

Enhance the postcompact hook to decompose compaction summaries into atomic facts (decisions, preferences, patterns, constraints) stored in structured format instead of a flat markdown summary. Based on pattern #13 from the pattern-harvest research — ADK Memory Bank / CrewAI remember_many() pattern. The goal is to preserve session intelligence through compaction events so that post-compaction context is richer and more retrievable, and to lay the groundwork for future semantic memory retrieval (embeddings).

---

## Goal

After compaction, session intelligence is preserved as discrete, typed, searchable facts in a structured store — not a lossy markdown blob — so that post-compaction context reconstruction recovers decisions, preferences, and patterns that the current hook silently drops.

---

## Non-Goals

- Not building embedding/vector infrastructure (that's the future #12 semantic retrieval milestone)
- Not replacing the existing auto-memory system in ~/.claude/projects/*/memory/ — this is complementary
- Not modifying the precompact hook (cortex-precompact.sh) — only the postcompact hook
- Not building a query interface for extracted facts (retrieval is a separate milestone)
- Not persisting facts across projects — facts are per-project in .cortex/

---

## Constraints

- PostCompact hook must complete in <5 seconds (hooks block the session)
- Cannot use external services or APIs (hook runs locally, no network calls)
- Must use Node.js or bash (consistent with existing hook infrastructure)
- Facts must be stored in a format that future embedding systems can consume (JSON or JSONL)
- Must not break existing postcompact behavior (last-compact-summary.md and next-prompt.md still written)
- The LLM is not available inside hooks — extraction must work from the precompact snapshot text, not via LLM calls

---

## Assumptions

- The precompact snapshot (cortex-precompact.sh output) contains enough structured information to extract atomic facts from
- A regex/pattern-based extraction approach can capture the majority of useful facts without LLM assistance
- JSONL is the right storage format for facts (append-friendly, line-oriented, future-embedding-compatible)
- Facts accumulate across compactions (append-only, not overwritten per compaction)
- The existing .cortex/ directory is the right location for the facts store

---

## Open Questions

- What categories of facts should be extracted? (decisions, preferences, patterns, constraints, blockers, context pointers — what else?)
- What does the precompact snapshot actually contain? Need to inspect cortex-precompact.sh output format to design extraction patterns
- Should facts have a TTL or staleness indicator? Session facts may become stale as code changes
- How should duplicate facts be handled across multiple compaction events?
- What's the maximum reasonable fact store size before it needs pruning?
