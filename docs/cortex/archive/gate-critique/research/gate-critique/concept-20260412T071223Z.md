## Owner Summary

- **What we found:** Cortex's existing gates check structure and completeness but do not adversarially challenge whether an artifact is correct or well-framed — that gap is real and the fix has a clear pattern: a separate critic invocation (different system prompt, not self-critique) running before each human gate decision.
- **What it changes:** The design splits into two distinct pieces: (a) artifact-type-specific critique dimensions (different questions for a brief vs. a spec vs. a contract), and (b) a three-tier severity router (STOP / CAUTION / GO) that determines whether the gate hard-blocks or advances with a receipt. Both pieces are needed; skipping either produces a noisy or ineffective critique.
- **What's still open:** Whether to build a new `/cortex-critique` skill or extend existing gate implementations inline — the cortex-review skill exists but covers only code diffs, not prose artifacts at early gates.

## Summary

Cortex currently has 7 named gates across 4 skills, all of which check structural conditions (is there a contract? are assumptions backed? does a conflict exist?) but none of which adversarially critique the artifact's quality, framing, or correctness. The research confirms this gap is real and that filling it requires: (1) separate critic invocations per artifact type using pre-committed critique dimensions (not per-call inference), (2) a three-tier severity routing system (STOP/CAUTION/GO) to prevent hard-block-only gates from being bypassed, and (3) persistent critique artifacts separate from the primary artifacts, with a small immutable receipt at each gate advance. The cortex-review skill is a code-review tool and does not satisfy the need at clarify→research or research→spec gates; those transitions currently have no critique mechanism at all.

## Findings

- **7 existing Cortex gates, 0 of which do adversarial critique.** The gates check: slug conflict (clarify-clarify), reclarify flag (mandatory), critical uncertainty, evidence backing, necessity verdict, contract approval (cortex-spec), and eval proposal approval (cortex-research). All are structural checks. None challenge whether the artifact is correct or well-framed.
- **cortex-review exists but is the wrong tool for early gates.** cortex-review (code review) operates on `git diff` and has contract compliance lenses. It fits spec→contract reasonably. It has no lenses for clarify-brief critique (problem framing, assumption explicitness) or research dossier critique (evidence adequacy, finding-to-question traceability). Building gate-critique on top of cortex-review for early gates would require significant new lenses.
- **Role separation is the #1 effectiveness requirement.** Critic must be a different invocation from the generator — different system prompt, different call. Asking the same model that produced the artifact to critique it is a known failure mode. This is the most important design constraint from the literature.
- **Pre-committed critique dimensions per artifact type outperform per-call inference.** Fixed dimension sets (like IEEE 830 for requirements: completeness, unambiguity, consistency, verifiability, correctness, traceability) catch more real issues than asking "what's wrong?" The dimensions must be codified in the skill, not generated dynamically.
- **Forced finding requirement breaks the rubber-stamp dynamic.** A critic that can return zero findings will drift toward approval under training pressure. Effective systems require the critic to produce at least N findings or explicitly justify why zero is valid.
- **Three-tier severity routing is the industry standard.** Binary block/pass gates fail at scale — either over-block (teams route around) or under-block (thresholds drift). SonarQube, GitHub required reviews, and CI quality gates all use: STOP (critical, hard-blocks gate), CAUTION (medium, advances with logged receipt), GO (low/info, silent advance). This maps directly to Cortex's autonomy preset system.
- **Separate critique artifact per gate is the clean persistence pattern.** Inline critique (embedded in the primary artifact) creates noise that pollutes readable artifacts. Appending findings to the primary artifact conflates spec with review. A separate `critique-{gate}.md` per gate keeps artifacts clean, survives edits to the primary artifact, and is accessible to later gates (a spec critique can read what the brief critique flagged).
- **Gate receipt pattern enables audit trails without bloat.** At gate advance, a small immutable receipt (GO/CAUTION/STOP + finding count + disposition) is appended to `.cortex/state.json` — not to the primary artifact. This keeps the artifact clean while maintaining an auditable record.
- **Critique findings that don't survive the gate are useless.** The most common failure mode in review systems: findings captured in a transient medium (inline chat, PR comment) that becomes inaccessible after gate advance. Cortex's "disk is truth" constraint directly addresses this — critique artifacts must be repo-local.
- **Clarify→research is the highest-value critique insertion point.** Bad framing at the clarify stage propagates through research, spec, and contract before being caught. The current pipeline has no critique at this transition. A framing attack at clarify→research catches the most expensive downstream mistakes at the lowest cost.

## Trade-offs

### Option: New `/cortex-critique` skill with artifact-type-specific lenses
**Pros:** Clean separation of concerns; can be invoked by multiple skills; critique dimensions are versioned independently; easier to test in isolation; gates in cortex-clarify/spec/research/drive can each invoke it at the right transition.
**Cons:** New skill surface to maintain; requires skill invocation from other skills (nested dispatch); adds complexity to the skills that invoke it.
**Verdict:** selected

### Option: Extend existing gate implementations inline
**Pros:** No new skill; critique logic lives alongside the gate it serves; fewer files to maintain.
**Cons:** Critique dimensions become scattered across 4+ skill files with no shared logic; hard to keep consistent; changes to critique dimensions require editing every skill; cannot reuse or test the critic in isolation.
**Verdict:** rejected — violates DRY and makes dimension updates error-prone

### Option: Extend cortex-review to cover prose artifacts
**Pros:** Leverages existing review infrastructure and persistence model.
**Cons:** cortex-review is architecturally built for git diffs; extending it to cover clarify briefs and research dossiers would require significant rework; mixing code review and artifact critique in one skill creates a confusing interface and complicates the skill's scope.
**Verdict:** rejected — wrong abstraction level; would be retrofitting a code review tool to critique prose

### Option: Inline critique in the gate brief (present AI findings in the gate prompt)
**Pros:** Simplest implementation; no separate artifact; human sees AI findings and immediately acts.
**Cons:** Violates "disk is truth" — findings exist only in chat. Findings are not accessible to later gates. No audit trail. If the conversation is cleared, findings are lost.
**Verdict:** rejected — violates owner-intent constraint

### Option: Three-tier severity (STOP/CAUTION/GO) vs. binary block/pass
**Pros of three-tier:** Prevents hard-block bypasses; CAUTION disposition allows progress while logging risk; calibrates over time via the findings register.
**Cons of three-tier:** More complex routing logic; what counts as STOP vs. CAUTION requires initial calibration.
**Verdict:** selected — binary gates are known to fail at scale in review systems

## Recommendations

- Build `/cortex-critique` as a new skill invoked by cortex-clarify, cortex-spec, cortex-research, and cortex-drive at gate transitions — do not extend cortex-review.
- Implement separate critic invocations per artifact type using the `cortex-critic` subagent type (which exists in the agent registry). The cortex-critic subagent profile already specifies: "adversarial reviewer, does NOT propose fixes, identifies problems and explains their potential impact." This is the right tool.
- Codify critique dimensions per artifact type: brief (completeness, unambiguity, consistency, verifiability, framing attack), research dossier (evidence adequacy, source authority, finding-to-question traceability, assumption backing), spec (scope coherence, AC testability, risk completeness, architecture consistency), contract (done criteria verifiability, write roots completeness, validator coverage).
- Implement three-tier severity routing: STOP (gate hard-blocks), CAUTION (gate advances with logged receipt), GO (silent advance). Map STOP → blocks in supervised mode, CAUTION → always advances with receipt, GO → always advances silently.
- Persist critique findings to `docs/cortex/reviews/{slug}/critique-{gate-name}.md` — separate from primary artifacts.
- Write a small gate receipt to `.cortex/state.json` at each gate advance: `{gate: name, verdict: GO|CAUTION|STOP, blocker_count: N, caution_count: N, disposition: advance|override|rejected, timestamp: ISO8601}`.
- Make AI critique non-gated by autonomy preset (always runs) and human critique a gate controlled by the `human_critique` gate (skippable in full-auto). This matches the confirmed design constraint from the clarify brief.
- Insert critique at clarify→research first (highest ROI — catches bad framing before research costs accumulate), then research→spec, then spec→contract (already partially covered by necessity and contract_approval gates).

## Adjacent Findings

- **Same-model critique is a known failure mode:** When the same model invocation that generated an artifact is asked to critique it, the critique systematically fails to catch the artifact's assumptions because they are shared context. The fix is a separate invocation with a different system prompt that treats the artifact as black-box input. This is directly relevant to gate-critique's implementation: the critic must be invoked as a separate call (cortex-critic subagent), not as a self-review prompt appended to the generating skill's context. Source: Constitutional AI research (Anthropic, arXiv:2212.08073); multi-agent review literature.

- **Hard-block-only review systems get bypassed via threshold drift:** In practice, review gates that only know "block" or "pass" drift toward permissiveness over time because teams raise thresholds to reduce friction. SonarQube's three-tier (GO/CAUTION/STOP) was introduced specifically to address this failure mode. This matters for gate-critique because full-auto mode will pressure the system toward permissiveness — the three-tier design with a findings register (even in full-auto) maintains calibration by logging CAUTION dispositions rather than silently discarding them. Source: SonarQube quality gate documentation; CI code review gate patterns (Perplexity research, 2026).

## Open Questions

- Which gate name to use in the autonomy gate system for human critique — `human_critique` or `critique_gate` or per-artifact names (`brief_critique`, `spec_critique`)? Single gate vs. per-artifact gates affects how precisely full-auto can be configured.
- What is the forced-finding minimum for each artifact type? (Critic must produce at least N findings or justify zero.) Calibrating N per artifact type requires a pilot.
- Should the findings register live in `.cortex/state.json` (lightweight, loses history at slug close) or in a dedicated `docs/cortex/reviews/{slug}/findings-register.md` (persists in archive)?
- How does the spec→contract critique interact with the existing necessity gate and contract_approval gate — does critique run before, after, or instead of necessity?
