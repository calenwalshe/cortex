# Clarify Brief: parallel-builds

**Slug:** parallel-builds
**Timestamp:** 20260406T193000Z
**Status:** draft
**Complexity:** complex

---

## Idea

How to run multiple builds in the same target project at the same time without conflict — a Cortex workflow for parallel autonomous execution. Today, state.json has one active slug, .planning/ tracks one phase, and git has one working tree. Running two /cortex-drive loops simultaneously would corrupt shared state. The goal is to enable multiple slugs building concurrently in the same project repo.

---

## Goal

Two or more /cortex-drive loops can run concurrently on different slugs in the same target project, each with isolated state, isolated git branches, and isolated GSD execution — merging cleanly when they complete, without corrupting shared files or stepping on each other's work.

---

## Non-Goals

- Not building a job scheduler or queue system (concurrency is "run two terminals", not a managed pool)
- Not supporting the same slug running twice (one slug = one drive loop)
- Not building cross-slug dependency management (parallel builds are independent)
- Not redesigning Cortex's artifact format (use the existing per-slug directory structure)
- Not building a merge conflict resolver (git handles that; we just need to avoid unnecessary conflicts)

---

## Constraints

- Must work within Claude Code's existing capabilities (multiple terminal sessions, Agent tool worktrees)
- Must not require a central coordinator process (no daemon, no server)
- state.json can only have one active slug — this is the core constraint to solve
- .planning/ is a shared namespace — GSD execution for two slugs can't share it
- Git working tree is shared — concurrent writes to the same branch will conflict
- Hooks fire per-session, not per-slug — hook state (supervisor.jsonl, facts.jsonl) must handle concurrent appends

---

## Assumptions

- Git worktrees provide sufficient isolation for concurrent file modifications (separate working directories, separate branches, shared .git)
- Claude Code's Agent tool `isolation: "worktree"` parameter creates usable worktrees
- Per-slug Cortex artifacts (docs/cortex/clarify/{slug}/, research/, specs/, contracts/) are already isolated by design
- The main conflict points are: state.json (one slug), .planning/ (one phase set), and the git working tree (one branch)
- JSONL files (facts.jsonl, supervisor.jsonl, decisions.md) can tolerate concurrent appends if each write is a single line

---

## Open Questions

- **State isolation:** Should each parallel build get its own state.json (per-worktree), or should state.json become multi-slug-aware (array of active slugs)?
- **Worktree vs branch strategy:** One worktree per slug? Per-slug branches that merge to main? How does GSD .planning/ work inside a worktree?
- **Hook behavior in worktrees:** Do hooks fire correctly when Claude is operating in a worktree? Does CLAUDE_PROJECT_DIR point to the worktree or the main repo?
- **Merge strategy:** When a parallel build completes, how does it merge back? Auto-merge? PR? What if two slugs modified the same file (e.g., both added hooks to settings.json)?
- **cortex-drive coordination:** How does drive loop A know that drive loop B exists? Do they need to know? Or is isolation sufficient?
- **GSD in worktrees:** Can /gsd:drive run inside a git worktree with its own .planning/? Or does .planning/ always live in the main repo?
