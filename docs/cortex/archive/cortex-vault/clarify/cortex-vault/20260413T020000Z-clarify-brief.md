## Idea

Wire the existing memory vault into Cortex so that intelligence phases can read prior learnings at session start and write new findings at gate transitions — using the hooks-as-event-bus architecture from the Drive notes and the autoresearch vault at ~/memory/vault/

---

## Goal

Cortex's intelligence phases (clarify, research, spec) read from and write to the existing memory vault (`~/memory/vault/`) at defined event boundaries, so that each new slug starts with accumulated cross-slug learnings rather than from zero, without requiring any manual curation.

---

## Non-Goals

- Not redesigning the vault itself — the vault architecture (FAISS index, facts.db, extraction scripts, inbox/promotion pipeline) stays as-is; this slug only wires Cortex to it
- Not improving the autoresearch classification loop (F1=0.25 targeting 0.7) — that is a separate experiment running in parallel; its outcome does not gate this slug
- Not replacing `facts.jsonl` — facts.jsonl stays as a lightweight per-session artifact; this slug adds vault as a deeper, cross-session persistent layer
- Not a general-purpose conversation memory system — only Cortex gate transitions produce vault writes; raw chat history is not ingested
- Not adding a database or external service — the vault is already file-based (SQLite, FAISS flat files, JSONL); this constraint is already met
- Not changing the execution phases (GSD, validate, repair) — read/write scope is intelligence phases only (clarify, research, spec)

---

## Constraints

- [owner-intent] No code without contract. Production code must not be written before a contract is approved.
- [owner-intent] Validators must run. No slug closes without validators passing.
- [owner-intent] Disk is truth. All state lives in repo artifacts. Chat is ephemeral.
- [owner-intent] GSD owns execution. Cortex does not write to .planning/ except via /cortex-bridge.
- [owner-intent] No sycophantic evals. Eval rubrics must test for actual correctness.
- Must work within the 10K char `additionalContext` hook cap — vault read injection must be selective (pointer or top-k facts), not a full dump
- Must survive /clear, /compact, and session crashes — vault is disk-resident; injection happens at SessionStart, not during conversation
- Must be additive — must not modify existing gate logic, break existing skill flows, or require changes to the primary artifact formats (briefs, dossiers, specs)
- The vault's `recall_query.py` and FAISS index are the canonical retrieval interface — do not build a parallel retrieval mechanism
- Vault writes must go through the inbox/promotion model from the Drive doc, not directly to the durable store — raw events in, promotion decides what is kept

---

## Assumptions

- The vault at `~/memory/vault/` is sufficiently stable to integrate against — it has a FAISS index, facts.db, inbox/, recall_query.py, and the extraction scripts are runnable
- The `additionalContext` field in SessionStart hook output is the right injection point for vault reads — confirmed in prior slugs (system-decomposition-map established the pointer pattern)
- Cross-slug learnings are worth surfacing at session start — architectural decisions, failed approaches, and lesson-type facts from prior slugs are decision-relevant for new slugs
- The Drive doc's promotion model (events → inbox → promotion → durable memory) is the right write architecture — write to inbox at gate transitions, promotion runs separately
- Gate transitions (dossier written, clarify brief written, spec written) are the right write triggers — they produce the highest-signal Cortex artifacts; raw tool use is too noisy
- The autoresearch classification loop (F1=0.25) is irrelevant to this slug — it classifies learning moments from raw chat; Cortex gate-transition artifacts are structured and don't need classification to be ingested
