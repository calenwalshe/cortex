**Slug:** cortex-vault  
**Phase:** concept

## Owner Summary

The vault exists and works. Wiring Cortex into it is a plumbing job, not a design job — the read/write interfaces are already defined and stable. The main decision the research surfaced: **do not write to the vault from bash hooks; write to the inbox from a Python extractor called at gate transitions, then let the promotion pipeline handle the rest.** The vault's inbox format is simple (YAML frontmatter + markdown body) and the `add_fact()` function in `fact_store.py` is the right API for structured insertion. The existing `cortex-session-start.sh` hook already has the right injection point — after line 40, before the health check — with ~5000–8000 chars of budget remaining after current state injection. The 10K cap is real. Top-5 vault facts using `recall_query.py` with `--project cortex` and a slug-relevant query produces well under 1500 chars.

**Key risk:** The episodic/procedural extractors are designed for session JSONL files, not Cortex structured artifacts. A separate Cortex-specific extractor is needed for gate-transition writes — this is not a blocker but it is new code that must be written.

## Summary

The vault read/write round-trip is fully audited at the interface level. The right integration pattern for this slug is clear. Four implementation-level questions remain unresolved (importability of `fact_store.py`, idempotency behavior, `--project` filter exact match semantics, and SessionStart budget measurement) — these are deferred to spec/implementation phase and do not block the design decision. The architecture decision is not contingent on these answers; they affect the implementation approach, not the approach choice itself.

1. **Read (SessionStart):** call `recall_query.py` with slug-derived query, inject top-5 results into existing `$FACTS` variable in `cortex-session-start.sh` after the current facts block
2. **Write (gate transitions):** call `fact_store.add_fact()` directly from a new Python extractor that reads completed Cortex artifacts (dossiers, specs, clarify briefs) and extracts typed facts — bypassing the inbox/promotion model for structured artifacts since they don't need LLM classification
3. **Extraction schema:** map artifact sections to `memory_type=semantic`, `scope=learning`, with `topic` encoding the fact category (architecture-decision, failed-approach, lesson, open-question)

## Findings

### Q1 — Vault Read Path

`~/memory/vault/recall_query.py` exposes a clean CLI:

```bash
python3 recall_query.py "QUERY_TEXT" [--deep] [--top-k N] [--type TYPE] [--project SCOPE]
```

**Returns:** Synthesized text (not raw facts):
```
You learned: [1-3 sentence synthesis] (session date: YYYY-MM-DD)
```

**Two modes:**
- Shallow (default): FAISS IndexFlatIP top-k search → LLM synthesis, target <3s
- Deep (`--deep`): query expansion + broader retrieval, multi-step

**Internal mechanics:**
- Embeddings: all-MiniLM-L6-v2, 384-dim, L2-normalized before indexing
- FAISS `IndexFlatIP` (inner product similarity post-normalization = cosine similarity)
- `facts.map.json` maps FAISS row index → fact_id in SQLite
- Post-retrieval filter: `WHERE invalidated_by IS NULL` (returns only active facts)
- Soft-fail: missing index returns empty string (safe for hook injection)

**Scope filter:** `--project SCOPE` filters by `project_scope` column in facts.db — this is the right parameter for scoping vault reads to Cortex-relevant facts.

**Key constraint for hook injection:** The output is already human-readable synthesized prose, not JSON. This is correct format for `additionalContext` injection — no reformatting needed.

### Q2 — Vault Write Path

**Two write paths exist:**

**Path A — Inbox/Promotion (designed for conversational extraction):**
- Inbox file: `inbox-{ISO8601}-{SEQ:03d}.md`
- YAML frontmatter: `id`, `type`, `status`, `source_type`, `source_ref`, `fetched_at`, `tags`
- Body: free-form markdown (numbered list or prose)
- Promotion: `promote_session.py` runs `episodic_extractor.py` + `procedural_extractor.py` → LLM classification → `facts.db` + FAISS
- **Problem:** extractors expect session JSONL format (turns), not Cortex structured artifacts. Writing a dossier as a free-form inbox stub would lose structure and require LLM reclassification of already-structured data.

**Path B — Direct `add_fact()` (designed for programmatic insertion):**

```python
from fact_store import add_fact

add_fact(
    content="Atomic fact text (1-3 sentences, self-contained)",
    session_id="cortex-{slug}",
    valid_from=YYYY-MM-DD,
    topic="architecture-decision",       # 1-2 word label
    entities=["cortex", "slug-name"],
    confidence=0.85,                     # High: Cortex artifacts are reviewed
    importance=0.7,
    scope="learning",                    # All Cortex-derived facts
    memory_type="semantic",             # Not episodic/procedural — structured knowledge
    project_scope="cortex",             # Makes facts retrievable via --project cortex
    ingestion_time=ISO8601_NOW
)
```

**Verdict:** Use Path B (direct `add_fact()`) for Cortex gate-transition writes. Cortex artifacts are already structured — sending them through inbox/LLM extraction would re-classify what's already classified. Path B is simpler, more reliable, and produces cleaner facts.

**Durable store:** Dual-layer SQLite (`facts.db`) + FAISS (`facts.faiss`). SQLite is the truth; FAISS is the search index. `add_fact()` writes to both atomically.

### Q4 — SessionStart Injection Format

**Confirmed JSON format:**
```json
{
  "hookSpecificOutput": {
    "hookEventName": "SessionStart",
    "additionalContext": "CORTEX STATE RESTORED\n\n{current-state.md content}\n\nRELEVANT FACTS FROM PRIOR WORK:\n{facts}\n\nCOHERENCE WARNINGS:\n{health_issues}"
  }
}
```

**10K char hard cap:** Confirmed. Claude Code harness saves content >10K to file and injects a pointer + preview instead. This means vault injection must be selective.

**Current budget allocation:**
- `current-state.md`: ~500–1500 chars
- `.cortex/facts.jsonl` retrieval (top-10 semantic, 30 lines): ~1000–3000 chars
- Coherence warnings: ~200–500 chars
- **Remaining for vault injection: ~5000–8000 chars**

**Vault query for injection:**
```bash
python3 ~/memory/vault/recall_query.py \
  "cortex intelligence phase architecture decisions lessons" \
  --top-k 5 \
  --project cortex
```

This produces ~800–1500 chars of synthesized prose — well within remaining budget.

**Right injection format inside hook:**
```
VAULT MEMORY (top-5 cross-slug facts):
{recall_query.py output}
```

This is distinct from "RELEVANT FACTS FROM PRIOR WORK" (which comes from `.cortex/facts.jsonl` — the per-session Cortex facts store). Vault facts are the cross-session persistent layer; Cortex facts are the local per-project store. Both can coexist in `additionalContext`.

### Q5 — How cortex-session-start.sh Currently Works

**Full flow (lines 1–76):**

1. Reads `current-state.md` → `$CONTENT`
2. Reads `.cortex/facts.jsonl` + `.cortex/state.json` → `$SLUG`
3. Tries semantic retrieval via `scripts/cortex/cortex-retrieve.py` if embeddings exist
4. Fallback: grep `.cortex/facts.jsonl` for slug-tagged facts (types: lesson, procedure, decision, pattern, observation)
5. Runs `scripts/cortex/cortex-health.py --json` → `$HEALTH`
6. Combines into `additionalContext` JSON output

**Vault injection point:** After line 40 (`fi` closing the facts retrieval block), before line 43 (health check):

```bash
# --- VAULT INJECTION (new) ---
VAULT_FACTS=""
VAULT_SCRIPT="${HOME}/memory/vault/recall_query.py"
if [[ -f "$VAULT_SCRIPT" && -n "$SLUG" ]]; then
  VAULT_QUERY="cortex ${SLUG} architecture decisions lessons"
  VAULT_FACTS=$(python3 "$VAULT_SCRIPT" "$VAULT_QUERY" --top-k 5 --project cortex 2>/dev/null || echo "")
fi
# ---
```

Then in the `$EXTRA` block (lines 54–61), append vault facts after the existing `$FACTS`:
```bash
if [[ -n "$VAULT_FACTS" ]]; then
  EXTRA="${EXTRA}\n\nVAULT MEMORY (cross-session):\n${VAULT_FACTS}"
fi
```

**No structural changes needed** to the hook's output format — vault facts are appended to `additionalContext` as additional plaintext context under a new section header.

### Q6 — Cross-Session Memory Injection Patterns in Agent Systems

**Letta (MemGPT) pattern:**
- Three-tier: core memory (always in context, ~2K tokens / 8K chars), archival (external vector store, retrieved by agent tool calls), recall (conversation history, external)
- Core memory is injected at initialization — equivalent to what `additionalContext` does at SessionStart
- Budget allocation: ~6.5% of context window reserved for core memory, rest for conversation
- **Key lesson:** Fixed-budget core memory with external-paging for archival is the proven pattern for avoiding context bloat

**Mem0 pattern:**
- Passive extraction: key facts pulled from interactions into consistent store
- No explicit budget-aware selectivity at session start
- Token-efficient but not adaptive
- **Key lesson:** Passive extraction works for conversational systems but not for structured artifact ingestion where classification is already done

**General industry patterns (2024-2026):**
- Lazy loading: fetch only task-relevant data at session start; reduces irrelevant data from 60-70% to <10%
- Budget zones: reserve system prompt + tools + output space first; inject memory in the remaining budget
- RAG top-k: 3–8 chunks, ~1K–10K tokens per request; more chunks degrades quality
- "Start lean" principle: ~500-token baseline at session start, add context profiles per task
- Windowing: trim history first at budget threshold; keep first/last N chars; use semantic compression

**For Cortex vault injection:** The Letta pattern is the right model — vault facts are equivalent to Letta's "core memory" (always-in-context, budget-bounded, high-confidence facts). Top-5 semantic retrieval with project scope filter = the right approximation of core memory for a file-based system.

### Q7 — Extraction Schema for Cortex-to-Vault Writes

Based on vault's `add_fact()` schema and Cortex artifact sections:

**Mapping table:**

| Artifact Section | content (1-3 sentences) | topic | memory_type | project_scope | confidence | importance |
|---|---|---|---|---|---|---|
| Clarify Non-Goal | "For slug X: Y was explicitly out of scope — rationale Z" | "scope-exclusion" | semantic | cortex | 0.95 | 0.6 |
| Clarify Constraint | "Constraint: X — applies to all Cortex work because Y" | "owner-constraint" | semantic | cortex | 0.95 | 0.8 |
| Clarify Assumption | "Slug X assumed Y; [outcome if known]" | "design-assumption" | semantic | cortex | 0.75 | 0.7 |
| Dossier Finding | "[Self-contained finding]. Source: [dossier section]" | "research-finding" | semantic | cortex | 0.80 | 0.7 |
| Dossier Trade-off (Verdict) | "For X: chose Y over Z because W" | "architecture-decision" | semantic | cortex | 0.90 | 0.8 |
| Dossier Adjacent Finding | "[Finding]. Applies to: [trigger condition]" | "adjacent-finding" | semantic | cortex | 0.75 | 0.65 |
| Spec Architecture Decision | "Chose X over Y and Z for slug W; rationale: R" | "architecture-decision" | semantic | cortex | 0.90 | 0.85 |
| Spec Alt Considered + Rejected | "Rejected X for slug Y because Z. Not just preference — [evidence]" | "failed-approach" | procedural | cortex | 0.85 | 0.75 |
| Spec Risk + Mitigation | "Risk: X in context Y. Mitigation: Z. Applied to slug W." | "risk-mitigation" | semantic | cortex | 0.80 | 0.70 |

**Provenance:** All Cortex-derived facts include `session_id="cortex-{slug}"` and `project_scope="cortex"`. This ensures `recall_query.py --project cortex` retrieves them. `valid_from` = artifact creation date.

**Self-containment rule:** Every content field must be self-contained — parseable without reading the source artifact. "Chose approach X" is bad (what's X?). "For cortex-vault: chose direct add_fact() over inbox/promotion for gate-transition writes because Cortex artifacts are pre-classified and don't need LLM extraction" is good.

**Extractor location:** New file `scripts/cortex/cortex-vault-extractor.py` — reads a completed Cortex artifact path, determines type from path pattern, extracts typed facts using section-specific extraction logic, calls `add_fact()` for each. Called at gate transitions from cortex-clarify (Phase 4c equivalent), cortex-research (Phase 2.9 equivalent), and cortex-spec (Phase 2c equivalent).

## Trade-offs

### Inbox/promotion vs. direct `add_fact()` for gate writes

**Inbox/promotion:**
- Pro: consistent with vault's existing architecture; promotion pipeline handles deduplication and contradiction detection
- Pro: non-blocking — write to inbox, promotion runs later
- Con: extractors expect session JSONL, not Cortex artifacts; requires new extractor type that mimics inbox format
- Con: adds latency between write and availability in FAISS index
- **Verdict: reject** for gate-transition writes. Cortex artifacts are structured — the inbox/LLM-extraction step adds noise, not value. The contradiction detection benefit doesn't outweigh the complexity.

**Direct `add_fact()`:**
- Pro: simpler, no intermediate format; fact is immediately in FAISS index
- Pro: Cortex artifacts are already reviewed by human at gate approval — high confidence, no reclassification needed
- Con: bypasses promotion pipeline's deduplication; may create near-duplicate facts if same slug is processed multiple times
- Con: requires handling the Python import (fact_store.py is in ~/memory/vault/, not in cortex repo)
- **Verdict: accept** with idempotency guard (check for existing fact with same session_id+topic before writing)

### Top-k=5 vs. top-k=10 for SessionStart injection

**top-k=5:**
- ~800–1500 chars synthesized output
- Fits comfortably in remaining 5K-8K additionalContext budget
- Risk: may miss relevant facts for broad slugs

**top-k=10:**
- ~1500–3000 chars synthesized output
- Still within budget but pushes limits for fact-heavy sessions
- **Verdict: use top-k=5 as default**, expose as configurable (VAULT_TOP_K env var)

### Synthesis vs. raw facts for hook injection

**Synthesized output (recall_query.py default):**
- LLM-synthesized prose: "You learned: X"
- Pro: compact, readable, already actionable
- Con: loses individual fact granularity; LLM synthesis may drop edge cases

**Raw facts (direct SQLite query):**
- Individual fact objects, one per line
- Pro: full granularity; Claude can pick which facts apply to current task
- Con: less compact; more chars per fact unit
- **Verdict: use synthesized output** from `recall_query.py`. The synthesis step trades granularity for compactness, which is the right trade at 5K char budget.

1. **Vault read interface is stable:** `recall_query.py "QUERY" --top-k 5 --project cortex` returns synthesized prose ready for `additionalContext` injection. No wrapper needed.

2. **Direct `add_fact()` is the right write path for structured Cortex artifacts.** The inbox/promotion pipeline is designed for conversational extraction; Cortex gate-transition artifacts don't need reclassification.
