## Idea

What you're describing is not a different execution model. It's a better pre-spec model: ideas do not move cleanly from clarify → research → spec in one pass; they evolve through framing, evidence gathering, re-framing, and bounded experiments until uncertainty is low enough that a spec can safely authorize mostly autonomous execution. That is close to how Cortex already thinks about the world, but it is not fully modeled yet in the current repo. Right now the docs still present a mostly linear pre-spec spine: /cortex-clarify → /cortex-research → /cortex-spec, where research is split into concept, implementation, and evals, each phase is manually requested, and /cortex-spec writes spec.md, gsd-handoff.md, and the first execution contract before GSD takes over execution.

The good news is that Cortex already has the right bones for this. The current design already treats clarify as a gate, keeps open questions in repo-local continuity files, forces human approval before GSD handoff, and uses contracts, validators, and eval plans as real control artifacts rather than chat-only intent. The phase guard also already blocks product-path writes during clarify|research|spec, which means Cortex is explicitly distinguishing pre-execution intelligence work from execution.

What is missing is a first-class model for scientific learning before commitment. The current research model has dossiers, but not a formal notion of "we hit a real uncertainty, so now we need a bounded hypothesis test, prototype, benchmark, or spike before we can spec." The scaffolded state schema also only seeds gates for clarify, research, and spec, and the current research dossier template is still summary/findings/trade-offs/recommendations/open questions, not a learning record with hypotheses, measurable signals, and decision rules.

The external research lines up very strongly with your instinct. The Design Council's Double Diamond explicitly says teams often learn something about the underlying problem that sends them back to the beginning, and that making and testing very early-stage ideas can be part of discovery. MIT Lincoln Laboratory's Hypothesis-Driven Development frames uncertain work as a series of experiments whose outputs are measurable evidence and organizational learning. Thoughtworks makes the same point more bluntly: in exploratory, uncertain phases, teams need hypotheses, not fixed requirements, and should use the scientific method—observation, hypothesis, experiment, evaluation, iteration. Design-Build-Test-Learn is the engineering version of the same pattern: iterative learning before or between commitments.

So the best fit for Cortex is this:

Cortex should evolve from a sequential pre-spec pipeline into a discovery loop with a commitment boundary.

Conceptually:
  clarify
    ↓
  research / discover
    ↘ if frame changed → clarify
    ↘ if critical uncertainty remains → experiment
  experiment
    ↘ if hypothesis falsified → clarify or research
    ↘ if uncertainty reduced enough → spec
  spec (commitment boundary)
    ↓
  GSD execute
    ↓
  validate ↔ repair
    ↓
  assure
    ↓
  done

That matches both the repo's current architecture and the outside research: pre-spec work is iterative and learning-oriented; post-spec work is contract-driven and mostly off-loop.

The most important design move is this: introduce a second contract type.

Today Cortex has an execution contract schema with objective, deliverables, write roots, done criteria, validators, eval plan, and approvals. The clean extension is a learning contract for pre-spec experimentation. Instead of "ship feature X," a learning contract says "test hypothesis H," with bounded scope, permitted write roots, measurable signals, kill criteria, and a clear decision rule: promote to spec, iterate, re-clarify, or abandon.

The pre-spec model:

1. Clarify — still turns fuzzy thought into a problem frame, but the clarify brief becomes a living frame, not a one-time artifact. Research can now mark reclarify_required: true when evidence changes the goal, constraints, or assumptions.
2. Research / Discover — keep concept, implementation, and evals, but add a fourth phase: experiment. This is where targeted R&D lives: prototype, benchmark, simulation, red-team probe, small integration spike, or user-study surrogate.
3. Experiment / Learn — bounded learning work. Experiments should be short, independent, and measurable. One hypothesis may have one or several experiments.
4. Spec / Commit — spec becomes the commitment boundary. /cortex-spec should also require that all critical uncertainties are either resolved by evidence or explicitly accepted by a human.

Concrete integration into the repo:
- Keep the 7-command core intact and extend /cortex-research (add --phase experiment or --mode hypothesis|benchmark|prototype|spike)
- Evolve open-questions.md into a structured uncertainty register with type, severity, resolution_path, and status fields
- Add two new artifact types: docs/cortex/experiments/{slug}/learning-contract-001.md and result-001.md
- Add experiment mode to .cortex/state.json and continuity schema
- Write-root policy: allow docs/cortex/experiments/ and .cortex/tmp/ during experiment; product-path writes require explicit human approval + rollback instructions
- Teach /cortex-spec three new blockers: reclarify_required is false, no unresolved critical uncertainties, every core assumption backed by evidence
- Human mostly on-loop before spec, mostly off-loop after spec

The highest-leverage next artifact is DISCOVERY_LOOP.md — a short design doc defining the new modes, transitions, artifact schemas, and spec-readiness gate.

## Goal

Cortex evolves from a linear clarify→research→spec pipeline into a discovery loop where clarify, research, and experiment iterate until all critical uncertainties are resolved or accepted, and then the spec becomes the commitment boundary authorizing mostly autonomous GSD execution.

---

## Non-Goals

- Not replacing or modifying the GSD execution model (post-spec stays unchanged)
- Not making pre-spec work autonomous — human remains on-loop for approvals and frame revisions
- Not adding a new top-level command surface beyond extending existing skills
- Not implementing a general-purpose experimentation or CI platform
- Not migrating or converting existing Cortex slugs/artifacts to new schemas
- Not changing the execution contract schema — only adding a parallel learning contract type

---

## Constraints

- Must remain backward-compatible: existing clarify briefs, research dossiers, specs, and execution contracts must continue to work without modification
- Phase guard logic must not be weakened — product-path writes remain blocked during all pre-spec phases
- Experiment write roots must be sandboxed (`docs/cortex/experiments/`, `.cortex/tmp/`) with product-path writes only under explicit human approval
- Human approval required before: risky learning contracts, major clarify revisions, and spec handoff
- The 7-command core surface must remain stable — no new required top-level commands
- All new state fields must be additive to `state.json` — no breaking schema changes

---

- The `memory-bank-archive` slug is effectively complete and the repo is clear for a new slug
- The existing phase guard, state.json schema, and continuity file structure are stable enough to extend without a rewrite
- `docs/cortex/experiments/` is a safe new write root that does not conflict with any existing path

- The 8 concrete touchpoints identified (CORTEX.md, INTELLIGENCE_FLOW.md, COMMANDS.md, cortex-research SKILL.md, research-dossier template, learning-contract template, experiment-result template, scaffold_runtime.sh, phase-guard, state.json schema, cortex-spec SKILL.md) represent the complete change surface for a v1 implementation
- Extending /cortex-research with `--phase experiment` is preferable to a new `/cortex-experiment` command

## Open Questions

- Should `--phase experiment` live inside `/cortex-research` or become a new top-level command (e.g., `/cortex-experiment`)? The current assumption is to extend research, but a separate command may be cleaner if experiment lifecycle diverges significantly.
- What is the exact schema for `reclarify_required`? Is it a field in the research dossier, a flag in `state.json`, a field in the uncertainty register, or all three?
- How does the structured uncertainty register relate to the existing `open-questions.md`? Does it replace it, extend it, or is it a separate artifact?
- Should learning contracts require the same human approval flow as execution contracts, or a lighter gate (e.g., auto-approved for low-risk experiments, required for product-path writes)?
- What is the minimum viable v1 scope? DISCOVERY_LOOP.md alone as a design reference, or must state.json schema + phase guard changes ship together?
- Does `experiment` mode need its own gate in `state.json` (e.g., `gates.experiment_complete`), or is it ephemeral within the research phase?
- How should the continuity system (`current-state.md`, `reup`) surface the active hypothesis and experiment ID so the session can resume correctly after `/clear` or compaction?
