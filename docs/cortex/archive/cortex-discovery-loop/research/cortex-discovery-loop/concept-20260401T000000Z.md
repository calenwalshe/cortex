# Research Dossier: cortex-discovery-loop — concept

**Slug:** cortex-discovery-loop
**Phase:** concept
**Timestamp:** 20260401T000000Z
**Depth:** standard

---

## Summary

Cortex's pre-spec spine is architecturally sound but models a linear world that doesn't match how real discovery works. The codebase audit confirms the bones are right — phase guard, artifact-first state, approval gates, contract schema — but two things are missing: a first-class experiment mode for bounded learning before commitment, and an uncertainty register that gives `/cortex-spec` real signal about whether discovery is actually done. The Gemini cross-reference and HDD literature provide a concrete schema for learning contracts with all the fields needed. The single most contested design decision is whether experiment belongs inside `/cortex-research` or as a new top-level command; the evidence favors a new command because experiment has a lifecycle (open/run/close), two artifacts, and different write-root policy — forcing that into a `--phase` flag creates a god command. One immediate discovered risk: the phase guard blocks meta-system writes (hot-context, reup) that are outside `CLAUDE_PROJECT_DIR`, which is a gap that exists today and will become more visible once experiment mode adds more live-session artifacts.

## Findings

### Internal Codebase Audit

- **CORTEX.md and INTELLIGENCE_FLOW.md** both describe a strictly sequential spine. LOOP-04 explicitly encodes `clarify → research → spec → execute → validate → repair → assure → done` with no backtracking path. The repair loop explicitly says "never back to clarify." This is correct for post-spec work but actively wrong as a description of pre-spec discovery.
- **`/cortex-spec` prerequisites** are purely artifact-existence gates: clarify brief exists + at least one research dossier exists. There is no check on whether uncertainties are resolved, whether `reclarify_required` is set, or whether core assumptions are evidence-backed. The gate can be passed with a shallow dossier that defers everything.
- **`cortex-phase-guard.sh`** permits writes to `docs/cortex/`, `.cortex/`, and `docs/cortex/fit/` during `clarify|research|spec`. Write roots are hardcoded string prefixes checked against `CLAUDE_PROJECT_DIR`. This correctly blocks product code during pre-spec. A new `experiment` mode would need `docs/cortex/experiments/` added to permitted roots — a one-line change.
- **`scaffold_runtime.sh`** already includes `archive` in `DOCS_SUBDIRS` (added by `memory-bank-archive`). Adding `experiments` is an identical one-line patch.
- **`state.json` schema** uses free-form string for `mode` — no enum enforcement. Gates are `clarify_complete`, `research_complete`, `spec_complete`, `contract_approved`. Adding `experiment_complete` or other gates is additive and backward-compatible.
- **Research dossier template** schema: summary, findings, trade-offs, recommendations, open questions, sources. No hypothesis, measurable signals, decision rules, or uncertainty severity. This is the template that most needs extending to support the discovery loop.
- **`open-questions.md`** is currently a flat stub. The upgrade to a structured uncertainty register is purely additive — add type/severity/resolution_path/status fields.
- **`/cortex-research` command surface** already uses `--phase` to differentiate output types (dossier vs. eval-proposal). A `--phase experiment` would be the fourth phase flag but would produce two artifacts and require lifecycle management, making it a poor fit for the existing `--phase` pattern.
- **Phase guard blocks meta-system writes**: `/home/agent/.claude/hot-context/cortex.md` and reup snapshot paths are outside `CLAUDE_PROJECT_DIR`, so they are blocked during `clarify|research|spec`. This is a live gap — not caused by the discovery loop change, but it will become more visible with experiment mode.

### External Research (Gemini)

**Learning contract canonical fields (HDD/Lean Startup/Shape Up):**
1. ID + Status + Owner
2. Problem/Opportunity Statement — user/business framing, not solution framing
3. Core Hypothesis — "We believe [action] for [users] will result in [outcome] because [reason]"
4. Key Assumptions — what must be true for the hypothesis to hold
5. Target User/System Context — who or what the experiment focuses on
6. Experiment Design — the minimal artifact or action to test the hypothesis (Shape Up "fat marker sketch")
7. Key Metrics/Evidence — quantitative + qualitative signals
8. Success Criteria / Learning Threshold — minimum outcome that constitutes "enough learning"
9. Risks & Dependencies
10. Appetite / Timebox — maximum investment before a decision is forced (Shape Up term)
11. Expected Learning — what knowledge is anticipated beyond yes/no
12. (Post-experiment) Actual Outcomes, Validated Learning, Decision, Rationale, Next Steps

**Decision rule outcomes after an experiment:**
- **Promote** — hypothesis sufficiently validated; proceed to spec
- **Iterate** — partial validation; create a new learning contract with modified hypothesis
- **Re-clarify** — experiment revealed the problem frame or assumptions were wrong; return to clarify
- **Abandon** — hypothesis unequivocally disproven; stop and reallocate

**Key convergence guardrails (Shape Up / Lean Startup / HDD):**
1. Fixed timebox / appetite — maximum investment is set before the experiment starts; decision is forced when it expires
2. Clear learning threshold — "enough learning" is defined upfront, not after the fact
3. Specific testable hypothesis — prevents scope creep and unfocused exploration
4. Minimal viable experiment — smallest artifact to test the core claim
5. Defined decision rule outcomes — forces closure; prevents analysis paralysis
6. Limited WIP — maximum number of active learning contracts at once
7. Regular review cadence — binding decision gates at fixed intervals

**Command surface verdict (Gemini):**
Option B (new `/cortex-experiment` command) is cleaner because: experiment lifecycle (`open/run/close`) is not a single-pass operation; two distinct artifacts (`learning-contract` + `result`) don't fit the dossier pattern; write-root permissions should be managed at the command level, not inferred from a flag value; forcing it into `--phase` would create a god command that violates single responsibility.

**Top 3 convergence failure risks:**
1. **Analysis paralysis** — endless exploration; no exit criteria → guardrail: timeboxes + decision gates
2. **Scope creep** — shiny object syndrome; frame drifts from original problem → guardrail: locked problem statement + out-of-scope backlog
3. **Indecision** — multiple viable options, no designated decision-maker → guardrail: explicit decision owner + decision framework (RICE, Pugh matrix, etc.)

## Trade-offs

### Option: Extend /cortex-research with --phase experiment

**Pros:**
- Keeps 7-command surface intact
- Reuses existing `--phase` routing infrastructure
- Minimal surface area change

**Cons:**
- Experiment has a lifecycle (open/run/close); existing phases are single-pass — forcing lifecycle into a flag creates conditional branching inside a command that is currently uniform
- Two output artifacts (learning-contract + result) don't fit the dossier template model
- Write-root policy for experiment would have to be inferred from a flag value, not from the command itself — fragile and error-prone
- Violates single responsibility: `/cortex-research` would need to handle both single-pass intelligence work and multi-step experimental lifecycle

**Verdict:** rejected

### Option: New top-level /cortex-experiment command (8th command)

**Pros:**
- Clean separation of concerns: research explores, experiment tests
- Lifecycle (open/run/close) is a natural fit for a dedicated command
- Write-root permissions managed at command level — explicit and auditable
- Artifacts (learning-contract, result) are first-class, not shoehorned into dossier schema
- Scales cleanly if additional lifecycle commands emerge

**Cons:**
- Breaks the "7-command surface" described in CORTEX.md and COMMANDS.md (now 8)
- Small additional cognitive surface for users
- Some boilerplate duplication with /cortex-research (slug resolution, state reads)

**Verdict:** selected — the lifecycle difference is decisive; "7-command surface" is a doc constraint, not a hard architectural limit; the right number of commands is the number that correctly models the distinct operations

### Option: reclarify_required as dossier field only

**Pros:** Simple; no state.json schema change

**Cons:** `/cortex-spec` would need to read all dossiers to find any that set this flag — fragile, order-dependent

**Verdict:** rejected in favor of propagating to state.json as a top-level flag

### Option: reclarify_required in state.json (propagated from dossier)

**Pros:** `/cortex-spec` reads one file; clear gate; easy to check and reset
**Cons:** Requires /cortex-research to write to state.json when flag is set — adds a write step to the research skill

**Verdict:** selected

### Option: uncertainty register replaces open-questions.md

**Pros:** Clean break; no legacy schema to support

**Cons:** Breaks existing continuity for slugs that already have open-questions.md; scaffold needs updating; more disruptive

**Verdict:** rejected — evolve open-questions.md in place by adding structured fields; flat questions remain valid entries with defaults

### Option: uncertainty register as a separate artifact

**Pros:** open-questions.md stays simple; uncertainty register is explicitly structured

**Cons:** Two files doing related jobs; `/cortex-spec` needs to check two places; continuity overhead doubles

**Verdict:** rejected — evolve open-questions.md

## Recommendations

- **Introduce `/cortex-experiment` as an 8th command.** The lifecycle difference is the deciding factor. Update CORTEX.md and COMMANDS.md to reflect "8-command surface" and document the rationale.
- **Add `reclarify_required: false` to `state.json` schema.** `/cortex-research` sets it to `true` when evidence changes the frame. `/cortex-spec` blocks if `true`. `/cortex-clarify` resets it to `false` when a new brief is written.
- **Evolve `open-questions.md` into an uncertainty register.** Add fields: `type: frame|knowledge|design|evidence|eval`, `severity: critical|noncritical`, `resolution_path: research|experiment|human`, `status: open|resolved|deferred|accepted-risk`. Flat entries default to `type: knowledge, severity: noncritical, resolution_path: research, status: open`.
- **Add `experiment_complete` gate to `state.json`.** Keep it optional for slugs that skip experiment — but when `/cortex-experiment` runs, it sets this gate. `/cortex-spec` can check it if any critical uncertainties were assigned `resolution_path: experiment`.
- **Tighten `/cortex-spec` readiness gate.** Add three blockers: (1) `reclarify_required` is false, (2) no `open` critical uncertainties remain, (3) every core assumption in the dossier is backed by research or experiment evidence. Current gate (clarify brief + any dossier) is too shallow.
- **Add `docs/cortex/experiments/` to scaffold and phase guard permitted roots.** One-line patch to `scaffold_runtime.sh` (`DOCS_SUBDIRS`) and one-line patch to `cortex-phase-guard.sh` (permitted roots). No other guard changes needed.
- **Update INTELLIGENCE_FLOW.md** to replace the strictly linear spine with the discovery loop diagram: clarify ↔ research ↔ experiment → spec (commitment boundary) → execute → validate ↔ repair → assure → done. Annotate that pre-spec backtracking is permitted; post-spec repair loop re-enters validate, never clarify.
- **Write DISCOVERY_LOOP.md as the authoritative design reference.** CORTEX.md and INTELLIGENCE_FLOW.md should reference it. It defines: mode transitions, artifact schemas for learning-contract and experiment-result, uncertainty register schema, spec-readiness gate definition, write-root policy for experiment mode, convergence guardrails.
- **Fix the phase guard meta-system gap separately.** The hot-context and reup snapshot paths outside `CLAUDE_PROJECT_DIR` are blocked today and will remain blocked. This should be addressed by adding an allowlist of known meta-system path prefixes (e.g., `~/.claude/`) to the phase guard, independent of the discovery loop work.

## Open Questions

- Should `/cortex-experiment` have explicit subcommands (`/cortex-experiment open`, `/cortex-experiment close`) or use a `--action open|run|close` flag? The lifecycle structure suggests subcommands, but the existing CLI style uses flags.
- What is the maximum number of concurrent active learning contracts? HDD and Shape Up both recommend limiting WIP — should this be enforced in state.json or left as a human discipline?
- How should the uncertainty register distinguish between uncertainties that _were_ resolved by a previous experiment vs. those that are still open? The `status: resolved` field covers this, but it needs a `resolved_by` pointer (experiment ID or research dossier path).
- Does DISCOVERY_LOOP.md belong in `docs/` (human-readable architecture doc) or as a template/schema file? The recommendation is `docs/DISCOVERY_LOOP.md` alongside INTELLIGENCE_FLOW.md.
- The phase guard meta-system gap (hot-context, reup blocked during pre-spec): should the fix be an allowlist in the guard script, or a separate hook that runs with lower privilege? The allowlist approach is simpler but requires hardcoding paths.
