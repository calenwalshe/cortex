# Clarify Brief: semantic-retrieval

**Slug:** semantic-retrieval
**Timestamp:** 20260403T233000Z
**Status:** draft
**Complexity:** complex

---

## Idea

Add semantic memory retrieval to Cortex so that session-start, postcompact, and skills can load only the facts relevant to the current task — not the entire facts.jsonl. Uses embeddings (local or API) over the .cortex/facts.jsonl store produced by the memory-extraction milestone. Based on pattern #12 from pattern-harvest research — Mem0/CrewAI/LangGraph Store pattern. Goal: 14x token savings on context loading by retrieving only relevant facts instead of loading all handoff files equally.

---

## Goal

Any Cortex hook or skill can query the fact store with a natural language question and get back the top-K most relevant facts in <2 seconds, so that context loading is selective rather than exhaustive — reducing token waste on irrelevant facts while preserving the important ones.

---

## Non-Goals

- Not building a full RAG pipeline (no document chunking, no retrieval-augmented generation loop)
- Not replacing the existing handoff file system (current-state.md, next-prompt.md, decisions.md remain as-is)
- Not building a UI for browsing or managing facts
- Not supporting cross-project retrieval (facts are per-project in .cortex/)
- Not building real-time streaming embeddings (batch on compaction is sufficient)
- Not fine-tuning or training custom embedding models

---

## Constraints

- Embedding must work locally without API calls (hooks run offline, can't depend on network)
- sentence-transformers 5.3.0 + torch 2.11 + CUDA are available on the target machine
- No additional pip packages for vector storage — must use what's available (numpy, SQLite, or flat file)
- Retrieval must complete in <2 seconds (hooks and session-start have tight performance budgets)
- First embedding pass (indexing existing facts.jsonl) must be tolerable — can be slower but not minutes
- Must not break existing hooks or skills — retrieval is additive, not a replacement
- Storage format must be simple — no separate server process (no chromadb, no external DB)

---

## Assumptions

- sentence-transformers `all-MiniLM-L6-v2` (or similar small model) produces good enough embeddings for fact retrieval — perfect recall is not required, good-enough recall at low latency is
- The fact store will remain small enough (<10K facts) that brute-force cosine similarity over numpy arrays is fast enough without an ANN index
- Embeddings can be computed lazily — embed new facts on each compaction, not in real-time
- A simple Python script callable from hooks (via subprocess) is the right interface — no need for a long-running server
- The embedding model loads in <3 seconds on first call (cold start) and subsequent calls reuse the cached model

---

## Open Questions

- **Storage format for embeddings:** numpy .npy file alongside facts.jsonl? SQLite with BLOB columns? Separate .jsonl with base64-encoded vectors? What's simplest to maintain and query?
- **Model choice:** all-MiniLM-L6-v2 (384-dim, fast, good quality) vs all-mpnet-base-v2 (768-dim, better quality, slower)? Or use ollama's embedding endpoint for consistency?
- **Cold start problem:** First invocation loads the model into memory (~1-3s). Is this acceptable for session-start hooks? Should we pre-warm somehow?
- **Query interface:** Python script with CLI args? Node.js wrapper calling Python? A shared library? What's the cleanest integration for hooks (bash/Node.js) calling into Python embedding code?
- **Embedding staleness:** When facts.jsonl grows, how do we know which facts are already embedded? Track embedded count? Use fact IDs?
- **Retrieval consumers:** Which hooks/skills will actually call retrieval? session-start? postcompact? cortex-status? All skills? Need to define the integration surface.

---

## Next Research Steps

1. Benchmark sentence-transformers model options on this machine — measure load time, embedding speed (facts/sec), and embedding dimension for all-MiniLM-L6-v2 vs all-mpnet-base-v2
2. Benchmark retrieval approaches — brute-force numpy cosine similarity vs faiss-cpu (if installable) vs SQLite with manual cosine — measure latency at 100, 1K, 10K facts
3. Research Mem0's embedding storage format — how do they persist embeddings alongside facts?
4. Design the embedding index format — evaluate numpy .npy (simplest), SQLite BLOB (queryable), JSONL with base64 (portable)
5. Prototype the query interface — Python CLI script that takes a query string and returns top-K facts as JSON
6. Design the integration points — which hooks/skills call retrieval, what format they expect, how to inject retrieved facts into context
7. Evaluate cold start mitigation — can we pre-warm the model during session-start? Use a smaller model? Cache embeddings in a format that doesn't require the model for retrieval?
