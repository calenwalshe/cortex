## Summary

The fix is **progressive disclosure** — a single HITL output with 3 layers, not 3 separate reports. The default layer is the owner summary (what it is, what we found, what could go wrong, your decision). Expanding reveals implementer detail. The full artifact is the auditor view. This matches the NN/g canonical pattern and the CLI verbosity convention (`-v`, `-vv`). The failure case research confirmed: verbose unprioritized reports cause alert fatigue and get ignored. The implementation is a template system in each skill's HITL output section, controlled by a single `report_level` setting.

## External Research (5 searches, 4 providers, $0.090)

### Search 1: Audience-Aware Reporting — SEED (Perplexity, $0.018)

**Three-layer model confirmed across industry:**

| Layer | Audience | Focus | Language |
|-------|----------|-------|----------|
| 1 | Executive/Owner | Business impact, ROI, risks, decision | Plain language, no jargon |
| 2 | Mid-level/Implementer | Benefits, architecture, trade-offs | Technical but concise |
| 3 | Expert/Auditor | Full methodology, data, evidence | Complete technical detail |

**Key insight:** AI tools can generate audience-adapted summaries from the same underlying data. The template approach (same data, different rendering) is better than generating separate reports.

### Search 2: Progressive Disclosure in CLI — VOCABULARY (Gemini, $0.039)

**Canonical patterns:**
- **Verbosity flags:** `-v`, `-vv`, `-vvv` (standard CLI convention)
- **Structured output:** `status` (OK/WARNING/ERROR) + `message` (human summary) + optional `detail`
- **Default is summary, detail on request** — not the other way around

**GitHub PR format as model:**
- Title: concise headline
- Summary: 2-3 bullets on what and why
- Detail: full diff, linked issues, test results
- This is exactly the progressive disclosure pattern: headline → summary → full detail

### Search 3: AI Tool Output Patterns — REFINE (Tavily, $0.016)

No directly applicable patterns found for HITL gate output specifically. AI coding tools (Claude Code, Cursor, Copilot) don't have a standardized "status report" format — they just output results inline. This is a gap Cortex can fill.

### Search 4: NN/g Progressive Disclosure — DEEP DIVE (Jina, $0.0001)

**Canonical UX principle (Jakob Nielsen, NN/g):**
- Show only the most important options initially
- Offer larger set on request
- "Most users can proceed without worrying about added complexity"

**Two criteria for progressive disclosure:**
1. Most relevant information first (what the user needs for their decision)
2. Secondary information available but not forced

**Staged disclosure:** Reveal one screen at a time, each with limited info, each advancing the task.

### Search 5: When Reports Fail — FAILURE CASES (Perplexity, $0.017)

**Why developers ignore AI status reports:**

| Problem | Impact |
|---------|--------|
| Verbose logs without prioritization | High cognitive load, skipped reviews |
| Missing rationale or metrics | Hard to assess urgency, inaction |
| Alert overload / unfiltered notifications | Fatigue, ignored critical issues |
| Ambiguous task handoffs | Outputs seem irrelevant |

**The fix the research recommends:**
- Urgency levels (not just status)
- Summary of actions tried (not just results)
- Hierarchy: critical → important → informational
- "What should I do next?" as mandatory field

## Design Decisions — All Resolved

### 1. Architecture → Progressive disclosure (3 layers in one output), not 3 separate reports

**Decision:** Single output with expanding detail. Owner summary is always shown. Implementer detail shown if `report_level >= 2`. Auditor detail shown if `report_level >= 3` or available as file link.

**Why:** NN/g confirms this is the canonical pattern. Three separate reports would mean maintaining three templates per gate type. Progressive disclosure means one template with conditional sections.

### 2. Default Level → Owner (Level 1)

**Decision:** Default to plain language, decision-focused summary. Technical detail is opt-in.

**Why:** The failure case research showed verbose unprioritized reports get ignored. The owner is always the audience at HITL gates (they're the one deciding). Implementers and auditors can expand.

### 3. Owner Summary Template → 4 mandatory sections

**Decision:** Every owner-level HITL summary must include:

1. **What this is** — one sentence, no jargon
2. **What we found / What was built** — 2-4 bullets of outcomes, not process
3. **What could go wrong / Risks** — honest risks in plain language
4. **Your decision** — what the human needs to decide right now

**Why:** Maps to the failure case research: summary + rationale + urgency + "what should I do next?"

### 4. Configuration → `report_level` in `.cortex/autonomy.json`

**Decision:** Add `report_level: 1|2|3` to autonomy config. Default 1 (owner). Overridable per-invocation with `--report-level 2`.

**Why:** Autonomy config already controls gate behavior. Report level is another aspect of how the system interacts with the human. Same config surface, same precedence rules.

### 5. Implementation → Template strings in skill HITL output sections

**Decision:** Each skill's HITL gate output section gets a structured template with level-conditional sections. The LLM generates the owner summary in-session (needs judgment about what matters), then appends implementer/auditor detail from the artifact data.

**Why:** The owner summary can't be a mechanical template — it needs LLM reasoning to decide what the most important findings are and what the risks mean in plain language. The implementer and auditor levels are mechanical (extract from artifacts).

## Trade-offs

| Decision | Chosen | Alternative | Why |
|----------|--------|-------------|-----|
| Architecture | Progressive disclosure (3-in-1) | Separate reports per audience | One template, not three. Less maintenance. |
| Default level | Owner (plain language) | Implementer (technical) | Failure research: verbose reports get ignored |
| Summary format | 4 mandatory sections | Freeform | Structure prevents omitting "what could go wrong" |
| Config location | autonomy.json | Separate config / env var | Reuses existing config surface |
| Owner summary | LLM-generated in-session | Template-only | Needs judgment about what matters |
