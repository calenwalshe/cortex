## Idea

frequently, using cortex we're building some kind of system (not just code) but some kinda system. so that's cool... but often in the cortex framework we need to decompose a system that we're building and have representation of it that the LLM can reason about and understand... but I want to do that once and do it deeply but then use it down the road... see we'll make a lot of changes and then it will come out of sync and we need to be resiliant to that... so basically this decompose helps, but its not the ground truth... we could update it too if we want... but if we don't it won't mess us up... it can only be helpful . you know what I mean?

## Goal

Introduce a durable, structured system decomposition artifact into the Cortex lifecycle that gives the LLM deep architectural context for reasoning across sessions — designed as advisory context (never a blocking gate), resilient to drift, and cheap to refresh but safe to ignore.

---

## Non-Goals

- Not a replacement for specs or contracts — the decomposition map is context, not a build plan
- Not a runtime dependency — no command should fail because the map is stale or missing
- Not an auto-sync mechanism — this does not watch code changes and self-update
- Not a formal architecture decision record (ADR) system — it captures structure, not rationale for decisions
- Not a project management or tracking artifact — no status, no progress, no milestones

---

## Constraints

- [owner-intent] No code without contract. Production code must not be written before a contract is approved.
- [owner-intent] Validators must run. No slug closes without validators passing.
- [owner-intent] Disk is truth. All state lives in repo artifacts. Chat is ephemeral.

- [owner-intent] No sycophantic evals. Eval rubrics must test for actual correctness.
- Must be a file-based artifact (no database, no external service) — per owner anti-goals
- Must not introduce new blocking gates into the Cortex pipeline
- The artifact must degrade gracefully — if stale, it provides partial context; if missing, everything still works
- Must be usable by any Cortex command that benefits from system-level context (research, spec, review, etc.)

---

## Assumptions

- The systems being built in Cortex are complex enough that a single session cannot hold the full picture — decomposition provides value across session boundaries
- LLMs reason better about systems when given structured component/relationship representations vs. raw code traversal
- Staleness is acceptable because the map captures architectural intent and component boundaries, which change less frequently than implementation details
- The existing Cortex artifact conventions (markdown, frontmatter, docs/ directory) are sufficient for this artifact type
- Users will occasionally refresh the map when it drifts too far, but the system should not nag or require this

## Open Questions

- What structural format best balances LLM reasoning quality with human readability? (e.g., nested markdown sections, YAML component graph, mermaid diagrams, or a hybrid)
- At what granularity should the decomposition operate? (system → subsystem → module → function, or just the top two levels?)
- Which Cortex commands should automatically load the decomposition map as context, and how should they consume it? (full injection, summary injection, on-demand reference)
- Should there be a lightweight "freshness signal" (e.g., a last-verified timestamp) so the LLM can weight its confidence in the map, without making it a hard gate?
- How should the initial decomposition be generated — manual authoring, LLM-assisted discovery from codebase, or a hybrid where the LLM proposes and the user confirms?
