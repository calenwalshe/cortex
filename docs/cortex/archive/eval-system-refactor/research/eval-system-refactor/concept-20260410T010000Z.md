## Summary

The Cortex eval system has the right conceptual shape (proposal → approval → plan → execute → results → repair) but is operationally hollowed out: the eval-designer agent is defined but never invoked (cortex-research writes proposals directly, bypassing it), eval-plans are 68–73% mechanical duplication of eval-proposals, results files are self-reported by the same session that wrote the code (directly violating owner-intent's "honest quality signal" non-negotiable), the repair loop documented in `docs/EVALS.md` has zero automation behind it, `eval-status.md` has a template but no producer, and the <10% false-positive kill criterion has no instrumentation. Of 10 slugs with eval artifacts, only 2 have executed results — and both were written in the same session as the implementation. This is a refactor target, not a redesign target: the bones are correct, but several components are aspirational documentation without code.

---

## Findings

- **Dead agent**: `cortex-eval-designer` is fully defined at `.claude/agents/cortex-eval-designer.md` with write-scope guards and a detailed proposal protocol, but `.claude/skills/cortex-research/SKILL.md` Phase 3 writes `eval-proposal.md` directly. Zero invocations of `@cortex-eval-designer` exist anywhere in hooks, skills, or other agents. The write-guard hook that protects its scope (`cortex-write-guard.sh`) is never triggered.
- **Proposal→plan duplication**: Across all 10 eval slugs, the transformation from `eval-proposal.md` to `eval-plan.md` is deterministic: filter approved dimensions, drop rubrics section, drop failure taxonomy section, add hand-authored Run Instructions. Fixtures are copied 100% verbatim; thresholds 98%. The only non-derivable content in the plan is the Run Instructions section (20–45 lines per plan). 68–73% of plan content is mechanically reproducible from the proposal.
- **Self-reported results**: Both executed eval result files (`kalshi-adaptive-loop/results-20260407T064500Z.md`, `kalshi-calibration-harness/results-20260407T060200Z.md`) were written in the same session as the code they evaluate. `kalshi-calibration-harness` results even document fixes applied *during* eval execution (`.gitignore` patterns added mid-run, recorded as "PASSED (with fix)"). There is no separation between code author and eval executor.
- **Repair loop is documentation-only**: `docs/EVALS.md` claims failed evals produce a "repair recommendation" and may "open a repair contract" with automated re-runs. No code generates repair recommendations. `cortex-postcompact.js` searches artifacts for existing `## Repair Recommendation` sections but never writes one. `cortex-task-completed.sh` detects `FAIL` lines in `eval-status.md` and blocks completion, but there is no next step — the blocking is terminal, not routing.
- **`eval-status.md` has no producer**: The 54-line template at `templates/cortex/eval-status.md` defines a composite scoring structure (dimension → 0–1 score → weighted composite). The live file at `docs/cortex/handoffs/eval-status.md` is an 11-line empty skeleton. `cortex-task-completed.sh` reads it; nothing writes it.
- **Failure taxonomy is written-only**: Every eval proposal contains a populated failure taxonomy table with severity (P0–P2) and repair paths, but no process reads these tables during failure handling. They're deleted entirely when the plan is generated. The `.gitignore` failure in `kalshi-calibration-harness` was not in the taxonomy and was fixed ad-hoc, with no feedback loop to update the taxonomy.
- **Run instructions are prose**: All 10 eval-plans encode run instructions as numbered Markdown steps with embedded fenced `bash` blocks. They are not machine-parseable; no tool extracts and executes them. Scaling requires manual shell execution by a human.
- **No false-positive instrumentation**: Owner-intent requires <10% validator false positive rate and defines >25% as a kill criterion. No logging, tracking, correlation, or computation of this rate exists anywhere in the repo. The kill criterion is unmeasurable and unactionable in its current form.
- **Idempotency gap in proposal writing**: The eval-designer agent definition states "if an eval proposal already exists, do not overwrite without explicit instruction," but cortex-research SKILL Phase 3 has no such guard. Re-running `/cortex-research --phase evals` silently overwrites, losing approval status.
- **10 proposals, 2 executions**: The system has produced proposals and plans for 10 slugs, but only 2 have produced results files. The 8-slug gap is not tracked anywhere — there is no backlog of "evals awaiting execution" visible to continuity state.

## Trade-offs

### Option A: Collapse proposal and plan into a single artifact
**Pros:**
- Eliminates 68–73% duplication across 10 slugs
- Removes the "selective deletion" smell where rubrics and failure taxonomy are written then discarded
- Single source of truth for eval intent and execution

**Cons:**
- Loses the approval inflection point between proposal (draft) and plan (approved subset)
- Approval gate would need to be represented as status on a single artifact rather than as a transition between two artifacts
- May make it harder to track "what was proposed but rejected"

**Verdict:** deferred — depends on whether the approval gate adds real value or is also rubber-stamp ceremony

### Option B: Automated proposal→plan generator (keep both artifacts)
**Pros:**
- Preserves approval inflection between draft and approved
- Eliminates manual duplication by making plan a deterministic filter of proposal
- Easy to implement: small script that reads proposal + approval decision, writes plan
- Backward compatible with existing artifacts

**Cons:**
- Preserves ceremony: two artifacts where one would do
- Still requires Run Instructions to be hand-authored somewhere (in proposal? separate file?)
- Does not solve the underlying question of whether the split is load-bearing

**Verdict:** selected (Phase 1) — lowest-risk, highest-leverage refactor; can happen without resolving Option A

### Option C: Executable eval manifest (hybrid: scripts for mechanical, markdown for subjective)
**Pros:**
- Enables automation: mechanical evals (functional, regression, integration, style) become runnable by tools
- Structured output (JSON) enables result parsing, failure classification, and repair routing
- Preserves approval gates for subjective dimensions (UX/taste, safety judgments) as markdown
- Makes eval-status.md composite scoring computable

**Cons:**
- Significant refactor of the Run Instructions model
- Existing 10 eval-plans would need migration or coexistence with new format
- Introduces a second artifact format alongside markdown (schema drift risk)

**Verdict:** selected (Phase 2) — necessary for automation, but should follow after duplication fix

### Option D: Independent evaluator separation (anti-sycophancy)
**Pros:**
- Directly addresses owner-intent non-negotiable: "No sycophantic evals"
- Forces a blind verification step between code implementation and results signoff
- Creates conditions where FP rate can be measured (two independent signals to correlate)
- Cheapest form: a separate agent session that cannot see code-writing context

**Cons:**
- Slower: adds a verification session to every execute→done transition
- Requires clear protocol for what evaluator can/cannot see
- Risk of evaluator becoming another rubber stamp if not carefully designed

**Verdict:** selected (Phase 3) — highest owner-intent alignment but highest operational friction; sequence after automation is in place

### Option E: Activate cortex-eval-designer (delegate from cortex-research)
**Pros:**
- Uses the existing agent definition rather than deleting it
- Provides write-scope enforcement via existing hook
- Natural home for eval-designer logic separate from research skill

**Cons:**
- Agent isolation costs context (designer sees less than the research skill does)
- Does not solve any of the other findings (duplication, self-reporting, etc.)
- May be premature if we end up collapsing proposal and plan (Option A) — the agent's scope would change

**Verdict:** deferred — decide after Options B/C/D are in place; may become moot

### Option F: Delete cortex-eval-designer (accept SKILL-owned eval design)
**Pros:**
- Removes dead code
- Acknowledges de facto reality (SKILL writes directly)
- Simpler system with fewer components

**Cons:**
- Loses the write-scope enforcement that the agent provides
- Signals that cleanup > principled architecture

**Verdict:** deferred — depends on Option E decision

## Recommendations

- **Phase 1 (quick win, highest leverage):** Build a deterministic proposal→plan generator. Input: `eval-proposal.md` + approval decision. Output: `eval-plan.md` with approved dimensions, copied fixtures and thresholds, and Run Instructions lifted from a new `## Run Instructions` section in the proposal (or stored separately). This eliminates 68–73% duplication and guarantees consistency.
- **Phase 1b:** Add an overwrite guard to cortex-research SKILL Phase 3 matching the eval-designer agent's rule. Re-running `/cortex-research --phase evals` must not silently destroy approval status.
- **Phase 2 (automation enabler):** Introduce a machine-readable eval manifest (JSON or YAML sidecar) encoding: dimension → fixtures → executable commands → pass/fail patterns. Keep the markdown eval-plan as human-readable documentation generated from the manifest. Build a minimal `cortex-eval-run` script that parses the manifest, executes commands, captures exit codes and structured output, and writes a results file. Start with functional correctness dimension only.
- **Phase 2b:** Make the failure taxonomy machine-readable. Index it by error pattern or exit code. On failure, look up the category and emit a structured repair recommendation (even if the recommendation is initially just "see taxonomy row X").
- **Phase 3 (anti-sycophancy):** Enforce separation between code author and eval executor. Simplest form: eval-run must be invoked in a fresh session (or subagent with restricted context) and cannot modify code files — only read, execute, report. The write-guard hook pattern already exists; extend it to the executor role.
- **Phase 3b:** Add false-positive instrumentation. Log each eval pass event to `.cortex/supervisor.jsonl` or a dedicated `eval-ledger.jsonl`. When a bug is later found in eval-passed code, log it as an FP case linked to the eval. Compute rolling 10-slug FP rate. Alert at >10% (warning) and >25% (kill criterion). This is cheap to add once the ledger exists.
- **Phase 4 (cleanup):** Decide cortex-eval-designer's fate. If Phase 1's generator lives in the SKILL, archive the agent with a comment linking to the commit that replaced it. If the generator lives in the agent, activate it and update the SKILL to delegate.
- **Phase 4b:** Decide eval-status.md's fate. If composite scoring is valuable, populate it from the Phase 2 run results (cheap once manifest exists). If not, delete the template and stop referencing it.
- **Defer:** Full proposal/plan collapse (Option A). Revisit after Phase 1 ships — if the approval gate on plans turns out to be ceremonial in practice, collapse them. Don't pre-decide.

## Adjacent Findings

- **Failure taxonomy as router, not doc:** The failure taxonomy tables in proposals are written with `Severity` and `Repair Path` columns implying operational routing, but no process reads them. This is a repeating pattern in the eval system — design documents get written as if they will be consumed by code, then no consumer is built. Watch for this pattern in Phase 2: machine-readable formats are only valuable if something machine-reads them. Source: all 10 eval proposals; no grep hits for taxonomy row parsing anywhere in hooks or skills.
- **Ten proposals, two executions — an invisible backlog:** 8 slugs have eval-plans that were never executed. These are not tracked as pending work anywhere in continuity state (`state.json`, `current-state.md`, `open-questions.md`). If eval execution is important to correctness, invisible eval backlog is a direct contradiction of the "disk is truth" non-negotiable. Matters for this slug because the refactor should decide whether to: (a) backfill those 8 executions, (b) treat them as opt-in future work, or (c) track them explicitly as eval debt. Source: `docs/cortex/evals/**/results-*.md` file count vs slug count.

## Open Questions

- Should Phase 1's generator be a script (in `scripts/cortex/`) or a hook (triggered on eval-proposal approval)? Leaning script-first for testability, but a hook gives automatic enforcement.
- For Phase 2's manifest format: JSON or YAML? YAML is more readable but adds a parser dependency. JSON is standard and parseable with built-ins.
- Does the Run Instructions section belong in the proposal or a separate sidecar? If in the proposal, it's visible during approval (good). If separate, the plan generator is simpler.
- Phase 3's "fresh session evaluator" — can this be a sub-agent in the same Claude Code session with restricted tool access, or does it need genuine process isolation? Sub-agent is cheaper but may not be "independent" enough to kill self-report bias.
- Should the 8 unexecuted eval-plans be executed retroactively as part of this refactor, or declared eval debt and scheduled separately? Backfilling would test the Phase 2 tooling end-to-end but adds scope.
- Is the approval gate between proposal and plan actually load-bearing today? Checking the autonomy config: `eval_proposal` gate defaults to true in supervised preset, but when does it actually fire in practice? If approvals have always been auto-approved in this repo, Option A (collapse) becomes more attractive.
